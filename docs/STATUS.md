# Status, a record

A record of how Yerk AI was built, one paragraph for each stage of the work ("Layer 4, run 2" and the like), for a reader who wants to know why a part works the way it does. The paragraphs were written as the work went on, and a few were brought up to date later, but the page as a whole is not checked against the code: a paragraph can describe something that has changed since. For what the code does now, read the six pages beside this one, which `yerk docs own` writes from the code, and CHANGELOG.md for what each merge changed.

## Status

Layer 5, run 3: one heavy worker per account, worker tools and the relay's edge cases (its watcher job kind left in shrink-1). Workers wait in line for their account (`[workers] per_account`, default 1), the card saying "waiting for an account" and the place, and the daemon starts the next when the account frees; `yerk status` shows the line. A worker gets no Yerk AI tools unless `[workers] yerk_tools` names the read-only ones (`recall`, `read_memory`), which come from its own stdio server that has no `send`, `worker` or `schedule` to give. A relay waits for an idle room (the card carries the result meanwhile), runs as a turn of its own (two completions are two relays, in order, never merged), and resumes the room's own session when the room's process is closed, as any message does, never a fresh one. A job's failure in a room reads "job NAME failed: it ended with an error" or "job NAME stopped: timed out at 10 min"; the exit code is in the run's ledger note and `yerk status --full`. A worker that moves account mid-run is not built.

Layer 5, run 2: scheduled jobs and the typing signal. The owner's timed work comes from one private `jobs.toml` (the example with placeholder values is `examples/private/jobs.toml`; `yerk explain jobs` describes every key from the code): a job is a `script` (a shell line run inside its unit under an account-free environment, with a cap), an `agent` (a worker with the message as its brief, the job's account and cap, its card in the job's room) or a `note` (a reminder: when it is due the room's own session is told its `message` and says it in its own voice; no worker, shell or account), on one of two schedules: a systemd calendar line with an IANA `tz` (since shrink-1: `Mon 10:00`, never cron; a cron line is refused with the calendar line for it) or `at` (one time, removed from the file after it fires). `yerk jobs sync` generates one systemd user timer and service per job, idempotently (unchanged jobs untouched, changed ones rewritten and restarted, removed ones disabled and their files gone), prints the diff and then every next fire time read back from systemd, naming any job that cannot be scheduled with why; `yerk jobs list` is the read-back, and `yerk status` lists the jobs with their next fire from systemd, never from memory. Timers carry `Persistent=true` and `AccuracySec=1s`, so a missed run fires once on return and a one-shot lands on its second. A run delivers by the cron-wrap rule: exit 0 with output posts the output to the room, exit 0 with nothing posts nothing, a failure or a timeout posts one alert line to the ops room (`[jobs] ops_room` in yerkd.toml, else the job's room); an agent job's last message is told by the room's own session through the same relay as a worker's, and a last message of exactly `NO_REPLY` is silence. Every run is a row in the `job_runs` ledger (planned and fired times, how it ended, what was delivered or why nothing was). The `schedule` tool in every room and `yerk schedule` add a one-shot or a recurring job, remove one or list them, writing the file and syncing, and answer with the next fire time read back; a missing zone is the room's configured one, never UTC by accident. A room that is not the owner's adds, lists and removes its own notes and sees no other job, since agent and script jobs run as the owner and stay the owner's rooms' own; such a room keeps 20 notes at most and adds 3 per 5 minutes, so a reminder and its follow-up check go in one turn, its call with no `kind` sets a note, and a note's message is at most 600 characters in any room (`[jobs] room_notes`, `room_note_minutes`, `room_note_burst` and `note_chars` in yerkd.toml; each refusal says the cap); a note missed while yerkd was down is told at its next start. The Discord adapter now sends the typing signal from the moment a message is taken until the first card post or the reply, refreshed every 8 seconds while nothing is visible and never once a card exists; it is not a delivery and is ledgered as nothing.

Layer 5, run 1: workers. Heavy work leaves the room (the mechanics send work that will take more than about five minutes to it, with a one-line answer now): `worker` (a tool in every room) and `yerk worker start|list|stop|report` run a headless `claude -p` as its own systemd transient unit `yerk-worker-<id>`, which outlives the daemon: one named account (its token file is the only one the unit's environment names, read inside the unit the way a room reads it), a brief, a staging folder with stdout and stderr in it, a report path, a TASKS.md and a cap (65 minutes unless the call or `[workers]` in yerkd.toml says otherwise), no MCP server and no subagent tool, so no worker starts another. Its card in the room shows the start and the cap and ticks a row per TASKS.md line as the worker ticks it (an inotify watch on the folder, at most one edit a second). When the unit ends, its ExecStopPost record settles the card with the report's first line, the report path and the exit state (done, died, timed out, stopped, lost); when the room is idle (no human message for 60 seconds and no turn running) one relay turn in the room's own session says the outcome in its voice under 1,500 characters with the report path, and a message landing during it is answered inside it; otherwise the relay is skipped and the ledger says why. The `workers` table in the run ledger keeps every worker; `yerk status` lists the running ones checked against the unit list; a daemon restart re-attaches from both, so no card is orphaned.

Layer 4, run 1: memory, the foundation. Every message of every room is filed in the day's log in the private memory tree as it lands (attachment-only and one-character ones included, one line per attachment, never twice for one message id). `yerk-index` keeps an FTS5 index over that tree in its own process (`units/yerk-index.service`), writing only the chunks that changed, with `yerk-index --check` comparing it against the disk and telling a timeout from a failure. Rooms get `recall` and `read_memory`; `yerk recall-bench` runs fixed question sets from the private layer against the index in three kinds, each scored and held to its ratchet apart and all reported together: recall (`[memory] bench`, default `evals/recall-questions.json`), episodic (what happened on a day, `episodic-questions.json` beside it) and self (what the owner is like and wants, `self-questions.json` beside it) (weekly, `units/yerk-recall-bench.timer`). Each ability and its cost tier is in `abilities.toml`.

Layer 4, run 2: recall before the first word. `yerk-index` also builds a name index from the fact files and the curated file's headings whenever one changes. A line whose first six words hold a known one-word name is keyed by that name; a first name answers through its own line ("Ada: ..."). The prompt hook puts the entries for the names a message mentions, then the room's own lines of the last 14 days on the message's topic, in front of the model before it starts (at most 1,500 characters, `budgets.toml` `[per_message.on_hit]`), and writes what it assembled, part by part, to the room's `assembled.jsonl`. The session-start recall pack is the room's own filed items of the last 14 days (what the owner sent, decisions, drafts), newest first, up to 6,000 characters with the open commitments, and a SessionStart command hook adds it again after every compaction (`yerk room compact ROOM` asks for one). Every tool call is ledgered with what it read, and a rule check after each reply logs, in shadow, a quoted figure or file the turn never read (a figure in one of the room's replies posted earlier in the same session counts as read, since the check read that reply; its narration before a tool call, its sends, file captions and notes, which the check never read, do not) and a "what did we decide" answered with no memory read. A figure is on file only where a line is about the same thing: the label words beside it in the reply sit beside it there too, its unit agrees, and the line is not the reply's own record; a line that only shares the digits is not its source. `yerk-index --rebuild` builds a new generation and swaps a link, so recall never fails during a rebuild.

Layer 11, rail run 2: the room reaches for the owner's past before it answers, code deciding when (`words.py`): a question about the owner's past ("what did I", "who did I go to lunch with", "last friday", a date asked about) runs the recall tool's own search, in the room's scope and as its reader, and its best hits come in with their cites; a name brings its best lines from that scope after its card, newest first, and so does a name or topic the message asks about ("who is X", "what do you know about X"), which has the line `[named, nothing on file: X]` when nothing holds it, so "not on file" is code's word and the mechanics tell the room to say it plainly. The 2,000 characters of the recall part bend per hit: one name takes all of it, several names share it, and a past-tense search takes what the names leave (beside one, each name brings its card's first line). Measured on twenty questions about the owner's own days, with the meaning search too busy to answer inside the hook's two seconds: a 1,500-character part held the answer for 8, 2,000 for 10, 3,000 for 11; with the index healthy (the cold read of Oct 21), 9 at 1,500 and 11 at 2,000. So `recall = 2000` in `[per_message.on_hit]`, 500 more characters (about 125 tokens) on a message that hits and inside the 4,000 cap, set in its own commit as a visible decision.

Layer 4, run 3: meaning search behind the keywords. With a provider key in the private folder (`secrets/openai.key`, or where `[memory] embeddings_key` in `yerkd.toml` points), `yerk-index` embeds every chunk once (OpenAI `text-embedding-3-small` at 256 dimensions, changed chunks only, the vector stored next to the chunk's hash and copied across a rebuild), backfills the tree in the background, resumable and in batches with a gap between them, and serves the search on a local port; `recall` fuses the meaning rank with the keyword rank by reciprocal rank fusion, its answer shape unchanged. No key: keywords only, exactly as before, and the room is told once in one line. A provider timeout or error: keywords only for that query, logged, told apart from a failure of the index. `yerk abilities` lists every ability as 🟢 on, 🟠 needs a provider key, or ⚪ on its free path, and `yerk explain NAME` answers from `abilities.toml` (what it does, needs and costs, the free path). The example question set (`examples/private/evals/recall-questions.json`) carries the two room-recall kinds: what was sent in a room recently, and what was said there on a day. The backfill cuts a request at 250,000 bytes, under the provider's 300,000 tokens since its tokenizer makes at most one token a byte, and halves it at once on a 400 that names the size; its unit caps it at MemoryHigh = 256M + 8.3M per 16,384 vectors (800M holds 1,064,960); `yerk deploy` restarts yerk-index right after yerkd, and its proof wants both on the new commit.

Layer 4, run 4: recall moved from its misses. The bench grew from 46 to 164 scored questions (13 controls) in eleven kinds, and the misses were read by reason before anything was tuned: 13 of the 14 paraphrase golds sat outside the chunk vector's own top ten (a chunk vector averages several unrelated lines), and 5 keyword hits at ranks 2 to 6 were lost in the merge (under reciprocal rank fusion with constant 60 a lone rank-2 hit scores 1/62 and loses to any chunk both searches place anywhere in their pools). So `yerk-index` now embeds every line of a day log and every bullet of a fact or topic file on its own (a units table beside the chunks: 20 characters or more past the bullet, one vector per distinct text, shared with a one-line chunk, filled for an existing index on first start, written and dropped with its chunk, copied across a rebuild), serves the line vectors and the chunk vectors together (`[memory] embeddings_units`, measured best as `both`; `lines` or `chunks` alone are the alternatives) from a blocked float16 store that grows without copying itself (`[memory] embeddings_width` narrows it; 128 dimensions was measured and lost), and `recall` fuses with constant 20 and holds each search's own first hit in the top six. A source prior for fact and topic files over day logs was built as a boost and measured at 0.15, 0.3 and 0.5: every value lost on both rates, so it ships at 0. On the 164-question set: top six 66.5% to 71.3%, top one 37.2% to 36.0%, paraphrase 0 to 3 of 14, correction 12 to 15 of 15. The targets (75, 40, paraphrase 50) are not met; the remaining paraphrase misses are the embedding model's, 9 of 14 golds sitting outside the line vector's own top 50 on questions built to share no word with their line. The line backfill took 5 minutes and about 10.4M tokens; the index process serves 342,800 vectors at about 260 MB resident.

Layer 4, run 5: the paraphrase misses against two levers, each measured on the 164-question set alone and then together. Lever A embedded a line or bullet behind its heading path (`<file title> > <section heading>: <line>`, the hit shown still the chunk). Lever B is `text-embedding-3-large` ($0.13 per 1M tokens against $0.02 for small, OpenAI's pricing page, read 2026-10-18), stored at 512 dimensions and kept at 256 (`embeddings_model`, `embeddings_dim`, `embeddings_width`), the same memory as small. Run 4 as shipped: top six 117 of 164 (71.3%), top one 59 (36.0%), paraphrase 3 of 14. A: 117, 66 (40.2%), 1, with a control missed and 30% more vectors (the index peaked at 303 MB in memory plus 188 MB in swap). B: 110, 64 (39.0%), 2, losing most on stale-trap questions (9 to 6: a better match also ranks the stale copies). A and B: 114, 61, 4 at 256 kept; 117, 57, 5 at 384 and 116, 59, 4 at 512, both past 300 MB. The large model brings four of run 4's eleven paraphrase misses into its own top three at 384, yet the top six does not move, since what paraphrase gains the other kinds lose. No setting reaches 75, 40 and 50, so run 4's settings stay the defaults; lever B is a setting a user with another model or budget can pick, described with what it costs and bought in `yerk config get memory` and `yerk explain embeddings`. Lever A was measured, lost and removed (alone: top six 117, top one 59 to 66, paraphrase 3 to 1 of 14, a control missed, 30% more vectors and past 300 MB; with B: 114 at 256 kept, past 300 MB at 384 and 512): its setting, the `head` column, the units refill and the per-write vector scan are gone, and these numbers and the run's report are its record. The run's backfills: 79.1M tokens, $7.41.

Layer 4, the shrink pass: the six files that hold the memory layer (memory.py, memindex.py, embeddings.py, mentions.py, and cli.py and mcp_server.py, which carry its commands and tools) are 2,790 lines, from 2,875 on the main this merged into. Kept, and now tested: the FTS5 checks and the orphan shadow-table repair from Hermes Agent, so a recovered index file starts again on its own and a Python without FTS5 is told so in one line (the cold read put them back: a damaged index heals without anyone running a rebuild). Every other test passes unchanged, `yerk map` prints the same, and the bench on one copy of today's index gives every question the same rank before and after: top six 115 of 164 (70.1%), top one 59 (36.0%), keywords only 84 (51.2%) and 40 (24.4%). Run 4's 117 was measured on the index as it was then; today's index gives 115 with or without this pass.

Layer 4, the recall diet: `recall` hands the room the lines that carry the match, not whole chunks. Each hit is `{cite, text}`: the best line (the most query weight, each word weighted by its rarity as the keyword rank weighs it; the line whose vector the meaning search matched, which yerk-index now names, counts as a match), then every other line holding a query word, heaviest first, then the lines nearest the best one, at most 750 characters a hit, cut at line ends and kept in file order (a gap reads "…"; a line too long for what is left is cut around its matches, at spaces). The cite is the snippet's first line, and `read_memory` takes it as its path. A call's first six snippets hold at most `[memory] recall_chars` together (default 4,500, six hits of 750; `yerk config get recall_chars`), each a share of what is left, and each hit past the sixth adds its best line, cut around the match to at most 160 characters, so a call of twenty hits shows its first six exactly as a call of six does. Ranking is untouched: `ranked` is the old recall (the same hits in the same order), the bench scores rank on its whole chunks and adds `kept`, the found answers whose snippet still holds every answer token. read_memory's default window is 12 lines, from 40: a whole hit chunk from its first line for 98 in 100 found answers (the 98th percentile is 11 lines), and its description says to ask for more lines or a later `from_line`. Measured on the 164 questions against one read-only copy of today's index, main e35ac5b against this branch: every question at the same rank in both modes (top six and top one 84 and 40 keywords only, 116 and 59 with the key, the provider's query vectors replayed); at the first defaults, 700 and 4,200, answers kept in the snippet 83 of 84 keywords only (q0923-06 lost, its answer split across two long lines) and 116 of 116 with the key; characters per recall call, median 5,714 to 4,353 and 95th percentile 6,364 to 4,779 keywords only, 5,491 to 4,174 and 6,300 to 4,706 with the key; per read_memory call at a hit, median 8,616 to 2,945 and 95th percentile 21,381 to 12,603 keywords only, 7,642 to 2,545 and 21,296 to 9,508 with the key. The defaults now shipped, 750 and 4,500, are the cold read of pull request 30's measurement on the same questions: answers kept in the snippet 84 of 84 keywords only and 116 of 116 with the key, for about 155 characters a call more (median 4,506.5 keywords only and 4,329 with the key), still about 21% under main; at 700, four answers sat within 0 to 40 characters of the cut. The tool definitions shrink (recall 641 to 614 characters, read_memory 511 to 509) and `yerk map` does not grow. Until yerk-index restarts on this code its meaning hits name no line, and the snippet leans on the keyword weights alone. yerk-index names that line (`near`) only when the daemon's search asks for it, so a daemon from before the diet, whose room filter knows nothing of it, never receives it, and yerkd and yerk-index restart in either order. A cite whose line runs past nine digits, or a path holding a NUL, reads as no such file. Against main at e35ac5b: 137 new lines outside tests (memory 127, memindex 4, embeddings 4, cli 1, mcp_server 1), 9 new tests, 620 passing and 2 skipped in all.

Layer 4, recall warm: `yerk-index` keeps the pages the keyword rank reads (the FTS tables, the `chunks` rows it joins, `meta`; 413 MB at 314,010 chunks) mapped into itself, so recall, which reads the index file itself as before, finds them in RAM. A box may drop its page cache on a clock (`echo 1 > /proc/sys/vm/drop_caches`; the author's trimmer does, every 2 minutes), and a drop passes any mapped page by, for every reader of the file. A connection's own page cache cannot do this: SQLite drops it whenever the writer commits, which is every pass. The pages are mapped at start, within 5 s of a writer pass that changed chunks, every 10 minutes and after a rebuild, and never locked, so real memory pressure can still take one until the next pass. index.json carries `pin`, and the unit's MemoryHigh rule and `yerk doctor` count its bytes. Measured on the author's box with the trimmer running, 16 keyword ranks 12 s apart across one drop, recall's own read (a fresh read-only connection and the same search, 80 hits each): on a pinned copy of the live index a median of 0.116 s (0.173 at most, 0.116 right after the drop), on the live file unpinned at the same moments a median of 0.494 s (3.604 right after the drop); the first pass took 7.1 s.

Layer 6, run 1: the rule-based gates. Every Claude Code hook a room uses posts to the daemon (UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, Stop and ConfigChange over http; SessionStart through curl, the one way Claude Code runs it), and `yerk_ai/gates.py` decides by code, so its gates block. A plain `rm` or `unlink` (with -r too) is rewritten to the trash command with the same paths and runs; a delete in any other shape is refused with the trash line for the model; the room hears nothing unless the trash fails. Shell text is read quote-aware first: quoted text, heredoc bodies and a word in a sentence are not commands. A command on the hardline list (from Hermes Agent) never runs. A write to yerkd.toml, rooms.toml or accounts.toml, or a restart of yerkd, is refused with one line while a person is mid-conversation or the memory index rebuilds. An external action (a send to another room, a public post, a login, money, a message out through another tool, or a rule under `[gates.external]` in yerkd.toml) is held with one line until an approver says `approve` in the room, then that same call (its normalised text and folder) runs once and any other is held again; the word counts only from a message the room itself wrote into its running turn, under the room's bound session (/hook has no secret yet); hold, word and release are ledgered. A working turn that ends with nothing in the room bounces once, naming the message it owes, and never when a part already landed under the turn's key; a session that replaced another posts a reset line; a changed settings file is a tamper row (who, what, when, the diff's hash, from line hashes, never the text). The evidence ledger gains each call's time and failure, and every hook call's own time is a `hook_calls` row, so `Ledger.hook_overhead` is the overhead per turn against the 150 ms bar at the 95th percentile. Decision 25 runs in shadow: a sentence claiming what code does or lacks, what is running, a decision or a file's contents, with no test run, status read, memory read or file read behind it in the turn, is ledgered with the sentence and the tools the turn ran. The stance check runs beside it, also in shadow (ROADMAP-v3 claim 3): it reads the owner's messages of the turn for a disagreement word on a short list (`words.PUSHBACK`: nah, no, nope, wrong, actually, not true, that's not, you're wrong, I disagree), counts only when the room posted a reply earlier in the same session, reads the reply for agreement, a "still stands" clause and a mistake it names, and checks the turn's tool calls after the message for a source read; it logs one `stance` row per such reply, `held` (what still stands, with that read, or a reply that neither agrees nor names a mistake of its own, read or not), `conceded` (what it got wrong, with that read) or `folded` (it agrees or concedes with neither), counted by label in the morning diff with only a fold as a finding, and it would start bouncing a fold only once it shows under 1 in 10 false alarms on 100 cases with a known-good control passing (decision 8). Two more run in shadow beside them: `person`, a sentence telling what someone said, wants, knows, decided or asked, or where they were (the owner as "you" included), from a turn that made no call that reads, and `quote`, a quoted span of three or more words given as someone's or a document's words that no read, prompt or earlier reply of the session carries; each is ledgered with its sentence or span and counted in the morning diff. The five judge-model reply gates are not built; none may block until it shows under 1 in 10 false alarms on 100 cases with a known-good control passing. A room gets tools beyond Read through `allow` in rooms.toml (permission rules), and the gates still run first.

Said or noted: in an owner's room a reply or a `send` that tells what a third person said, decided, wants or asked, or quotes their words, from a turn that made no reading call is turned back once with the fix (read where their words are and cite it, or write it as "from my notes, not their words"); the second try goes out, a person's room only logs, and each refusal is a `person-refused` or `quote-refused` shadow row the morning diff counts. A sentence about the owner ("you", or the name `[import] me` gives his words) or the room is never such a claim. A room's own note is shown behind "[the room's note, not their words]" wherever recall shows it, a person's words filed with `remember` `said` and `source` behind "[their words]", and the text files sent to an owner room (its `work/inbox`, transcripts included) are recall roots there.

Pictures seen: a picture sent to an owner room (png, jpg, jpeg, gif, webp, heic) is filed beside it in the same turn as `NAME.seen.txt`, so a later recall finds it the way it finds the uploads and transcripts. The room reads the picture before answering anyway, so the `seen` tool costs no second model call: it writes a first line by code (the room, the message id, the local time it was saved, its name), then every word on the picture as the room read it, in reading order (a screenshot of a chat keeps who said what exactly as shown), then a line or two of what it shows: a person in a photo the owner sends in his own room is the owner unless its own text says otherwise, anyone else named only as the picture's own text names them. The sidecar is a text kind of the inbox, private, cited as `<room>/work/inbox/<id>/NAME.seen.txt:line`, and recall and read_memory show its lines behind "[text on a picture he sent, as the room read it]", never as anyone's words; a room that read a picture and filed nothing is turned back once to file it. A person's room files no picture, as its uploads are never indexed. `yerk pictures backfill ROOM [--limit N] [--dry-run]` files the pictures sent before this: Yerk workers on the room's own account and model read them 20 to a batch, one batch after another so the account's other workers wait for one batch at most, each batch's card and one line in the machine room; `--dry-run` lists each sidecar it would write and starts nothing. `--root FOLDER` does the same for the pictures under a folder the room lists in rooms.toml (`read` or `also`), each sidecar beside its picture, cited and indexed under that folder as its other files are (a file there with no front matter is private); any other folder is refused.

Workbooks and PDFs: an .xlsx or .xlsm, or a PDF, sent to an owner room gets its text written beside it as it is staged, by code with no model call, so a later recall finds what is in it the way it finds a picture's sidecar or a transcript. `NAME.sheet.txt` has a `## <sheet name>` section for each sheet, a line for each row with a value, its cells tab-separated, a formula as the value saved with it; `NAME.pdf.txt` has a `## page N` section for each page. Its first line is written by code like a picture's (the room, the message id, the local time it was saved, its name, its sheets or pages). A PDF with no text on any page (a scan) gets that one line with its pages and "no text layer, not read", never OCR; a file that does not open, one line saying so. Past `[files] chars` in budgets.toml (200,000) the text is cut and its last line says how many characters were not kept; a file still being read after `[files] secs` (60; a PDF reads at about half a second a page) stops there, its last line saying so. The `[attachment]` line names the text file, so the room can read it in the same turn; a file that takes past 30 s goes in without it and its text lands when it is done. The text file is a text kind of the inbox, private, cited as `<room>/work/inbox/<id>/NAME.sheet.txt:line`, and recall and read_memory show its lines behind "[text of a file sent to the room, as extracted]", never as anyone's words. A person's room's files are never read this way. `yerk files backfill ROOM [--dry-run]` writes the text of the workbooks and PDFs sent before this, and of any whose text is older than the file, in that process with no yerkd and no model; `--root FOLDER` does the same under a folder the room lists in rooms.toml (`read` or `also`), each beside its file, cited and indexed under that folder. A .csv is a text kind already; Word and PowerPoint files are not read yet.

Needs: a room that cannot do what it was asked (no tool, a refused tool, a page that will not open) files what it needed with the `need` tool and never builds a way of its own, so every room keeps the one same way of doing each thing. The filing is one line, `- ROOM, TIME: asked: ...; tried: ...; needed: ... [m:ID]`, and a workaround the room did anyway rides on it as `did anyway: ... [shadow]`, so the builder sees what was improvised. Each need is a proposal of kind `need` on the day's `<memory>/rules-proposals/<day>.md`, `## N. need: ABILITY`, numbered past every number on the day's page and every number a need has held, so a new need never takes an earlier one's (until 2026-11-11 the count restarted each day; curate's own take the numbers the day's needs leave, and its 05:00 rewrite of the page keeps their blocks), recorded in `<state>/needs.json`, and said in one line in the machine room. A needs.json that is there but cannot be read is never read as empty (2026-11-23): a filing or a change is refused, naming the file, and writes nothing, and the pipeline does nothing and says so once. The same ability filed again from any room is folded into the open need, its count one higher, never a second builder. `yerk needs build DAY N` turns a need into a worker brief (every ask as filed, the repository and where to read, and what done looks like: the ability built once in Yerk with its tests, the suite green, README, CHANGELOG and its abilities.toml entry, committed on branch `need-DAY-N`, a report whose first line is the PR or the branch) and starts a builder on `[needs] account` (default: `[curate] account`, else the workers' own pick), its card in the machine room. A worker's gate refuses a push and a pull request, so the builder only commits; the branch reaches its PR from outside the run, and the owner's cold read merges, so one deploy gives every room the same tool. A day log is chunked by room id and class as well as by size (`memindex.lane`): a line of another room or class than the chunk's starts a new chunk, an attachment line stays with its line (after a line cut in pieces it is a chunk of its own, never the head of the next line's), a free-form line is the owner's alone and the day header goes with the first chunk, so a room that is not an owner room, which ranks and gets only the chunks it may read whole, finds every line of its own, where before a line of hers beside one of the owner's left her recall and reached her through her pack, her topic hits and read_memory only. The chunker's VERSION is 2, and a yerk-index whose index was built under another VERSION or scope chunks every file again on its first pass, writing only the chunks whose text changed (an unchanged chunk keeps its hash and with it its vector; the changed ones are embedded in the background), so no `--rebuild` is needed; `yerk-index --check` reads scope-changed until that pass lands. Mention recall runs in every room with `mention_recall` on: an owner room gets every name on file as before, and any other room gets the entries of the files it may read when it asks, class shared or class room with its own id (the daemon reads the file's front matter or `.class` sidecar then, as recall and read_memory do, so a sidecar edit counts from the next message; yerk-index records each entry's class and room too, and the front matter itself is no entry), never an owner-class file's, and a name only such a file holds takes no words from one of its own, under the same 1,500-character cap.

Moving in, keeping clean, and the probes out of the package: `yerk room add` (Moving a chat in, below) and `yerk retention` land together, paid for by the contract probes leaving the package for tests/contract/probes.py, where a person or a timer runs them as `python tests/contract/probes.py NAME` (the drill as `... drill`; units/yerk-imessage-probe.service calls it there), each still writing its raw event log to <state>/probes; `yerk probe` and `yerk drill` are gone, and the package's ceiling goes from 14,611 to 14,226 lines. The sweep covers a room's scratch: its work folder but the person's files in inbox/ and the dot entries Claude Code and its sandbox keep at its top, and the copies of the files it sent (outbox/, read only to send one again after a crash), are kept 2 days, and past 500 MB a room loses its oldest files first, never one written in the last hour and never while it has a turn in flight; what leaves waits a day in the trash (`scratch_trash`; everything else a week). A month of a busy room in tests/test_retention.py (page renders, a 900 MB burst, sends, transcripts, workers, ledger rows, the sweep each morning) stays under one bound fixed before it starts. A person room made by `yerk room add` copies the other person room's persona and rulebook without that room's own text: every line naming its folder goes, and so does the persona's `# About the owner` section, written again from the template with OWNER, PERSON and RELATION for the owner to fill in.

`yerk doctor` checks the install each day after the sweep (units/yerk-doctor.timer, 04:40): the private folder's layout, any rooms.toml key no loader reads (config.ROOM_KEYS), the jobs (a job whose room or account is not on file, a one-shot past its time still in the jobs file and not running, a job's runs of the last day that did not start, were cut or are undelivered, a watch's findings held more than a day; read only, a jobs file or ledger it cannot read said), an owner room that drifts from rooms.toml's `[defaults]` (below), memory classes and day-log lines, token expiry where the token file says when it was issued, the index, each running room's hooks and the folders' growth past `[doctor] growth_mb` (500 MB a day), quiet when all is well and a line per finding, the count and the first in the morning diff. It also reads the memory index: a memory cap under what `units/yerk-index.service`'s rule gives its vector count, a backfill paused after three failures in a row, two memory roots with one cite (a root whose folder name an earlier root has is cited with as much of its path as tells them apart), and yerk-index on other code than yerkd. It is also the crash repair, on yerkd's start before any room opens and daily: a hard power-off zeroes the line a file was writing, so every day log, assembled log and bound transcript with a NUL byte is backed up, then its line mended (the NULs out, the text kept when it still reads), else blank in a day log so every cited line number holds, dropped from a JSONL file, never in a room with a turn in flight or waiting.

`yerk curate` keeps the cards each night after the doctor (units/yerk-curate.timer, 05:00), in two parts: a sweep in code blanks a card line said twice, a superseded line and a line `until` a date now past, and moves a cite only when its quoted words sit on exactly one line of its file, every other drift one finding in the morning diff, each card backed up first. Then each card gets a pack of the day's lines that name it as the card's reader may read them, a worker that sees only the pack proposes lines, a second knocks them down by `yerk_ai/curate.md`, code checks shape, head, secrets and that each cite is a line of the pack, and the lines land with a backup only when the recall bench does not fall, a correction only ever proposed, never applied, and `--since DATE` the same code over a range for a backfill.

Then the rule files, by proposal only: the same nightly run (and `yerk curate --rules [--dry-run]` alone; the nightly run keeps the day's proposals as they are when a `yerk curate --rules` of that day already built them, so the numbers its card showed are the ones `--apply` takes) reads the rules file, each room's rulebook, `rules-topics.md` (and `rules-overflow.md` until yerkd moves it) whole and proposes topic rules (a rule of the rules file filed off a message that names its topic, on none of the shape check's every-reply topics, named by under a third of the week's messages, moved to `rules-topics.md` with the scope a filing would give it), gates (a rule a code check could hold on a reply, a banned phrase, a format or a figure, with the check it would need; curate never builds one and `--apply` refuses it), merges (one job, near-duplicate words, or one message on jobs that overlap, never one message alone, every clause and the fuller example kept), cuts (a superseded line a session start still sends, a cite to a day-log line that is gone, an older line a newer one on the same job says otherwise to, both quoted), condensations (a line past 600 characters: its prose first, a clause it says again or a hedge, then its quoted asides, and its examples last, only when its file is past its line even without the rest, since a rule's worked examples are its strongest words; never a reason, only its own words kept, and the WHY names what it kept) and promotions (a held rule that fits again, or a topic rule for every room that rode in most of the week's sessions and fits), each with the week's evidence: the shadow bounces, rated replies and `yerk` lines that touch it, with their cites. On a converted store (its `rules/` folder there) the index, `rules-topics.md` and `rules-overflow.md` are no rule files of the pass, each room's rulebook is read as before, and each live lesson is read once as its rule line, its examples out, for a gate alone, cited at its summary's line; `--apply` refuses any proposal that would write the index, those two files or a lesson, since a lesson changes only by filing it again or retiring it. They go numbered to `memory/rules-proposals/<day>.md` (0600, BEFORE, AFTER, WHY, EVIDENCE, each file's size now and with all of them in) and the ten that save the most to one card in the machine room, once a day, none when there are none. Nothing in a rule file changes until the owner says so: `yerk curate --apply DAY N[,N...]` writes those numbers, every file backed up first, refused whole when a line changed since or a file would pass its line in `budgets.toml`, a line blanked rather than cut so every cite keeps its number, and `yerk curate --apply DAY undo` puts the last apply back byte for byte. Without units/yerk-curate.timer, the rules pass alone runs nightly as a jobs.toml script job (`example-curate-rules` in examples/private/jobs.toml: 04:30, silent, `yerk curate --rules || [ $? -eq 1 ]`, since exit 1 is proposals to read), no account, since the pass is code; and the 06:30 morning diff lists the last day's proposals by kind with their numbers and the `--apply` line.
