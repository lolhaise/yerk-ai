# Guide

The long guide to Yerk AI: how to run it, use it and look after it, and how each part works. Read the front page (README.md) first, then go to the section you need; each one stands on its own. The sections run from everyday use (the commands, moving or importing a chat, running it as a service, backup, the private folder) to how it works inside (how a room runs, what you see, add-ons, voice notes, texting, web reach, how a room answers from Claude Code's own docs, and the ledger, its small database of what ran). The six pages beside this one (commands, tools, settings, budgets, hooks, units) are written from the code by `yerk docs own`; where one of them and this page disagree, that page is right, because it is the code's own word.

## Use

```
uv sync
uv run yerk map example-room                 # the example room's context, part by part, against budgets.toml
uv run yerkd                                 # every room with a discord:<channel id>, through the Discord adapter
uv run yerk map example-room --wire          # also the sizes as sent, read from the room's Claude Code transcript (a line that does not parse, as a crash leaves one, is skipped and counted)
uv run yerk setup-room ROOM                  # a Discord room's test webhook; its URL goes to secrets/ (0600), never printed
uv run yerk room close ROOM                  # the running yerkd closes ROOM's process now (never mid-turn); the session stays
uv run yerk room add NAME --from discord:ID  # a Discord chat moves in as the room NAME-on-yerk (Moving a chat in, below)
uv run yerk import discord-guild:ID --dry-run   # every chat on the server, counted; without --dry-run, imported (Importing a chat, below)
uv run yerk location day --dry-run           # the day's places from yerkd.toml [location], the one day-log line it would write
uv run yerk accounts                         # per account: order, token age and days left (warns inside 30), rests, last health call
uv run yerk accounts cool NAME MINUTES       # rest an account by hand; `clear NAME` lifts it; a running yerkd sees both at its next pick
uv run yerk accounts mint NAME               # `claude setup-token` for NAME: the browser flow shown, the token stored 0600, never shown
uv run yerk accounts token NAME              # or store a token from stdin (never echoed), 0600, issued today
uv run yerk accounts health                  # one tiny model turn per account and its login identity, a ledger row each
uv run yerk status                           # the card: each account's live meters, resets and bill day, the next resets in order, what runs, memory, stalls
uv run yerk morning                          # the morning diff to the role = "machine" room (units/yerk-morning.timer: 06:30)
uv run yerk deploy [REF] --private DIR       # REF onto the running yerkd: fast-forward only, fast tests, recall controls, a quiet room, proof, else rollback
uv run yerk deploy --unit                    # the same, moving a systemd-run yerkd onto units/yerkd.service (Install below)
uv run yerk retention --dry-run              # what the nightly sweep (units/yerk-retention.timer) would move to the trash, by kind
uv run yerk doctor --dry-run                 # the daily check (units/yerk-doctor.timer): a line per finding, nothing when all is well
uv run yerk curate --dry-run --since 2026-10-19   # the night's card curation (units/yerk-curate.timer): what it would sweep and propose
uv run python tests/contract/probes.py drill --config-dir DIR   # the Claude Code upgrade drill: the version, hello, fold and resume on one account, a verdict
uv run python tests/contract/probes.py hello|fold|resume|blocks|smoke|measure|check|idle --config-dir ~/.claude   # one contract probe
uv run pytest
```

- `--private DIR` or `YERK_PRIVATE` points at your private folder (default: the fake one in `examples/private/`).
- `yerk map ROOM --wire` reads every later message by part, Yerk AI's (clock, metadata, place, rules, recall, taste, a compaction's recall pack) against their budgets.toml keys, which is where its OVER comes from, the reply header, attachment lines and the message's own text as reported and never cut, and Claude Code's own blocks by name, then lists the week's five largest by the part that made them large.
- `YERK_STATE` sets the state folder (default `~/.local/state/yerk`): the room-to-session table, session locks, the ledgers, cooldowns, logs, which `yerk retention` (units/yerk-retention.timer, 04:20) keeps from growing forever: the days each kind keeps are `[retention]` in yerkd.toml, a room's scratch (its work folder but the person's files in inbox/ and any top folder holding a file named KEEP, and the copies of what it sent) keeps 2 days and 500 MB (`scratch`, `scratch_mb`), and what leaves waits a week in the state folder's trash, a room's scratch a day (`trash`, `scratch_trash`); a swept room finds what went where in its work/RETENTION.md, and the morning diff names the room and its folders.

## Moving a chat in

`yerk room add NAME --from discord:<channel or thread id> [--person ID] [--voice FILE] [--since YYYY-MM-DD] [--like ROOM] [--dry-run]` moves a Discord chat in as the room NAME-on-yerk, in six steps, each said as it is done. `--dry-run` reads and prints every step and writes and sends nothing: run it first.

1. Channel: a private channel NAME-on-yerk, made with the bot token yerkd.toml names, with the permission overwrites of the room it is made like (so the same people see it); with `--person` that person is let in as well. A channel of that name already there is kept.
2. Voice: `--voice FILE` is copied to the layer's rooms/NAME.md; without it, a one-line placeholder to write.
3. Block: `[rooms.NAME-on-yerk]` from a template in examples/rooms/. owner.toml copies an owner room of yours (`--like`, else the last owner room in rooms.toml that is not the machine room) with its channel and voice set. person.toml copies a person room (`--like`, else the last room with `people`), so its wall is reused: privacy family, `people` the id, Read, Grep and Glob only, no `read`, `also` or sandbox, and a layer of its own under the private folder (0700) holding copies of that room's persona and rulebook less its own text (every line naming its folder, and the persona's `# About the owner` section, the one about its person), the template's `about` section at the persona's end in its place, and pinned.md and open-loops.md to write. Before anything changes, the rooms.toml it would write is loaded (config.rooms) and the daemon's people guard runs on it, and a person room's files are read for any path into the private folder outside its own layer; a miss stops it with one line. Then rooms.toml is copied into backups/ with the time in the name, and the block is appended.
4. History: the old channel's or thread's messages (from `--since` on, else all) filed in the day log under the room's id and class: the owner's lines `owner`, the person's `person`, everyone else's `other`, each with its author's handle, as the daemon files a live line; attachments up to 25 MB saved into the layer's NAME-attachments/ (0700, files 0600). It goes by message id and file name, so a second run only tops up. Yerk's bot must be able to read the old channel. An owner room's block that has an `also` lists that folder in it (a block with none recalls every root and is left so), the yerkd.toml `[memory] also` line for it is printed to add by hand before the deploy (yerkd does not start on a room's `also` outside `[memory] also`), and the last two lines are `yerk pictures backfill NAME-on-yerk --root <folder>` and `yerk files backfill NAME-on-yerk --root <folder>` to run after it, the one folder in the private folder a backfill takes; `yerk doctor` names a room whose folder still holds pictures or documents with no sidecar.
5. Restart: none. It prints the one `yerk deploy` line to run, detached, at a quiet moment.
6. Check: the room's context against budgets.toml; the test webhook (yerk-test-sender) found or made in the new channel, its URL in secrets/discord-NAME-webhook.url (0600, never printed); the yerkd.toml `test_senders` line with its id added, printed to apply before the deploy and never written here; and the warm-up line to post through it.

A person room's persona and rulebook start as the other person room's less its own text: fill in OWNER, PERSON and RELATION in the persona's last section, read the rest for anything else of that room's, and write pinned.md, before the person talks there.

An OpenClaw box moves its notes in with `yerk import openclaw:<workspace dir> [--since YYYY-MM-DD] [--dry-run]`, one workspace a run: MEMORY.md, USER.md, memory/, wiki/ and media/gym copied as they are into <private>/openclaw/<its name>/<the same path> (files 0600), the box tools' state, the kinds the index does not read and every dot or secrets folder left, each line with a shape of yerk doctor's secret scan, or whose key names a secret (a token, a password, a pin, a session) whatever its value, written as its kind; by path and sha256, so a second run writes nothing and the same command tops up.
After a real run it prints the yerkd.toml and rooms.toml lines that read the copies (in each `also` a box path becomes its copy in its place, so every cite name stays; a `read` stays while the box runs; a denyRead keeping a shell off the box gains the copies), to make by hand before yerk-index and yerkd are restarted; it never writes them.

## Importing a chat

`yerk import discord:<channel or thread id> [--since YYYY-MM-DD] [--files] [--dry-run]` files a Discord chat's whole history into the day logs with no room made, through the one import `yerk room add` uses (step 4 above): by message id, so a second run only tops up and a message already in the day log is never filed twice. Its lines go under the room id `discord:<id>`, the chat's name as the label, class `private`: an owner room reads them, no person room does. `[import] classes` in yerkd.toml changes that per id: `"shared"` lets every room read them, and `"room:<a room's id>"` files them under that room's id and class, behind its wall, its people's lines as `person`; a person's old channel belongs with her room, `classes = {"<old channel id>" = "room:discord:<her room's channel id>"}`. A message is filed once, under the first room id it gets: a chat imported before its room is made stays under `discord:<id>`, and a later `yerk room add` files none of it under the room, so a chat that will become a person's room waits in `[import] skip` until `yerk room add` has moved it in. A chat a room covers (its `channel` or `watch` in rooms.toml) is filed as that room files it. Attachments are named in their line with their size and not downloaded; `--files` saves each one up to 25 MB into the private folder's attachments/discord-<id>/ (0700, files 0600). `--dry-run` reads and counts, writes nothing, and prints every line it would file.

`yerk import discord-guild:<guild id> --dry-run` is the server's inventory: every text, news, voice and stage channel and every thread under one (active and archived, public, and the private ones the bot may list), one line each: its parent, how many messages (counted by paging them all; for a chat the bot cannot read, Discord's own count where a thread has one, said as such, else unknown), the first and last day, whether a room covers it, and the class it would get. Without `--dry-run` it imports every chat on the list that no room covers and `[import] skip = ["<id>", ...]` leaves in, one after another, each said as it is done; a chat it cannot read is said, the rest go on, and the run ends 1. Discord hands one bot about a hundred messages a second, so a big server takes minutes. Yerk's bot must be able to read a chat (View Channel and Read Message History): one it cannot read is listed with the day it was made and the day of its last message, read from their ids, and its threads are not asked for.

`yerk import imessage:<chat.db> [--contacts <db>]` and `yerk import gmail` move a person's texts and mail in as files, not day-log lines: `imports/texts/<person or group>.md`, a file a person (named by their contact, else their number or address) and a file a group chat, a chat deleted on the phone placed by its messages' `ck_chat_id`; and `imports/mail/<YYYY-MM>.md`, Gmail's All Mail a file a month. One line a message: who, when in the install's zone, the text on one line, attachments and app messages as tags; a newsletter, a draft and a security mail marked; 400 characters of a mail's text, 1,200 of your own sent mail. Both only read: the databases are opened read-only (a copy of `~/Library/Messages/chat.db` with its `chat.db-wal` beside it, or the newest texts are missing, which the Terminal needs Full Disk Access to make; and of the Contacts `AddressBook-v22.abcddb` under `~/Library/Application Support/AddressBook/Sources/`), Gmail with EXAMINE and BODY.PEEK, by `[gmail] user` and `password_file` in yerkd.toml (a path in the private folder, or absolute, to a file holding an app password alone on its line or after `App password:`, never printed; Google makes one at myaccount.google.com/apppasswords once 2-Step Verification is on, and revokes it when the account's password changes); `[import] me` is the name your own texts are written under. A security mail, a security text from a short code (a bank's, a sign-in's) and anything shaped like a key, a token or a one-time code are written as their kind only, never the secret, so no file the index reads holds a live code or key. A setup that is not there (the database, the `[gmail]` keys or its file, a folder of files no import wrote) is refused with exit 2 before anything is read; a Gmail batch that fails is said and left for the next run, and the run ends 1. By id (a message's guid, a mail's UIDVALIDITY:UID, one a line in `imports/texts.ids` and `imports/mail.ids`), a second run adds only what is new, and a folder of files no import wrote is refused. The files carry no class, so they read as private: with `imports/texts` and `imports/mail` in `[memory] also`, an owner room reads them and no person room does. `--since` and `--dry-run` work as for a chat.

## Install as a service

`units/yerkd.service` runs yerkd under systemd with `Type=notify` (a start counts once READY=1 says the port listens), `WatchdogSec=30` (the beat stops when the event loop stops, and systemd restarts it), `MemoryHigh=2G` with `MemoryMax=4G` (raise MemoryHigh by 350M for each room kept open past five), `KillMode=mixed` with `TimeoutStopSec=30` (a stop sends yerkd SIGTERM alone: it says STOPPING=1, ends each room's Claude Code itself, closes the gateway clean and exits 0, in about a second; a turn cut mid-run has its messages run again once at the next start, marked), and `NoNewPrivileges` with `PrivateTmp` (no setuid gain for a room's shell, a /tmp of its own). `yerk status` names the version and the commit that runs; `yerk status --json` is the same as one document for a monitoring tool (rooms, accounts, the last turn per room, the day's failed turns and unanswered messages, the index, the newest backup's age). CHANGELOG.md names what each merge changed. Copy it to `~/.config/systemd/user/`, set `YERK_PRIVATE` and `YERK_STATE`, and `systemctl --user enable --now yerkd.service`. A yerkd started by hand with `systemd-run --user --unit=NAME` moves onto it with `yerk deploy --unit` (the unit is the one the running yerkd's pid is in; `[deploy] unit = "NAME"` in yerkd.toml names it instead): the unit's command (read word by word from systemd's bus), folder and environment go into the file under the same name, written 0600, and the file unit starts at the next quiet moment; a failed proof puts the transient unit back. After that `yerk deploy` restarts it in place. `[deploy] tree` names the daemon's checkout (default: the unit's working folder), `tests` the fast subset (default `tests/test_scrub.py`, `test_budget.py`, `test_card.py`, `test_style.py`), and `proof_seconds` how long the proof may take (60). The fast tests run with the deploy's private and state folders as `YERK_PRIVATE` and `YERK_STATE`, so the budget test builds every real room the way the daemon does, rules file included, and a room past a budget fails the deploy with the room and its part on the card. With no `--private` and no `YERK_PRIVATE` those folders are the ones on the running yerkd's own command line (`--private` and `--state` in its unit's ExecStart, and the card's second line says `private layer: the daemon's`), and with none there the deploy refuses in one line, `no private layer: pass --private`, so the fast tests never read the fake example layer. After the fast tests the deploy holds the layer's recall controls on the code under test (`yerk recall-bench --controls`, which writes nothing): each is searched on the exact half, one missed there once more with the meaning half, and one missed then deploys nothing, the card naming it (`recall: N of N hit`, and how many only through the meaning half, when they hold).

## Backup

`yerk backup` writes one dated archive, `yerk-YYYYmmdd-HHMMSS.tar`, 0600 in a 0700 folder: the private folder whole (secrets as bytes, with their modes), the ledger through SQLite's own backup (whole while yerkd writes), the rooms' session bindings and small state files, the index's metadata, and the `yerk*` units. Its last member, `MANIFEST.json`, lists every file with its bytes, sha256 and mode. The index's vector store goes in only with `--with-index` (`yerk-index` rebuilds it from the layer); logs and a room's scratch never do. `[backup]` in yerkd.toml: `path` (default `yerk-backups` beside the private folder), `keep` (the last 7 stay), `units` (default `~/.config/systemd/user`). `units/yerk-backup.timer` runs it at 04:10, before retention's 04:20; `yerk status` says the newest one's age and size, and `yerk doctor` says one older than 36 h. An archive on the layer's own disk survives a bad edit, not a dead disk: copy the folder off the box with a tool of your own.

`yerk restore ARCHIVE --to DIR` reads the whole archive against its manifest first and refuses one cut short or changed in a byte, before it writes anything; then it writes `DIR/private`, `DIR/state` and `DIR/units`, a line a step (`--dry-run` says them and writes nothing). DIR must be empty. Without `--to` it writes the layer's own folders: straight in when they are empty (a new disk), and over ones that hold files only with `--force`, after a backup of the layer. What it replaces, a unit file too, is moved to `<state>/trash/<day>/restore-<time>/` first, never deleted. It refuses while yerkd runs on the target unless `--force`. A room's Claude Code sessions live in each account's own folder, outside the archive: a restored `sessions.json` points each room back at its session, and one the account no longer holds starts fresh with the recap line, as a lost session does.

## The private folder

- `rooms.toml`: one entry per room: channel (`discord:<channel id>`), account order, model, tool allowlist, privacy class, time zone, and the context files. `layer` names the folder those files come from (default: the private folder itself). `people` lists the Discord user ids the room answers besides the owner (unset: the owner only; the owner is answered in every room).
- `[defaults]` in `rooms.toml`: the tool set every owner room carries, declared once, so the rooms keep one way of doing things without a hand edit per room. It holds `allow` and `mcp.<name>` server tables only (each room keeps its own `sandbox`); any other key stops the start with one line naming it. A room whose privacy is owner (or unset) carries each default it does not set itself: its own `allow`, or its own `mcp.<name>` table, replaces that one default whole, and `allow_remove = [...]` drops named tools from the allow it inherits. `{room}` in a server's `args` and `env` is filled with the room's name. A room whose privacy is anything else inherits nothing. `yerk doctor` names an owner room that drifts, one line each: red for a default tool its own allow misses and its `allow_remove` does not name, orange for its own copy of a default (an allow equal as a set, a server equal once `{room}` is filled), the way rooms come apart later. `yerk room add` copies the room it is made like as written, so a new owner room inherits under its own name.
- A room with `people` reads its own lines and the shared files only, so it takes no `read` folder and no shell tool, unless `shell = "trusted"`: then it lists the owner rooms' tools (Bash, Write, Edit and the rest), its shell runs inside the wall the daemon builds (below), and Write and Edit reach its layer and work folder only. Its `[rooms.NAME.sandbox]` table may add `filesystem.denyRead`, `filesystem.denyWrite` and the `network` allowlist; any other key, an `allow` rule for the file tools, or a wall that cannot be built stops the start with one line. `yerk explain trusted` says the same. What is sent to a person's room (its uploads, a recording's transcript, the pictures it files with `seen`) is recalled there as its own, read by that room and the owner's rooms only, and a reply there that says what a third person said from a turn that read nothing is turned back once, as in an owner room.
- `taste.jsonl` in an owner room's layer: the owner's thumbs on the room's replies, kept the way the old box keeps them. A message of the owner's in the room's own channel that praises or faults the last reply ("that was good", "too long") adds one row, one per reply per sign; a test sender, a person or the harness never rates. Every message in that room then carries the `taste` part after recall: three praised and two faulted replies, the owner's words beside what the room had said, the room's own newest first, then the other rooms' (`[per_message.on_hit] taste`).
- The file is the switch: a layer without `taste.jsonl` gets no row and no part, and a room with `people` gets neither. `yerk map` shows the part's size.
- `[location]` in `yerkd.toml`: where the owner is, from a phone's fixes. `file` holds one JSON fix a line (`ts_iso`, `lat`, `lon`, `speed_mps`, the shape the box's location watcher writes), `places` the watcher's table of named places (`{"places": [{"label", "lat", "lon", "radius_m"}]}`, a `todo` row never matching), `stale_after` how old the newest fix may be (default `3h`). Both files are only read, and nothing goes to the network: a fix is named by the nearest place whose radius holds it. Every message of the owner's in an owner room then carries the `place` part after the metadata line, `[place] near the office (Example City), 7 min ago, stationary` (moving: faster than 2 m/s, or 150 m from the fix before; `[per_message.parts] place`). There is none when the newest fix is past `stale_after` or at no named place (the road, a place not in the table, so no coordinate is ever said), in a room whose privacy is not owner, or on a person's message; no table, no part anywhere. The mechanics say when a room uses it unasked: at a gym, it logs the session there; at work, it minds the hours and the commute; moving, it keeps replies short. `yerk map` shows the part.
- `yerk location day [DATE]` writes the day's places into that day's log as one line, class private, so the owner's rooms recall it and no person's room reads it: each stay at a named place with its first and last fix (`08:40 to 12:00 the office (Example City); 12:45 to 17:05 the office (Example City); 17:40 to 23:40 home (Example Town)`), a stay ending at another place or at a gap of 30 minutes between its fixes; never a coordinate. A re-run replaces its own line where it stands (its id is the day's), so no other line moves and every cite into the file holds; `--dry-run` prints the line and writes nothing. It runs nightly as a script job in `jobs.toml`; a script job's environment keeps PATH and HOME but not `YERK_PRIVATE`, so the command names the folder:

  ```toml
  [jobs.location-day]
  kind = "script"
  schedule = "55 23 * * *"            # 23:55, the day nearly whole
  tz = "<your [memory] timezone>"
  room = "<an owner room>"
  cap = 2
  deliver = "silent"                  # the day log is the output; a failure still alerts the ops room
  command = "$HOME/yerk-ai/.venv/bin/yerk location day --private $HOME/<your private folder>"
  ```
- `accounts.toml`: one line per account: `name = { config_dir = "...", order = 1 }`, optionally `token = "secrets/..."` (the default is `secrets/claude-<name>.token`). Adding or removing an account is that one line; a room's own `accounts` list only orders the accounts it names, the rest follow.
- `yerkd.toml`: the daemon's settings: the Discord token file, the owner's user id, webhook ids accepted as senders in test mode, the local port. A running `yerkd` writes its pid and port to `yerkd.json` in the state folder.
- `[watch] assistants` in `yerkd.toml` lists other assistants' Discord user ids: in a channel a room watches, their messages go in that room's day log under their own label once they stop changing (a progress card never), never answered and never read as anyone's instruction, so the room can read what was already said there. A message the owner sends there waits for that answer (the first of theirs after it to go 6 s with no edit and no delete; a progress card, a message with an OpenClaw tool row or Yerk AI's own card shape, never is, however long it sits still), up to the room's `watch_wait` in rooms.toml (default 150 s), counted again from the card's last edit while that card is up, three times `watch_wait` at most and at most 30 s more once the card is deleted with no reply, then comes in as one turn with the answer under it, or with a line that it had not come; the room's own channel never waits on it. Their files, in that channel or in the room's own, are saved in the room's `work/inbox/<message id>/` as a person's are (an owner room's PDFs and workbooks with their text beside them), once a message: an answer a held message waits for has them saved before that turn, its line naming where each was saved or that it could not be fetched, and any other message as it is filed. None is a file the room must open before it answers, and one that will not come is never a notice in the room, since no one there sent it.
- `secrets/`: files only you can read (mode 0600), for example the bot token. Nothing in the repository reads them except the daemon at start, and every room's settings deny its Read tool and its shell the folder. A worker's unit sees the state folder read-only and its own folder writable; the install's secret, this folder and every room's folder are not there at all, but for the worker's own account token, bound back read-only for its first step, so a worker spends no money outside the daemon's tools, their gates and the ledger.
- The Discord bot: invite it with the `bot` and `applications.commands` scopes and permissions `274878008384` (View Channels, Send Messages, Send Messages in Threads, Read Message History, Add Reactions, Attach Files), and turn on its Message Content intent; it asks for no other intent (Guilds and Guild Messages, no members, presences or direct messages). `yerk room add` and `yerk setup-room` also need Manage Channels and Manage Webhooks (`275414879312` with them), and an import of a server's private archived threads Manage Threads. Administrator adds every channel and every server setting, which Yerk itself never uses: give it only when a plug-in of yours acts as the bot on the server (moderation, admin writes), knowing that a room steered through that plug-in reaches all of it.

## How a room runs

One `claude -p` process per active room, stream-json in and out, with:

- `--session-id` on a session Yerk AI minted, or `--resume` on the room's own session; one live process per session, by lock file
- `--setting-sources ""` and `--settings`, so only the settings Yerk AI writes apply: a Read rule for the room's folder, Read deny rules on every secret, the hooks (each a command hook whose `curl` posts the event to the daemon with the room's token read from a 0600 file beside the settings), and `autoCompactWindow` from `budgets.toml` `[session] compact_window` (a room's own `compact_window` in `rooms.toml` overrides it; 0 leaves it to the model), so a room compacts where Yerk AI says, never at the model's window edge: a room that rides the whole window re-reads all of it on every message and pays it in full after an idle hour, when the prompt cache is gone. A compaction loses nothing searchable: every line is in the day log, and the recall pack comes back after it
- Claude Code's sandbox, `enabled` with `autoAllowBashIfSandboxed`, for a room whose `tools` run a shell (Bash, Monitor, PowerShell or `default`) and that rooms.toml gives no `[rooms.NAME.sandbox]` table: without it a Read deny stops `cat` and the Read tool but not a script, `grep` or a redirect; a room's own table, `enabled = false` included, is passed as written (on Linux the sandbox needs bubblewrap and socat)
- for a room with `shell = "trusted"`, the daemon's own sandbox instead, rebuilt at each process start: no command retried outside it, no start without it, and denied to the shell for reading and writing every entry of the private and state folders but the room's own (the other layers, the memory folder, rooms.toml, imports; every other room's folder, the ledger), every memory root and every other room's layer and `read` folders, `projects/` under each account's folder, and each folder of the home that holds one of those; its outbox is read only and the Python user site-packages are re-opened (proven on Claude Code 2.1.304 by a scratch probe: its layer, work folder and python-docx open, every walled path, the rest of the home and the network closed)

A topic rule's words (its triggers) are its job's words and what its own words name, a #channel, a file, code in backticks or a capitalised word mid-sentence, each weighted by how few rules say it with the rarity weight recall's keyword search gives a word; a rule filed with `remember`'s `triggers` (the owner's words, "money" or "how do I make money") loads on its job's words and those instead, kept in an `[on: ...]` mark before its trailer, each picked one weighing as a word only one rule says, a phrase held when a message says each of its words that names something (a, the and how name nothing; a trigger with no other word is refused, nothing filed), and a filing of its job that names none keeps them; a message whose words (its attachments' names among them) weigh three quarters of a word only one rule says gets the rule in its per-message `rules` part, after the "Rules changed since you last looked" block and under the same 1,500 characters, best match first, each rule once per session and again after a compaction. Before this, such a rule waited in `rules-overflow.md` in no room; yerkd's first start with the change moves that file's rules into `rules-topics.md` once, the old file kept beside it as `rules-overflow.md.moved`; a `[rooms: NAME,...]` mark typed on a line there before that start is the scope that rule gets, whatever its words. `yerk map ROOM` gives the topic rules' size and which rode on the room's last 20 messages, and `yerk doctor` names a topic rule that can never load (longer than the per-message part, or kept to no room on file)

The room runner:

- A message for an idle room starts a turn. A message that arrives mid-turn goes straight to the process's stdin and is answered inside the same turn; the replayed copy (`--replay-user-messages`) is the proof it was accepted. When that turn fails, a message that folded into it after it started is not failed with it: it runs next as its own turn, and its card says so. A result of Claude Code's own turn for a background command's notice (`origin` kind `task-notification`, what a resume streams first for the commands a crash left running) never ends or answers a turn.
- Only the final text after the last tool call is delivered. A turn owns one progress message, edited with its first visible line, then replaced by the reply, split under the channel's limit and never inside a code block. Every `remember` result ends with `next`, the shape of the answer that follows the call (first and whole, the filing one clause at its end), and a final text that only reports a filing (`remember`, `schedule`, `hold` or `settings` called last, the answer above the call or never written) bounces once, a `stub` row in the shadow ledger the morning diff counts. A final text whose first paragraph is a note to the room itself before the answer (at most 700 characters, holding a rulebook tag, `Landed:` or `Bounced:`, or with more after it, a directive such as "Confirm" or "Keep" beside a shape word such as "in a line", "style" or "nuance", and no you or your) bounces once for the answer alone, a `note` row. In a room with people, a final shaped as the owner rooms' status board (a line opening on ☑, ☐, ⛔, 🟦 or 🟨, the colour key, "unblocks:") bounces once for two or three plain sentences, a `board` row. A fenced block a room posted on an earlier day of the last 14, equal once each line is stripped, blank lines dropped, runs of spaces made one and the fence's tag left out, is turned back once per result, in `send` before it posts and in the final text at Stop, naming the day and time it first went out and asking for a line-by-line re-read against today, a `paste` row; the room's next send goes out. In an owner's room, a document (.docx, .pdf, .xlsx, .pptx, .txt, .md, .csv) or a pasted block going out through `send` or in the final text with no claims sheet written that turn (a file whose name holds claims, beside the document or in the work folder: one row per claim, its source line, the quote) is turned back once per result the same way, saying what the sheet is and where it goes, a `sheet` row; a room with people only ledgers it.
- Files go out on one path, up to what the bot can send (measured: 20,971,520 bytes, Discord's own answer, above discord.py's 10,485,760 for a tier 1 guild). A file a crash left unconfirmed is sent again from its outbox snapshot, labelled, unless the room already shows it; the message runs again told which files are in the room.
- An edit of a message still waiting revises it before it runs; an edit of one already running or answered comes in again, marked; a message deleted while it waits never runs. A reply carries the message it answers.
- A failed turn takes the action `failures.toml` gives its class: transient reruns the same session (twice at most), overflow compacts then reruns, auth and quota rest that account (doubling per account and kind, kept across restarts; a rate limit instead rests the account for the model it hit until the reset the stream names, else the account's weekly reset from its last reading, an hour at the least) and continue the same turn under the same card on the next account, resuming the same session; when every account is out of the model a room was put on, the turn runs on rooms.toml's model under the same card, which says so, and the next message tries the pinned model again; a session that cannot be resumed starts fresh with a one-line recap; anything else is a visible notice. An empty reply resumes the same session once more on a new process, then starts fresh with the recap line, which says the day log holds what was said; the card names which happened.
- A turn Claude Code answered on a fallback model after a block stands, and its card and ledger row say so; the room's next turn starts a fresh session on the room's own model.
- After 30 idle minutes the process closes; the next message resumes the session.
- A room compacts between turns, never inside one. Idle 25 minutes (budgets.toml `[session] idle_compact_after`) with its session at 0.7 of its compaction window or more (`idle_compact_at`), it is compacted then, in the background, the way `yerk room compact` does it (the recall pack comes back after it), so the next message finds it small instead of waiting minutes in its own turn for Claude Code's compaction. The session's size is the last call's usage as the stream says it, kept in each turn's ledger row, so a restart keeps it. One try per growth: after a compaction, kept or failed, the next waits for a turn to grow the session again, and a failed one is logged once. A message that comes in during a compaction (this one or `yerk room compact`) waits and runs right after it, and the log says how long it waited. A room's own keys in rooms.toml move the line; `idle_compact_at = 0` turns it off, and so does a window left to the model (`compact_window = 0`), whose size Yerk AI cannot know.
- A hop resumes the same session on the next account by the transcript's absolute path (`--resume` takes one, as the docs promise), learnt from the first hook call of the session and kept in the room's binding; the id alone is searched only in the resuming account's own `projects` folder. Pointing every account's `projects` folder at one (a symbolic link) is an optimisation that lets the id be found anywhere, not a requirement.
- Every call to the daemon (`/hook`, `/mcp`, `/control`) carries the `x-yerk-secret` header: a room process sends the token minted for it at start and bound with its session (the daemon knows the room by that binding, never by a header a caller picks), the CLI and the job units send the install's secret from `secrets/yerk-http.secret` under the state folder (never inside a room's layer, so no room's read rule reaches it; `yerkd.json` names the path), and a worker's own server sends `secrets/yerk-worker.secret` beside it, which opens `recall` and `read_memory` only. A hook call no binding explains is answered `{"yerk": "unbound"}` and logged, never with a silent `{}`.
- The day log's line is `- HH:MM:SS+hh:mm room#id role@who: body [c:class] [m:id]`: the offset is each line's own from the configured IANA zone, the room's stable id (`id` in rooms.toml, else its channel) rides beside its name, the author is a role and a handle, and the class (private, room or shared) says who may read the line back. `recall` and `read_memory` return to a room only shared files and its own lines; the owner's rooms read everything. Lines written before this shape were rewritten once, the originals copied to `backups/` (the rewrite left in shrink-1, its job done on the one install), and the reader still parses the old line.

The daemon's one local HTTP server carries `/mcp` (the tools `send`: text, or a file from the sending room's own folders, to a room; `hold`: end the turn while waiting on a named event or worker; `recall`: ranked chunks of the memory tree with path, line and a `file:line` to cite; `read_memory`: exact lines of a file inside the memory tree, nothing outside it), `/hook` (the clock and metadata lines and the recall part, keyed on the session id through the room-to-session table; the recall pack after a compaction; the Stop checks) and `/control` (`yerk room close`, `yerk room compact`).

## What you see

Each morning the diff also shows yesterday's calls, every pick, plan or "you should" a room made for you (read by code, no model): the room and its words, and under them the call's number and the cites its turn read, or "no reads behind it", the first 20 and then the count.
A call that stood on a wrong line is fixed at that line with `yerk calls fix <number> <path:line> <what is true>`, filed the way `remember` files a correction and never into a persona or a rule, and the next morning's diff shows the fix.

## Add-ons

The core is what every install runs. An add-on is an ability in a repo of its own, installed only where it is wanted. Its root holds `addon.toml`, an abilities.toml entry with `repo` (its git URL), `version`, `size` (its own ceiling, in lines of its code) and `install` (its package and module, its MCP server and allow lines, its yerkd.toml tables, the rooms.toml keys it reads, its units, its budget lines, its words file and its tests, and the attachment types it reads, each to one of its own tools, as `reads = { "video/*" = "mcp__NAME__frames" }`).

```
yerk add examples/addons/hello --private ~/yerk-private --dry-run   # each step it would take, nothing written
yerk add examples/addons/hello --private ~/yerk-private             # a folder, a git URL, or an ability whose entry names its repo
yerk remove hello --private ~/yerk-private                          # each step undone, the private folder as it was
```

`yerk add` fetches it into the state folder's `addons/NAME`, refuses it when its code is over its own `size`, its name is not one plain word (letters, digits, `-` and `_`), a words file, test or unit it names is outside its folder (absolute, through `..` or through a link) or a budget value is not a whole number, installs its package into this venv, writes its server as `[defaults.mcp.NAME]` and its tools into `[defaults] allow` in rooms.toml and its tables into yerkd.toml (marked blocks the loaders read back first), links its units into `~/.config/systemd/user`, and runs its own fast tests; a failing test, or any step that fails, undoes every step. The rooms get it at yerkd's next start. While it is installed its budget lines count in the gate, its rooms.toml keys are known to `yerk doctor`, an attachment of a type it reads gets a line naming its tool under the room's `[attachment]` line, `yerk deploy` runs its fast tests after the core's, `yerk abilities` says installed (or what is missing) and `yerk status` names it. examples/addons/hello is the example: one MCP tool, one unit, one budget line, one words file and one test.

## Voice notes

A voice note or recording sent to a room arrives with one line under its `[attachment]` line: the room takes in the sound only through the `transcribe` tool on Yerk's own server (the daemon has the network, a room's shell has none), which returns the words with a timestamp per segment and saves them beside the audio as `NAME.transcript.txt`, and a turn that ends without calling it bounces once.
Pass 1 is OpenAI whisper-1 on the install's OpenAI key (`secrets/openai.key`, ffmpeg on the machine); with `secrets/groq.key`, pass 2 runs Groq whisper-large-v3-turbo on the same chunks and marks uncertain, with both readings, a segment the two disagree on; every paid call is a spend row, the morning diff says the day's total, and a recording past US$1 waits for the owner's yes (`yerk explain transcribe`).
With `secrets/meta.key`, Meta's Muse Voice Transcribe in DIARIZATION mode says who talks when: 540-second windows starting every 450 s (one request takes 10 minutes at most), its letters matched across windows by the speaking time they share in each 90-second overlap, and each line takes the letter covering most of it (`[00:14:00 -> 00:14:03] B: then email the vendor`); the words and their times stay whisper-1's. The line under the file's head gives each letter's speaking time and tells the room the letters are not names, so it says who is who as a guess unless the owner says, and how many letters could not be matched across windows when any could not. One voice writes no letters, so a voice note reads as before; without the key, or when a window fails, the words come back unlabelled under `speakers: none (Muse: why)`. Muse is US$0.18 an hour of audio sent, about 1.2 times the recording since the windows overlap, inside the same US$1 gate.

A room answers with a voice note when the owner asks for one or to say it out loud (the mechanics line), through the `voice_note` tool on the same server: the box's recipe, MiniMax speech-2.8-hd first (`secrets/minimax.key`) and Fish Audio s2.1-pro-free on any MiniMax failure (`secrets/fish.key`), the whole note on one voice; `[[pause]]` alone on a line between sections, `(break)` for a short pause, and an optional `voice/pronounce.txt` in the private folder for MiniMax's pronunciation rules, one `word/say-it` a line.
The joined sections go to -14 LUFS and opus 48 kHz in ogg under the room's `work/voice/`, and the first 20 seconds are read back by whisper-1 and must match the script's opening, or the note is deleted; `send` posts it with no text as a Discord voice message (flag 8192, its duration and waveform), or as the plain file when Discord refuses that form, and says so; every paid call is a spend row and a note past US$1 waits for the owner's yes (`yerk explain voice_note`).

## Texts in your name

An owner's room the owner asks to text someone sends it with the `text` tool on Yerk's own server: one text, an iMessage or else an SMS, from the owner's Mac to the person's phone number or email address, never a name, which the room recalls from the owner's texts or asks for. Plain ssh holds no grant to drive Messages, so the Mac runs a small bridge app that holds them and serves imsg's JSON-RPC on a socket; the daemon reaches it by ssh to `[imessage] host` and socat to its `socket` (or `command`, whole), asks its `status` and then sends once, on a connection of its own. The call is held first: the room is shown the text as it will read and who it goes to exactly as it is sent, and only the owner's approval word sends that exact call, once; an edit is a new call and a new preview. The tool sends nothing the gate did not release, so with the `text-out` rule turned off in `[gates] off`, or a hook that failed open, no text goes. A person's room, an install with no Mac set up, a name in place of a number and an empty text are refused before the owner is asked. A text the Mac's bridge never answered is not sent; one it took and did not confirm may have gone out, and the room says so and never sends it again unasked. Each outcome is a `text` row in the ledger's gates table, after the hold, the word and the release.

## Deletes you order

A room's shell deletes only inside its work folder (a plain `rm` there goes to the trash; one outside is refused, and Claude Code's sandbox keeps the rest of the disk read-only to it). An owner's room the owner orders to delete something outside it, old crash dumps, a full trash or old backups to free the disk, calls the `delete` tool on Yerk's own server with the whole paths, and the refusal of its own `rm` names that tool. The call is held first: the room is shown every path whole and what it is (a file and its size on disk, a folder, a link), and only the owner's approval word releases that exact call, once; the daemon then deletes each path for good, not to the trash, since the trash frees nothing, a file or a link unlinked (never what a link points to) and a folder removed whole without following a link inside it, and the result says what went, what would not and why, and the space freed. The tool deletes nothing the gate did not release, so with the `delete-outside` rule turned off in `[gates] off`, or a hook that failed open, nothing goes. A person's room, a path that is not whole, not there or not its own real path (a link or a `..` on its way, so the path shown is the path deleted), the root, a top folder, the home folder, a mounted disk or a folder holding one, and Yerk AI's own folders (its code, its state and private folders, the memory, an account's folder) or one holding them are refused before the owner is asked; Yerk's own state is kept by `yerk retention`. Each outcome is a `delete` row in the ledger's gates table, after the hold, the word and the release.

## Web reach

Rooms read pages and search the web through one plug-in, `plugins/web` (`yerk-web`, an MCP server in JavaScript with its own package.json and tests), outside the harness: it is not in budgets.toml's [code] count, and the harness's only part in it is the ledger's `spend` table and the morning diff's spend line. A room attaches it with an `mcp` table and allows its five tools, and `[defaults]` in rooms.toml does both for every owner room at once (rooms.toml.example's `[defaults]` has both, commented):

- `web_fetch(url, max_chars?)`: the fetch ladder. Free rungs on the machine first, each only when installed and skipped without a try when not: F1 a plain fetch with browser headers, F2 the machine's own stealth browser (CloakBrowser, or Chromium with playwright-core), F3 trawl's captcha-solving browser. Then Browserbase, paid, with its key: L1 Fetch, L2 Fetch with proxies, L3n a browser session without proxies, L3 one with proxies, captcha solving and a saved login per site. Every read passes the same blocked-page check; a page that stays shut comes back named by its wall (login_required, captcha_unsolved, geo_blocked, http_404 and the rest) with every rung tried. F2 stops waiting once the page's text is readable, settled and has no request in flight (6 s at most, 10 s while a short page is still loading), and waits out only a challenge that clears on its own. A page whose text sits behind a modal dialog that hides the rest reads as the page, not the dialog. When two free rungs meet the same captcha or challenge, L1 and L2 are skipped (a fetch cannot solve one) and the whole call is capped at 45 s. Per site, and per path class within it (the host and the path's first route word, so a site's listing pages and its search pages keep their own), it remembers which step read it and starts there next time (one step cheaper once a day, since sites change), a host that refused the free rungs rests from them a day, and the free rungs keep to 30 reads a minute and 6 a host in one window every room's process shares. A Microsoft Bookings page (Bookings with me, on Outlook's hosts or `bookings.cloud.microsoft`) is read as a guest: a link without the `anonymous` flag Microsoft's share links carry gets it, first in the query, so no rung lands on Microsoft's sign-in; the page then shows "Sign in or continue as guest", and F2 clicks Continue as guest and reads the meeting types and open times that click brings (a plain read gets only the page's app shell), and the answer says so. A read still on that screen is no answer at any rung, and once F2 has clicked or met it the climb stops before Browserbase, whose rungs make no click; a guest view that goes on to a sign-in is named so, with the next move, never as a login to save.
- `web_search(query, count?)`: Exa first, then Parallel's paid Search API, each with its key, then You.com's and Parallel's keyless engines; the answer names the engine. When the query asks for a video and a `yt-transcript` command is on the machine, transcript excerpts join that result.
- `web_research(query, effort?, schema?, system?)` and `web_research_result(run_id)`: the Exa Agent, one cited research job a call, at four fixed efforts (1.2, 2.5, 10 or 50 US cents), the dearer xhigh behind the owner's yes in words and the metered modes refused, under one daily cap of two US dollars for every room, booked before the request goes out.
- `web_image(url, max_bytes?)`: one picture in a post or a page, a jpeg, png, gif or webp of 15 MB at most, read by F1 as a browser asks for a picture and by L1 and L2 only when a site refuses that (never a browser rung), saved in the room's work folder as `web/<the URL's sha1, 12 hex>.<ext>` for the room's own Read, with its path, bytes, type, width, height and rung, the same URL within a day answered from that copy and a private host refused as web_fetch refuses it.

Keys are files in the private folder's `secrets/`, one each, 0600, read on every call and never printed: `exa.key` (search and research), `parallel.key` (search), `browserbase.key` and `browserbase-project.id` (the paid rungs). With none, pages are read from the machine and search runs on the keyless engines; research needs its key. Settings live in an optional `web.json` in the private folder, `{"fetch": {...}, "search": {...}, "research": {"dailyUsd": 2}}`, with the names the code's DEFAULTS use (`plugins/web/lib/fetch/util.js`, `plugins/web/lib/search/util.js`); a key is never read from it. State is `<state>/web/`: the site memory, the Browserbase contexts that keep saved logins, the meters, the call logs (hostnames and query hashes only) and the research runs. Every paid call is one row in the ledger's `spend` table (room, tool, engine, US dollars as billed or at list price), and the morning diff says `spent yesterday: US$0.11 on 2 calls`. Install: Node 22.13 or newer, then `npm ci --omit=dev` in `plugins/web`. Tests: `npm test` there runs the offline cases, and the stealth browser's own cases against a local page server when the machine has its engine; `YERK_WEB_LIVE=1 YERK_PRIVATE=<private folder> npm test` adds a live page read and, with a search key, one live search.

## Yerk knows its harness

A room asked how Claude Code works, or whether its own rules are written the way the docs say, answers from a read. `yerk docs refresh` fetches the Claude docs Yerk runs on into `<state>/docs/claude/<slug>.md`, each headed by its source, fetch time and content hash: the prompting guide, the prompting page of each model in models.toml, and the Claude Code pages on settings, hooks, memory, sandboxing, MCP, the command line and the system prompt flags (the sites answer `Accept: text/markdown` with Markdown). The folder is a memory root of class shared in every install, a room with its own `also` included, so a room's own recall finds the docs in every room and cites them as `docs/claude/<slug>.md:line`, every one below the owner's own notes, which say how this install's things are where the docs say how Claude works anywhere; `yerk docs list` and `yerk docs show NAME` read what is kept. What a room is handed per message (the lines on a name or topic it asks about, the past-tense search) never holds the docs, so a question about the owner's day is not answered from a prompting page by accident. `yerk doctor` fetches them once a week (`[docs] fetch = false` turns that off; `yerk docs refresh` still fetches when run), and a page whose hash moved is a line in the next morning diff (`docs changed: <slug>`), since a changed guide means the rules may be stale against it.

An owner room reads Yerk's own code too: the daemon writes a Read rule for the checkout that runs (the folder the package runs from) into each owner room's settings at its process start, and the mechanics name its path, so a worker's claim about Yerk, or a question on how Yerk does a thing, is checked with the room's Read, Grep or Glob before it is said, never relayed on a report's word. A checkout that holds the private or the state folder (a clone on its example layer) is opened around them, each of its other entries by a rule of its own, and the read denies on every secret still beat the rule. It is a rule, never an --add-dir, since Claude Code's sandbox opens an added folder to the room's shell for writing, and no room writes the harness. A room whose privacy is not owner reads its own folders only (`yerk explain harness-code`).

The doctor also scores every rule file a room loads (the mechanics, its persona, rulebook and voice, the rules file) against the guide: a negative with no why in its line, a shouted word, an example outside `<example>` tags, an alarm mark on an instruction, and one topic said in two files a room loads. A count past budgets.toml `[shape]` is a finding, a rule filed with `remember` and `job` in the last day that misses the shape is named by its cite (the room is never refused the rule), each room's report is `docs/shape/<room>.md` (class room, so a room reads its own), and the morning diff carries the totals. `yerk docs shape` prints the reports without a doctor run and `yerk docs shape --rules` each count's exact rule. The mechanics say how a rule is written (what to do, then its why, one line; a ban only where the thing itself is the point; an example inside `<example>` tags, marked landed or bounced) and that a question about the harness or the room's own rules is answered from `docs/`, never from memory; the mechanics and the example layer are in that shape.

**Upgrading:** yerkd.toml gains an optional `[docs]` table: `pages` (slug = URL, replacing the default list whole), `refresh_days` (7), `fetch` (true; false and the doctor never fetches), `topics` (name = regex, added to the shipped topic map) and `acronyms` (words of four or more capitals that are names, not shouting). budgets.toml gains `[shape]` (every threshold 0). The memory index takes `<state>/docs` as a new root at its next start, so every file is chunked again once; run `yerk docs refresh` once to fetch the pages before the first weekly run.

## Ledgers

One SQLite file, `ledger.sqlite`: `turns` (account, models, time to first visible event and to the end, how it ended, which messages it answered), `inbound` (every channel message by its id, written before anything runs; a crash runs it again once, marked), `outbound` (every message posted, with the id the channel returned, and a card's text at each post and edit, so a card the reply replaced can still be read back), `holds`, `health` (the daily call per account: pass or fail, login method, an identity fingerprint, never the email), `spend` (one row per paid call a plug-in makes: room, tool, engine, US dollars; the morning diff's spend line). A turn row also names the failure's source in the table and the hop that brought the turn to its account.

## Files

- `budgets.toml`: every size limit, in characters as Claude Code counts them
- `failures.toml`: failure classes and what each one does next
- `units/`: the daily health call's systemd user timer, the memory index service and the weekly recall bench timer (copy and enable them yourself)
- `abilities.toml`: every ability, what it needs and its cost tier (free, key or paid), with the free path
- `rooms.toml.example`, `accounts.toml.example`: templates for your private folder
- `yerk_ai/lifted/`: code taken from other MIT projects and from the author's own tools, each file with its origin; see `NOTICE`
- `yerk_ai/channels/`: channel adapters (Discord)
- `plugins/web/`: the web plug-in ("Web reach" above), outside the [code] count
