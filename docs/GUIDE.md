# Guide

The long guide to Yerk AI: how to run it, use it and look after it, and how each part works. Read the front page (README.md) first, then go to the section you need; each one stands on its own. The sections run from everyday use (the commands, moving or importing a chat, running it as a service, backup, the private folder) to how it works inside (how a room runs, what you see, add-ons, voice notes, texting, web reach, how a room answers from Claude Code's own docs, and the ledger, its small database of what ran). The six pages beside this one (commands, tools, settings, budgets, hooks, units) are written from the code by `yerk docs own`; where one of them and this page disagree, that page is right, because it is the code's own word.

## Use

```
uv sync
uv run yerk map example-room                 # the example room's context, part by part, against budgets.toml
uv run yerkd                                 # every room with a discord:<channel id>, through the Discord adapter
uv run yerk map example-room --wire          # also the sizes as sent, read from the room's Claude Code transcript (a line that does not parse, as a crash leaves one, is skipped and counted)
uv run yerk setup-room ROOM                  # a Discord room's test webhook; its URL goes to secrets/ (0600), never printed
uv run yerk room close ROOM                  # the running yerkd closes ROOM's process now (never mid-turn); the session stays
uv run yerk room add NAME --from discord:ID  # a Discord chat moves in as the room NAME-on-yerk (Moving a chat in, below)
uv run yerk import discord-guild:ID --dry-run   # every chat on the server, counted; without --dry-run, imported (Importing a chat, below)
uv run yerk location day --dry-run           # the day's places from yerkd.toml [location], the one day-log line it would write
uv run yerk accounts                         # per account: order, token age and days left (warns inside 30), rests, last health call
uv run yerk accounts cool NAME MINUTES       # rest an account by hand; `clear NAME` lifts it; a running yerkd sees both at its next pick
uv run yerk accounts mint NAME               # `claude setup-token` for NAME: the browser flow shown, the token stored 0600, never shown
uv run yerk accounts token NAME              # or store a token from stdin (never echoed), 0600, issued today
uv run yerk accounts health                  # one tiny model turn per account and its login identity, a ledger row each
uv run yerk status                           # the card: each account's live meters, resets and bill day, the next resets in order, what runs, memory, stalls
uv run yerk morning                          # the morning diff to the role = "machine" room (units/yerk-morning.timer: 06:30)
uv run yerk deploy [REF] --private DIR       # REF onto the running yerkd: fast-forward only, fast tests, recall controls, a quiet room, proof, else rollback
uv run yerk deploy --unit                    # the same, moving a systemd-run yerkd onto units/yerkd.service (Install below)
uv run yerk retention --dry-run              # what the nightly sweep (units/yerk-retention.timer) would move to the trash, by kind
uv run yerk doctor --dry-run                 # the daily check (units/yerk-doctor.timer): a line per finding, one green line when all is well
uv run yerk curate --dry-run --since 2026-10-19   # the night's card curation (units/yerk-curate.timer): what it would sweep and propose
uv run python tests/contract/probes.py drill --config-dir DIR   # the Claude Code upgrade drill: the version, hello, fold and resume on one account, a verdict
uv run python tests/contract/probes.py hello|fold|resume|blocks|smoke|measure|short|think|check|idle --config-dir ~/.claude   # one contract probe
uv run pytest
uv run python tests/verify_daemon.py         # the real daemon, offline, driven from outside: one line a check (Checking a change, below)
```

- `--private DIR` or `YERK_PRIVATE` points at your private folder (default: the fake one in `examples/private/`).
- `yerk map ROOM --wire` reads every later message by part, Yerk AI's (clock, metadata, place, rules, recall, taste, a compaction's recall pack) against their budgets.toml keys, which is where its OVER comes from, the reply header, attachment lines and the message's own text as reported and never cut, and Claude Code's own blocks by name, then lists the week's five largest by the part that made them large.
- `YERK_STATE` sets the state folder (default `~/.local/state/yerk`): the room-to-session table, session locks, the ledgers, cooldowns, logs, which `yerk retention` (units/yerk-retention.timer, 04:20) keeps from growing forever: the days each kind keeps are `[retention]` in yerkd.toml, a room's scratch (its work folder but the person's files in inbox/ and any top folder holding a file named KEEP, and the copies of what it sent) keeps 2 days and 500 MB (`scratch`, `scratch_mb`), and what leaves waits a week in the state folder's trash, a room's scratch a day (`trash`, `scratch_trash`); a swept room finds what went where in its work/RETENTION.md, and the morning diff names the room and its folders.
- Checking a change: the unit tests swap the daemon's long-lived tasks for ones that return at once, so a tree where one of them never runs passes them (the meters' keeper taken out of `run_discord` passed every test of the five files that cover it). `uv run python tests/verify_daemon.py` runs yerkd's own `main()` instead, offline, on a scratch copy of the example layer with only the outside world replaced (Claude Code, Discord, systemd, the Mac, the network), drives it from outside as a person or a program does, and prints one line a check, state first, in about 10 seconds: every task `run_discord` starts is seen doing its first piece of work, and one it starts that the run has no check for fails it. `--drive FILE` adds the one feature you changed and `--keep` leaves the scratch folder to read; `.claude/skills/verify/SKILL.md` is the recipe Claude Code's `/verify` follows in this repo, and says what a report pastes as evidence. `tests/test_verify_daemon.py` runs it once in the suite.

## Moving a chat in

`yerk room add NAME --from discord:<channel or thread id> [--person ID] [--voice FILE] [--since YYYY-MM-DD] [--like ROOM] [--dry-run]` moves a Discord chat in as the room NAME-on-yerk, in six steps, each said as it is done. `--dry-run` reads and prints every step and writes and sends nothing: run it first.

1. Channel: a private channel NAME-on-yerk, made with the bot token yerkd.toml names, with the permission overwrites of the room it is made like (so the same people see it); with `--person` that person is let in as well. A channel of that name already there is kept.
2. Voice: `--voice FILE` is copied to the layer's rooms/NAME.md; without it, a one-line placeholder to write.
3. Block: `[rooms.NAME-on-yerk]` from a template in examples/rooms/. owner.toml copies an owner room of yours (`--like`, else the last owner room in rooms.toml that is not the machine room) with its channel and voice set. person.toml copies a person room (`--like`, else the last room with `people`), so its wall is reused: privacy family, `people` the id, Read, Grep and Glob only, no `read`, `also` or sandbox, and a layer of its own under the private folder (0700) holding copies of that room's persona and rulebook less its own text (every line naming its folder, and the persona's `# About the owner` section, the one about its person), the template's `about` section at the persona's end in its place, and pinned.md and open-loops.md to write. Before anything changes, the rooms.toml it would write is loaded (config.rooms) and the daemon's people guard runs on it, and a person room's files are read for any path into the private folder outside its own layer; a miss stops it with one line. Then rooms.toml is copied into backups/ with the time in the name, and the block is appended.
4. History: the old channel's or thread's messages (from `--since` on, else all) filed in the day log under the room's id and class: the owner's lines `owner`, the person's `person`, everyone else's `other`, each with its author's handle, as the daemon files a live line; attachments up to 25 MB saved into the layer's NAME-attachments/ (0700, files 0600). It goes by message id and file name, so a second run only tops up. Yerk's bot must be able to read the old channel. An owner room's block that has an `also` lists that folder in it (a block with none recalls every root and is left so), the yerkd.toml `[memory] also` line for it is printed to add by hand before the deploy (yerkd does not start on a room's `also` outside `[memory] also`), and the last two lines are `yerk pictures backfill NAME-on-yerk --root <folder>` and `yerk files backfill NAME-on-yerk --root <folder>` to run after it, the one folder in the private folder a backfill takes; `yerk doctor` names a room whose folder still holds pictures or documents with no sidecar.
5. Restart: none. It prints the one `yerk deploy` line to run, detached, at a quiet moment.
6. Check: the room's context against budgets.toml; the test webhook (yerk-test-sender) found or made in the new channel, its URL in secrets/discord-NAME-webhook.url (0600, never printed); the yerkd.toml `test_senders` line with its id added, printed to apply before the deploy and never written here; and the warm-up line to post through it.

A person room's persona and rulebook start as the other person room's less its own text: fill in OWNER, PERSON and RELATION in the persona's last section, read the rest for anything else of that room's, and write pinned.md, before the person talks there.

An OpenClaw box moves its notes in with `yerk import openclaw:<workspace dir> [--since YYYY-MM-DD] [--dry-run]`, one workspace a run: MEMORY.md, USER.md, memory/, wiki/ and media/gym copied as they are into <private>/openclaw/<its name>/<the same path> (files 0600), the box tools' state, the kinds the index does not read and every dot or secrets folder left, each line with a shape of yerk doctor's secret scan, or whose key names a secret (a token, a password, a pin, a session) whatever its value, written as its kind; by path and sha256, so a second run writes nothing and the same command tops up.
After a real run it prints the yerkd.toml and rooms.toml lines that read the copies (in each `also` a box path becomes its copy in its place, so every cite name stays; a `read` stays while the box runs; a denyRead keeping a shell off the box gains the copies), to make by hand before yerk-index and yerkd are restarted; it never writes them.

## Importing a chat

`yerk import discord:<channel or thread id> [--since YYYY-MM-DD] [--files] [--dry-run]` files a Discord chat's whole history into the day logs with no room made, through the one import `yerk room add` uses (step 4 above): by message id, so a second run only tops up and a message already in the day log is never filed twice. Its lines go under the room id `discord:<id>`, the chat's name as the label, class `private`: an owner room reads them, no person room does. `[import] classes` in yerkd.toml changes that per id: `"shared"` lets every room read them, and `"room:<a room's id>"` files them under that room's id and class, behind its wall, its people's lines as `person`; a person's old channel belongs with her room, `classes = {"<old channel id>" = "room:discord:<her room's channel id>"}`. A message is filed once, under the first room id it gets: a chat imported before its room is made stays under `discord:<id>`, and a later `yerk room add` files none of it under the room, so a chat that will become a person's room waits in `[import] skip` until `yerk room add` has moved it in. A chat a room covers (its `channel` or `watch` in rooms.toml) is filed as that room files it. Attachments are named in their line with their size and not downloaded; `--files` saves each one up to 25 MB into the private folder's attachments/discord-<id>/ (0700, files 0600). `--dry-run` reads and counts, writes nothing, and prints every line it would file.

`yerk import discord-guild:<guild id> --dry-run` is the server's inventory: every text, news, voice and stage channel and every thread under one (active and archived, public, and the private ones the bot may list), one line each: its parent, how many messages (counted by paging them all; for a chat the bot cannot read, Discord's own count where a thread has one, said as such, else unknown), the first and last day, whether a room covers it, and the class it would get. Without `--dry-run` it imports every chat on the list that no room covers and `[import] skip = ["<id>", ...]` leaves in, one after another, each said as it is done; a chat it cannot read is said, the rest go on, and the run ends 1. Discord hands one bot about a hundred messages a second, so a big server takes minutes. Yerk's bot must be able to read a chat (View Channel and Read Message History): one it cannot read is listed with the day it was made and the day of its last message, read from their ids, and its threads are not asked for.

`yerk import imessage:<chat.db> [--contacts <db>]` and `yerk import gmail` move a person's texts and mail in as files, not day-log lines: `imports/texts/<person or group>.md`, a file a person (named by their contact, else their number or address) and a file a group chat, a chat deleted on the phone placed by its messages' `ck_chat_id`; and `imports/mail/<YYYY-MM>.md`, Gmail's All Mail a file a month. One line a message: who, when in the install's zone, the text on one line, attachments and app messages as tags; a newsletter, a draft and a security mail marked; 400 characters of a mail's text, 1,200 of your own sent mail. Both only read: the databases are opened read-only (a copy of `~/Library/Messages/chat.db` with its `chat.db-wal` beside it, or the newest texts are missing, which the Terminal needs Full Disk Access to make; and of the Contacts `AddressBook-v22.abcddb` under `~/Library/Application Support/AddressBook/Sources/`), Gmail with EXAMINE and BODY.PEEK, by `[gmail] user` and `password_file` in yerkd.toml (a path in the private folder, or absolute, to a file holding an app password alone on its line or after `App password:`, never printed; Google makes one at myaccount.google.com/apppasswords once 2-Step Verification is on, and revokes it when the account's password changes); `[import] me` is the name your own texts are written under. A security mail, a security text from a short code (a bank's, a sign-in's) and anything shaped like a key, a token or a one-time code are written as their kind only, never the secret, so no file the index reads holds a live code or key. A setup that is not there (the database, the `[gmail]` keys or its file, a folder of files no import wrote) is refused with exit 2 before anything is read; a Gmail batch that fails is said and left for the next run, and the run ends 1. By id (a message's guid, a mail's UIDVALIDITY:UID, one a line in `imports/texts.ids` and `imports/mail.ids`), a second run adds only what is new, and a folder of files no import wrote is refused. The files carry no class, so they read as private: with `imports/texts` and `imports/mail` in `[memory] also`, an owner room reads them and no person room does. `--since` and `--dry-run` work as for a chat.

## Install as a service

`units/yerkd.service` runs yerkd under systemd with `Type=notify` (a start counts once READY=1 says the port listens), `WatchdogSec=30` (the beat stops when the event loop stops, and systemd restarts it), `MemoryHigh=4G` with `MemoryMax=8G` (raise MemoryHigh by 500M for each room kept open past seven), `KillMode=mixed` with `TimeoutStopSec=30` (a stop sends yerkd SIGTERM alone: it says STOPPING=1, ends each room's Claude Code itself, closes the gateway clean and exits 0, in about a second; a turn cut mid-run has its messages run again once at the next start, marked), and `NoNewPrivileges` with `PrivateTmp` (no setuid gain for a room's shell, a /tmp of its own). `yerk status` names the version and the commit that runs; `yerk status --json` is the same as one document for a monitoring tool (rooms, accounts, the last turn per room, the day's failed turns and unanswered messages, the index, the newest backup's age). yerkd reads each account's meters again in the background, `claude -p /usage` through `nice -n 19`, one account at a time and each about every 15 minutes, so a card that asks nothing (a room's `/status` first answer, `yerk status --json`) shows that reading where it is newer than the stream's and says its age only past an hour; its meter there has `source` `kept` and its own `at`, apart from `live` (asked now) and `stream` (a room's turn's own). CHANGELOG.md names what each merge changed. Copy it to `~/.config/systemd/user/`, set `YERK_PRIVATE` and `YERK_STATE`, and `systemctl --user enable --now yerkd.service`. A yerkd started by hand with `systemd-run --user --unit=NAME` moves onto it with `yerk deploy --unit` (the unit is the one the running yerkd's pid is in; `[deploy] unit = "NAME"` in yerkd.toml names it instead): the unit's command (read word by word from systemd's bus), folder and environment go into the file under the same name, written 0600, and the file unit starts at the next quiet moment; a failed proof puts the transient unit back. After that `yerk deploy` restarts it in place. `[deploy] tree` names the daemon's checkout (default: the unit's working folder), `tests` the fast subset (default `tests/test_scrub.py`, `test_budget.py`, `test_card.py`, `test_style.py`), and `proof_seconds` how long the proof may take (60). The fast tests run with the deploy's private and state folders as `YERK_PRIVATE` and `YERK_STATE`, so the budget test builds every real room the way the daemon does, rules file included, and a room past a budget fails the deploy with the room and its part on the card. With no `--private` and no `YERK_PRIVATE` those folders are the ones on the running yerkd's own command line (`--private` and `--state` in its unit's ExecStart, and the card's second line says `private folder: the daemon's`), and with none there the deploy refuses in one line, `no private folder: pass --private`, so the fast tests never read the fake example layer. After the fast tests the deploy holds the layer's recall controls on the code under test (`yerk recall-bench --controls`, which writes nothing): each is searched on the exact half, one missed there once more with the meaning half, and one missed then deploys nothing, the card naming it (`recall: N of N hit`, and how many only through the meaning half, when they hold).

## Backup

`yerk backup` writes one dated archive, `yerk-YYYYmmdd-HHMMSS.tar`, 0600 in a 0700 folder: the private folder whole (secrets as bytes, with their modes), the ledger through SQLite's own backup (whole while yerkd writes), the rooms' session bindings and small state files, the index's metadata, and the `yerk*` units. Its last member, `MANIFEST.json`, lists every file with its bytes, sha256 and mode. The index's vector store goes in only with `--with-index` (`yerk-index` rebuilds it from the layer); logs and a room's scratch never do. `[backup]` in yerkd.toml: `path` (default `yerk-backups` beside the private folder), `keep` (the last 7 stay), `units` (default `~/.config/systemd/user`). `units/yerk-backup.timer` runs it at 04:10, before retention's 04:20; `yerk status` says the newest one's age and size, and `yerk doctor` says one older than 36 h. An archive on the layer's own disk survives a bad edit, not a dead disk: copy the folder off the box with a tool of your own.

`yerk restore ARCHIVE --to DIR` reads the whole archive against its manifest first and refuses one cut short or changed in a byte, before it writes anything; then it writes `DIR/private`, `DIR/state` and `DIR/units`, a line a step (`--dry-run` says them and writes nothing). DIR must be empty. Without `--to` it writes the layer's own folders: straight in when they are empty (a new disk), and over ones that hold files only with `--force`, after a backup of the layer. What it replaces, a unit file too, is moved to `<state>/trash/<day>/restore-<time>/` first, never deleted. It refuses while yerkd runs on the target unless `--force`. A room's Claude Code sessions live in each account's own folder, outside the archive: a restored `sessions.json` points each room back at its session, and one the account no longer holds starts fresh with the recap line, as a lost session does.

## The private folder

- `rooms.toml`: one entry per room: channel (`discord:<channel id>`), account order, model, tool allowlist, privacy class, time zone, and the context files. `layer` names the folder those files come from (default: the private folder itself). `people` lists the Discord user ids the room answers besides the owner (unset: the owner only; the owner is answered in every room). The owner adds one more from the room itself by asking there: its `people` tool takes a person who wrote in the room's own channel, named by one of their messages, on the owner's own words of that turn, kept in the daemon's override in the state folder over rooms.toml, which is never written, and joined at every start; `drop` undoes it, and a room rooms.toml could not give `people` is given none (`yerk explain room-people`).
- `[defaults]` in `rooms.toml`: the tool set every owner room carries, declared once, so the rooms keep one way of doing things without a hand edit per room. It holds `allow`, `worker_addons` and `mcp.<name>` server tables only (each room keeps its own `sandbox`); any other key stops the start with one line naming it. A room whose privacy is owner (or unset) carries each default it does not set itself: its own `allow`, its own `worker_addons`, or its own `mcp.<name>` table, replaces that one default whole, and `allow_remove = [...]` drops named tools from the allow it inherits. `{room}` in a server's `args` and `env` is filled with the room's name. A room whose privacy is anything else inherits nothing. `yerk doctor` names an owner room that drifts, one line each: red for a default tool its own allow misses and its `allow_remove` does not name, orange for its own copy of a default (an allow equal as a set, a server equal once `{room}` is filled), the way rooms come apart later. `worker_addons` names the room's own add-on tools every worker started from the room gets (a tool as `allow` has it, or a server's name for each of its tools `allow` names), whoever starts it: the `worker` tool, `yerk worker start`, a booked agent job, the daemon's own workers; one `allow` has not, or on a server whose table passes a credential, is skipped and the worker starts, and `worker_addons = []` gives a room's workers none. A start's own `addons`, and an agent job's `addons` in jobs.toml, give more, refused when the room has not one. `yerk room add` copies the room it is made like as written, so a new owner room inherits under its own name.
- A room with `people` reads its own lines and the shared files only, so it takes no `read` folder and no shell tool, unless `shell = "trusted"`: then it lists the owner rooms' tools (Bash, Write, Edit and the rest), its shell runs inside the wall the daemon builds (below), and Write and Edit reach its layer and work folder only. Its `[rooms.NAME.sandbox]` table may add `filesystem.denyRead`, `filesystem.denyWrite` and the `network` allowlist; any other key, an `allow` rule for the file tools, or a wall that cannot be built stops the start with one line. `yerk explain trusted` says the same. What is sent to a person's room (its uploads, a recording's transcript, the pictures it files with `seen`, where a password, a passphrase, a key or a token a picture shows is written `[left out]`, as in every room) is recalled there as its own, read by that room and the owner's rooms only, and a reply there that says what a third person said from a turn that read nothing is turned back once, as in an owner room.
- `taste.jsonl` in an owner room's layer: the owner's thumbs on the room's replies, kept the way the old box keeps them. A message of the owner's in the room's own channel that praises or faults the last reply ("that was good", "too long") adds one row, one per reply per sign; a test sender, a person or the harness never rates. Every message in that room then carries the `taste` part after recall: three praised and two faulted replies, the owner's words beside what the room had said, the room's own newest first, then the other rooms' (`[per_message.on_hit] taste`).
- The file is the switch: a layer without `taste.jsonl` gets no row and no part, and a room with `people` gets neither. `yerk map` shows the part's size.
- `[location]` in `yerkd.toml`: where the owner is, from a phone's fixes. `file` holds one JSON fix a line (`ts_iso`, `lat`, `lon`, `speed_mps`, the shape the box's location watcher writes), `places` the watcher's table of named places (`{"places": [{"label", "lat", "lon", "radius_m"}]}`, a `todo` row never matching), `stale_after` how old the newest fix may be (default `3h`). Both files are only read, and nothing goes to the network: a fix is named by the nearest place whose radius holds it. Every message of the owner's in an owner room then carries the `place` part after the metadata line, `[place] near the office (Example City), 7 min ago, stationary` (moving: faster than 2 m/s, or 150 m from the fix before; `[per_message.parts] place`). There is none when the newest fix is past `stale_after` or at no named place (the road, a place not in the table, so no coordinate is ever said), in a room whose privacy is not owner, or on a person's message; no table, no part anywhere. The mechanics say when a room uses it unasked: at a gym, it logs the session there; at work, it minds the hours and the commute; moving, it keeps replies short. `yerk map` shows the part.
- `yerk location day [DATE]` writes the day's places into that day's log as one line, class private, so the owner's rooms recall it and no person's room reads it: each stay at a named place with its first and last fix (`08:40 to 12:00 the office (Example City); 12:45 to 17:05 the office (Example City); 17:40 to 23:40 home (Example Town)`), a stay ending at another place or at a gap of 30 minutes between its fixes; never a coordinate. A re-run replaces its own line where it stands (its id is the day's), so no other line moves and every cite into the file holds; `--dry-run` prints the line and writes nothing. It runs nightly as a script job in `jobs.toml`; a script job's environment keeps PATH and HOME and the unit's `YERK_PRIVATE` and `YERK_STATE`, so a `yerk` line runs on this install's folders (naming the folder as below does no harm):

  ```toml
  [jobs.location-day]
  kind = "script"
  schedule = "*-*-* 23:55:00"         # 23:55, the day nearly whole
  tz = "<your [memory] timezone>"
  room = "<an owner room>"
  cap = 2
  deliver = "silent"                  # the day log is the output; a failure still alerts the ops room
  command = "$HOME/yerk-ai/.venv/bin/yerk location day --private $HOME/<your private folder>"
  ```
- A watch is a script job with `deliver = "tell"` (`yerk schedule add NAME --kind script --deliver tell`, or the schedule tool's `deliver` "tell"): no model runs while it polls, its output, when there is any, is told to its room's own session as a due note is, in a turn of its own once the room is idle, said in the room's voice (cut at 4,000 characters with the path of the whole of it), and no output costs nothing. `wakes` (default 6, 1 to 60) is the most turns it wakes the room in any hour; past it each finding waits in its run's folder and the newest is told once the hour allows, as one turn naming how many were held back. Its script keeps what it has seen in `$YERK_WATCH_STATE`, a 0700 folder of the job's own kept across runs that Yerk never reads, so it primes itself on its first run and marks an item seen once it has printed it; a failure alerts the ops room as any script job's does.
- `yerk jobs stop NAME`, or the schedule tool's `stop` in an owner room (any other room gets the line it has today), ends a job's run in progress. A script job's service is stopped and read back as down, every open run row of the job is closed as stopped (`exit` and `result` "stopped", `delivery` "none", a note saying who asked), and the machine room gets the stopped line a worker's job gets, never the failure alert; a row the runner ended first is left as it is. An agent job's running worker is stopped as `yerk worker stop` stops one, its end saying itself once. The timer is never touched, so the next fire stays; a one-shot leaves the file and its units go, as at the end of any run. The answer says what was stopped, how long it had run and the next fire read back; with nothing of the job running it says when the job last ran and its next fire, and exits 1. With no daemon a script's run is still stopped and closed, the command saying the machine room was not told; an agent job's worker is the daemon's, so nothing is stopped. A stop reads as a failure nowhere: not in `yerk status`, not in the alert rule below, not in the doctor's review, and a restart's sweep never closes a stopped row again.
- One alert per unchanged failure: when a recurring job's run fails (a script's error exit or time out, an agent job's end that is not done, did not start or stopped) and its previous ended run, a stop skipped, failed with the same result and its alert post is known, that post is edited instead of a new one being sent: the same line and "N times since HH:MM, last HH:MM" in the machine room's clock, the new run's row holding the same post. A different result, a good run between, or an edit that cannot be made (the post deleted, the edit refused, a channel with no edit) posts anew. The first good run after alerted failures edits the post once to say the job is ok again and when, and the next failure posts anew. The ledger's run rows are the only state, so it holds across a restart; a one-shot and the lines other parts of Yerk AI send post as before.
- `yerk doctor` reviews the jobs, read only, beside its cron line check: a job whose room is not in rooms.toml or whose account is not in accounts.toml, a one-shot past its time still in the jobs file and not running, a job's runs of the last 24 hours that did not start, were cut or still read undelivered (one line per job with how many and the last time), and a watch's findings held more than a day, each one line naming the job and what to do. It starts, stops, edits and removes nothing, and a jobs file or ledger it cannot read is one line saying so, never clean. The nightly sweep keeps the folder of a watch's held finding whatever its age, since its output is what the room is told once the hour allows.
- `accounts.toml`: one line per account: `name = { config_dir = "...", order = 1 }`, optionally `token = "secrets/..."` (the default is `secrets/claude-<name>.token`). Adding or removing an account is that one line; a room's own `accounts` list only orders the accounts it names, the rest follow.
- `yerkd.toml`: the daemon's settings: the Discord token file, the owner's user id, webhook ids accepted as senders in test mode, the local port. A running `yerkd` writes its pid and port to `yerkd.json` in the state folder.
- `[watch] assistants` in `yerkd.toml` lists other assistants' Discord user ids: in a channel a room watches, their messages go in that room's day log under their own label once they stop changing (a progress card never), never answered and never read as anyone's instruction, so the room can read what was already said there. A message the owner sends there waits for that answer (the first of theirs after it to go 6 s with no edit and no delete; a progress card, a message with an OpenClaw tool row or Yerk AI's own card shape, never is, however long it sits still), up to the room's `watch_wait` in rooms.toml (default 150 s), counted again from the card's last edit while that card is up, three times `watch_wait` at most and at most 30 s more once the card is deleted with no reply, then comes in as one turn with the answer under it, or with a line that it had not come; the room's own channel never waits on it. Their files, in that channel or in the room's own, are saved in the room's `work/inbox/<message id>/` as a person's are (an owner room's PDFs and workbooks with their text beside them), once a message: an answer a held message waits for has them saved before that turn, its line naming where each was saved or that it could not be fetched, and any other message as it is filed. None is a file the room must open before it answers, and one that will not come is never a notice in the room, since no one there sent it.
- `secrets/`: files only you can read (mode 0600), for example the bot token. Nothing in the repository reads them except the daemon at start, and every room's settings deny its Read tool and its shell the folder. A worker's unit sees the state folder read-only and its own folder writable; the install's secret, this folder and every room's folder are not there at all, but for the worker's own account token, bound back read-only for its first step, and its own room's work folder, bound back at its own path, so a worker spends no money outside the daemon's tools, their gates and the ledger. A start whose brief names a path its worker cannot see still starts, and says so: its answer names each such path (`unseen`) with a sentence for the caller, and the worker's prompt names them, to be said in the report's first lines.
- The Discord bot: invite it with the `bot` and `applications.commands` scopes and permissions `274878008384` (View Channels, Send Messages, Send Messages in Threads, Read Message History, Add Reactions, Attach Files), and turn on its Message Content intent; it asks for no other intent (Guilds and Guild Messages, no members, presences or direct messages). `yerk room add` and `yerk setup-room` also need Manage Channels and Manage Webhooks (`275414879312` with them), and an import of a server's private archived threads Manage Threads. Administrator adds every channel and every server setting, which Yerk itself never uses: give it only when a plug-in of yours acts as the bot on the server (moderation, admin writes), knowing that a room steered through that plug-in reaches all of it.

## How a room runs

One `claude -p` process per active room, stream-json in and out, with:

- `--session-id` on a session Yerk AI minted, or `--resume` on the room's own session; one live process per session, by lock file
- `--setting-sources ""` and `--settings`, so only the settings Yerk AI writes apply: a Read rule for the room's folder, an Edit rule on its work folder in every room (on its layer too in a trusted room), so its Write and Edit tools and a shell redirect land there as called and a write anywhere else is asked as before (without it Claude Code asks for every Write and Edit, and for a shell write its sandbox does not auto-allow, with nobody at the keyboard to say yes; proven on Claude Code 2.1.316 by a scratch probe), Read deny rules on every secret, the hooks (each a command hook whose `curl` posts the event to the daemon with the room's token read from a 0600 file beside the settings), and `autoCompactWindow` from `budgets.toml` `[session] compact_window` (a room's own `compact_window` in `rooms.toml` overrides it; 0 leaves it to the model), so a room compacts where Yerk AI says, never at the model's window edge: a room that rides the whole window re-reads all of it on every message and pays it in full after an idle hour, when the prompt cache is gone. A compaction loses nothing searchable: every line is in the day log, and the recall pack comes back after it
- Claude Code's sandbox, `enabled` with `autoAllowBashIfSandboxed`, for a room whose `tools` run a shell (Bash, Monitor, PowerShell or `default`) and that rooms.toml gives no `[rooms.NAME.sandbox]` table: without it a Read deny stops `cat` and the Read tool but not a script, `grep` or a redirect; a room's own table, `enabled = false` included, is passed as written (on Linux the sandbox needs bubblewrap and socat)
- for a room with `shell = "trusted"`, the daemon's own sandbox instead, rebuilt at each process start: no command retried outside it, no start without it, and denied to the shell for reading and writing the owner's whole home but the room's own folders (each entry of the home that holds none of them whole, one that holds one walked the same way, a link by its target), so a key, an account's token file, a backup or the shell history that no list names is closed too, and wherever they are, every entry of the private and state folders but the room's own (the other layers, the memory folder, rooms.toml, imports; every other room's folder, the ledger), every memory root and every other room's layer and `read` folders, and `projects/` under each account's folder; its outbox is read only and the Python user site-packages are re-opened read only (`allowRead`, which re-opens a path inside a denied one). Until 2026-11-03 only the folders the daemon knew were denied, and the rest of the home stayed readable to the shell (proven on Claude Code 2.1.304 by a scratch probe: its layer, work folder and python-docx open, every walled path and the network closed)
- `--add-dir` on the room's folder; every part of the appended context starts with `[from <absolute path>]`, so the model can re-read the file a fact came from
- `--mcp-config` naming only Yerk AI's server, with `alwaysLoad: true`, and `--strict-mcp-config`; a `--tools` allowlist; `--model`
- `--append-system-prompt-file` with the assembled context, built to the sizes in `budgets.toml`; the install's rules file is a part of its own (`rules`, after the hand-kept files, since the rooms write it as they go), so a rulebook near its cap never pushes a shared rule out, and a part past its size is sent trimmed under a marker that names it, whole lines only and the marker counted inside the size (a rule file, the rules part or a rulebook, keeps its first lines whole and drops the newest, never a middle line; any other file keeps its first and last lines; the recall pack never needs it, since it leaves its oldest items out whole to fit, after the open commitments), and the machine room is told how many lines of the part's file went and its size; a rule filed with `remember` and `job` that would take the rules file past its size is fitted first, the `<example>` blocks out of the rules newest first and its own first until the file is 150 characters under it, the rule's own words never cut; a rule with no room even then goes whole to `rules-topics.md` beside the rules file, the topic rules, loaded on demand rather than at session start (its job's older line, in the rules file or the topic rules, marked superseded by it and named in the result's `replaced`, as a filing into the rules file names its job's topic line it marked): its result says `topic` with the words it loads on, the room ends its reply saying so, and the machine room (else `[jobs] ops_room`) gets one notice, "filed as a topic rule: loads when <its words> come up", with its job, its room and the rooms it is for. A topic rule's words (its triggers) are its job's words and what its own words name, a #channel, a file, code in backticks or a capitalised word mid-sentence, each weighted by how few rules say it with the rarity weight recall's keyword search gives a word; a rule filed with `remember`'s `triggers` (the owner's words, "money" or "how do I make money") loads on its job's words and those instead, kept in an `[on: ...]` mark before its trailer, each picked one weighing as a word only one rule says, a phrase held when a message says each of its words that names something (a, the and how name nothing; a trigger with no other word is refused, nothing filed), and a filing of its job that names none keeps them; a message whose words (its attachments' names among them) weigh three quarters of a word only one rule says gets the rule in its per-message `rules` part, after the "Rules changed since you last looked" block and under the same 1,500 characters, best match first, each rule once per session and again after a compaction. A rule is for every room unless its line carries `[rooms: NAME,...]` before its trailer; a filing writes the mark when the heaviest of the rule's words that any room's rulebook says is said by the filing room's rulebook alone (its topic is that room's own: "teams" outweighs "message", which every rulebook says), naming every room that reads that rulebook; a rule whose words no rulebook says, or the heaviest of them another room's too, is every room's. Before this, such a rule waited in `rules-overflow.md` in no room; yerkd's first start with the change moves that file's rules into `rules-topics.md` once, the old file kept beside it as `rules-overflow.md.moved`; a `[rooms: NAME,...]` mark typed on a line there before that start is the scope that rule gets, whatever its words. `yerk map ROOM` gives the topic rules' size and which rode on the room's last 20 messages, and `yerk doctor` names a topic rule that can never load (longer than the per-message part, or kept to no room on file)

The room runner:

- A message for an idle room starts a turn. A message that arrives mid-turn goes straight to the process's stdin and is answered inside the same turn; the replayed copy (`--replay-user-messages`) is the proof it was accepted. In a room with more than one person only the same person's message folds in: another person's waits for its own turn, and messages that waited are joined into one turn only while the sender stays the same. When that turn fails, a message that folded into it after it started is not failed with it: it runs next as its own turn, and its card says so. A result of Claude Code's own turn for a background command's notice (`origin` kind `task-notification`, what a resume streams first for the commands a crash left running) never ends or answers a turn.
- Only the final text after the last tool call is delivered. A turn owns one progress message, edited with its first visible line, then replaced by the reply, split under the channel's limit and never inside a code block. In a room with people that card shows the room's newest holding line (the text it sends itself) and a step count, never a step's words; `card = "steps"` in its block in rooms.toml gives it an owner room's card instead, the model's newest line and one row per step, done or not done (the thinking line stays owner-only). Every `remember` result ends with `next`, the shape of the answer that follows the call (first and whole, the filing one clause at its end), and a final text that only reports a filing (`remember`, `schedule`, `hold` or `settings` called last, the answer above the call or never written) bounces once, a `stub` row in the shadow ledger the morning diff counts. A final text whose first paragraph is a note to the room itself before the answer (at most 700 characters, holding a rulebook tag, `Landed:` or `Bounced:`, or with more after it, a directive such as "Confirm" or "Keep" beside a shape word such as "in a line", "style" or "nuance", and no you or your) bounces once for the answer alone, a `note` row. In a room with people, a final shaped as the owner rooms' status board (a line opening on ☑, ☐, ⛔, 🟦 or 🟨, the colour key, "unblocks:") bounces once for two or three plain sentences, a `board` row. In any other room, an owner room or the machine room, with `[gates] retired_marks` set in yerkd.toml (none by default), a final holding one of those marks anywhere in a line outside a fenced block bounces once for a plain numbered list, a bold lead of two or three words a line and who does what in words, a `retired` row; with the list set, the session start's room pack quotes the room's earlier lines without the marks, a line that was only a colour key left out whole. A fenced block a room posted on an earlier day of the last 14, equal once each line is stripped, blank lines dropped, runs of spaces made one and the fence's tag left out, is turned back once per result, in `send` before it posts and in the final text at Stop, naming the day and time it first went out and asking for a line-by-line re-read against today, a `paste` row; the room's next send goes out. In an owner's room, a document (.docx, .pdf, .xlsx, .pptx, .txt, .md, .csv) or a pasted block going out through `send` or in the final text with no claims sheet written that turn (a file whose name holds claims, beside the document or in the work folder: one row per claim, its source line, the quote) is turned back once per result the same way, saying what the sheet is and where it goes, a `sheet` row; a room with people only ledgers it. A person's message that comes in while a turn runs is written into it with one line ahead, saying it was sent so many seconds after the message above while the room was answering, to be answered in that same reply by name (a message from the channel the room watches goes in without it, since its own line says how it is answered); a final that covers such a message, once its replay is seen, and carries none of its numbers (nor, in a message of three words or fewer, its words of three letters or more, filler such as "okay" or "thanks" aside) bounces once to be written again naming it in its first words, a `fold` row.
- Files go out on one path, up to what the bot can send (measured: 20,971,520 bytes, Discord's own answer, above discord.py's 10,485,760 for a tier 1 guild). A file a crash left unconfirmed is sent again from its outbox snapshot, labelled, unless the room already shows it; the message runs again told which files are in the room. A file the room posted days ago, its outbox snapshot swept, comes back with `attachments`: the daemon's bot reads that message (by its id, in the room's own channel then the one it watches; by its link; or, with a file's name alone, the newest message the room posted it in, from the ledger) and saves its files to the room's inbox, where the sweep never takes them, for `send` to post again (need 69 of 2026-11-06).
- An edit of a message still waiting revises it before it runs; an edit of one already running or answered comes in again, marked; a message deleted while it waits never runs. A reply carries the message it answers.
- A failed turn takes the action `failures.toml` gives its class: transient reruns the same session (twice at most), overflow compacts then reruns, auth and quota rest that account (doubling per account and kind, kept across restarts; a rate limit instead rests the account for the model it hit until the reset the stream names, else the account's weekly reset from its last reading, an hour at the least, and that rest ends early when its usage comes back: a live reading of the account taken since the rest began, yerkd's own about every 15 minutes or one `/status` asks for, with no meter binding its model full (the session, the week, that model's own week) frees the account for the next pick, though a turn that hits the limit again before the end a reading took away rests the account to that end) and continue the same turn under the same card on the next account, resuming the same session; when every account is out of the model a room was put on, the turn runs on rooms.toml's model under the same card, which says so, and the next message tries the pinned model again; a session that cannot be resumed starts fresh with a one-line recap; anything else is a visible notice. An empty reply resumes the same session once more on a new process, then starts fresh with the recap line, which says the day log holds what was said; the card names which happened.
- A turn Claude Code answered on a fallback model after a block stands, and its card and ledger row say so; the room's next turn starts a fresh session on the room's own model.
- After 30 idle minutes the process closes; the next message resumes the session.
- A room compacts between turns, never inside one. Idle 25 minutes (budgets.toml `[session] idle_compact_after`) with its session at 0.7 of its compaction window or more (`idle_compact_at`), it is compacted then, in the background, on a copy of the session launched without fast mode, as a turn's copy is (the recall pack comes back after it), so the next message finds it small instead of waiting minutes in its own turn for Claude Code's compaction; a message that comes in meanwhile is answered at once on the live session and carried to the copy, which becomes the room's session as that turn ends. With no process alive to copy (after a restart), the room's process starts first and a message waits for that start alone; a room with fast mode on waits for its next turn instead. The session's size is the last call's usage as the stream says it, kept in each turn's ledger row, so a restart keeps it. Every compaction Yerk AI starts sends `/compact` with one line after it, what the summary keeps besides Claude Code's own: the person's orders in their words, what is still owed to them, and a guess marked `UNVERIFIED:`. A room's `compact_focus` in rooms.toml is its own text for that, empty or false for none; Claude Code's own compaction inside a turn is as it was. One try per growth: after a compaction, kept or failed, the next waits for a turn to grow the session again, and a failed one is logged once. A message that comes in during a compaction that holds the room (`yerk room compact`, or a turn that ended near Claude Code's own line) waits and runs right after it, and the log says how long it waited. A room's own keys in rooms.toml move the line; `idle_compact_at = 0` turns it off, and so does a window left to the model (`compact_window = 0`), whose size Yerk AI cannot know.
- A hop resumes the same session on the next account by the transcript's absolute path (`--resume` takes one, as the docs promise), learnt from the first hook call of the session and kept in the room's binding; the id alone is searched only in the resuming account's own `projects` folder. Pointing every account's `projects` folder at one (a symbolic link) is an optimisation that lets the id be found anywhere, not a requirement.
- Every call to the daemon (`/hook`, `/mcp`, `/control`) carries the `x-yerk-secret` header: a room process sends the token minted for it at start and bound with its session (the daemon knows the room by that binding, never by a header a caller picks), the CLI and the job units send the install's secret from `secrets/yerk-http.secret` under the state folder (never inside a room's layer, so no room's read rule reaches it; `yerkd.json` names the path), and a worker's own server sends `secrets/yerk-worker.secret` beside it, which opens `recall` and `read_memory` only. A hook call no binding explains is answered `{"yerk": "unbound"}` and logged, never with a silent `{}`.
- The day log's line is `- HH:MM:SS+hh:mm room#id role@who: body [c:class] [m:id]`: the offset is each line's own from the configured IANA zone, the room's stable id (`id` in rooms.toml, else its channel) rides beside its name, the author is a role and a handle, and the class (private, room or shared) says who may read the line back. `recall` and `read_memory` return to a room only shared files and its own lines; the owner's rooms read everything. Lines written before this shape were rewritten once, the originals copied to `backups/` (the rewrite left in shrink-1, its job done on the one install), and the reader still parses the old line.
- A thing with a date is filed with it: `remember` takes `due` (and `owes`, the name of whoever owes it to the owner), the line carries it as a mark like `[due 2026-12-02 owes Example Roofers]` before its class and id, and it is open until its outcome is filed with `replaces` naming it or its date is more than 14 days past. What is overdue or due in the next 7 days, as far as the room may read it and never another room's own lines, opens the recall pack at a session start and after a compaction, and `yerk due` lists it on the command line.

The daemon's one local HTTP server carries `/mcp` (Yerk AI's tools, each in docs/tools.md, among them `send`: text, or a file from the sending room's own folders, to a room; `hold`: end the turn while waiting on a named event or worker; `recall`: ranked chunks of the memory tree with path, line and a `file:line` to cite; `read_memory`: exact lines of a file inside the memory tree, nothing outside it), `/hook` (the clock and metadata lines and the recall part, keyed on the session id through the room-to-session table; the recall pack after a compaction; the Stop checks), `/control` (`yerk room close`, `yerk room compact`, `yerk worker`, the job units), `/status` (`yerk status`) and `/page` (a room's live page, A live page below). `recall` takes `since` and `until` (each `YYYY-MM-DD`, either alone), which keep the search to files named for a day in that range before it ranks, so a question about one day competes with that day's files alone, and a range that finds nothing is searched once more without it, which the answer says (`widened`, and one line).

## What you see

Every card, notice and status line follows one rule set, written down with an example of each in [STYLE.md](../STYLE.md): the state first (🟢 done, 🟠 running or partly, 🔴 not done, ⚪ nothing to do), one short line per item at phone width, no file paths or exit codes in a room (a report is "report saved" with `yerk worker report <id>` behind it), times as a person says them, and the same words in every room from one vocabulary, `yerk_ai/words.py`. The developer detail lives behind `yerk worker report <id>` and `yerk status --full`. A worker's card settles with its report's first line in two phone lines at most, a quiet end's too (a last message of exactly NO_REPLY: no turn in the room, so the card is all it says, "finished clean, nothing to add" only when that line is NO_REPLY as well or there is no report), and a scheduled job's worker card starts its small line with the job's name, so the runs of one job and of another are told apart on a phone (`yerk explain job-cards`). `yerk abilities` lists every ability one line each, built or known but not built (voice is described, not shipped, and `yerk explain voice` says how it would be built and why it is not); `yerk config get presentation` prints the presentation settings with their plain words. `tests/test_style.py` holds every renderer to it.

Each morning the diff also shows yesterday's calls, every pick, plan or "you should" a room made for you (read by code, no model): the room and its words, and under them the call's number and the cites its turn read, or "no reads behind it", the first 20 and then the count.
A call that stood on a wrong line is fixed at that line with `yerk calls fix <number> <path:line> <what is true>`, filed the way `remember` files a correction and never into a persona or a rule, and the next morning's diff shows the fix.

`abilities.toml` holds 139 abilities: 76 built and 63 described, known and not built. The described ones are the abilities a long-running personal install grew over months, written neutrally: reading bank balances read-only, a browser on its own profile, a morning brief, watching a page, and 59 more. ## Add-ons

The core is what every install runs. An add-on is an ability in a repo of its own, installed only where it is wanted. Its root holds `addon.toml`, an abilities.toml entry with `repo` (its git URL), `version`, `size` (its own ceiling, in lines of its code) and `install` (its package and module, its MCP server and allow lines, its yerkd.toml tables, the rooms.toml keys it reads, its units, its budget lines, its words file and its tests, and the attachment types it reads, each to one of its own tools, as `reads = { "video/*" = "mcp__NAME__frames" }`).

```
yerk add examples/addons/hello --private ~/yerk-private --dry-run   # each step it would take, nothing written
yerk add examples/addons/hello --private ~/yerk-private             # a folder, a git URL, or an ability whose entry names its repo
yerk remove hello --private ~/yerk-private                          # each step undone, the private folder as it was
```

`yerk add` fetches it into the state folder's `addons/NAME`, refuses it when its code is over its own `size`, its name is not one plain word (letters, digits, `-` and `_`), a words file, test or unit it names is outside its folder (absolute, through `..` or through a link) or a budget value is not a whole number, installs its package into this venv, writes its server as `[defaults.mcp.NAME]` and its tools into `[defaults] allow` in rooms.toml and its tables into yerkd.toml (marked blocks the loaders read back first), links its units into `~/.config/systemd/user`, and runs its own fast tests; a failing test, or any step that fails, undoes every step. The rooms get it at yerkd's next start. While it is installed its budget lines count in the gate, its rooms.toml keys are known to `yerk doctor`, an attachment of a type it reads gets a line naming its tool under the room's `[attachment]` line, `yerk deploy` runs its fast tests after the core's, `yerk abilities` says installed (or what is missing) and `yerk status` names it. examples/addons/hello is the example: one MCP tool, one unit, one budget line, one words file and one test.

## Voice notes

A voice note or recording sent to a room arrives with one line under its `[attachment]` line: the room takes in the sound only through the `transcribe` tool on Yerk's own server (the daemon has the network, a room's shell has none), which returns the words with a timestamp per segment and saves them beside the audio as `NAME.transcript.txt`, and a turn that ends without calling it bounces once.
Pass 1 is OpenAI whisper-1 on the install's OpenAI key (`secrets/openai.key`, ffmpeg on the machine); with `secrets/groq.key`, pass 2 runs Groq whisper-large-v3-turbo on the same chunks and marks uncertain, with both readings, a segment the two disagree on, and where whisper-1 wrote no words (a `♪` through speech it missed) and Groq heard some, Groq's lines stand in, each marked `(second pass only)` and counted on the file's first line; a request that ran long (a timeout, or an error after 30 seconds) is never sent again, and a quick busy answer gets three tries; every paid call is a spend row, the morning diff says the day's total, and a recording past US$1 waits for the owner's yes (`yerk explain transcribe`).
With `secrets/meta.key`, Meta's Muse Voice Transcribe in DIARIZATION mode says who talks when: 120-second windows starting every 60 s, 16 at once, each given up after 100 seconds (Meta cuts a request at about 2 minutes, and on 2026-11-12 a 120-second window took about a minute), its letters matched across windows by the speaking time they share in each 60-second overlap, and each line takes the letter covering most of it (`[00:14:00 -> 00:14:03] B: then email the vendor`); the words and their times stay whisper-1's. A voice that says nothing through an overlap gets a new letter when it speaks again, so a splice of about 10 seconds of each voice's speech from both sides of that break goes to Muse once more, in two orders, and in a third when those two leave a letter unsure; a new letter that two of them put with one earlier voice takes that voice's letter again, and one that two of them heard with no earlier voice is a new voice; a splice that gives one letter to two voices a window heard apart (each speaking 5 seconds in it) is not used, a letter never joins a voice a window heard apart from it, and a bridge that fails joins nothing. The line under the file's head gives each letter's speaking time and tells the room the letters are not names, so it says who is who as a guess unless the owner says, and how many letters the bridges left unsure, when any. One voice writes no letters, so a voice note reads as before; without the key, or when a window fails, the words come back unlabelled under `speakers: none (Muse: why)`, and no window starts after one has failed. ## Texts as you

Texting answers some of your iMessage threads in your name while you are away from them, for the people on your reply list and no one else. When Alex texts you and stops for a moment, one model call reads the thread and decides one thing: a reply of one to three texts, a tapback, nothing, or a hold for you. A second call, which can reach nothing of yours but the thread, Alex's sheet and the draft, checks every reply and tapback, and the code lets one go only when that check passes and every thing it says about you rests on your own texts in the thread, the sheet or a topic of yours. At the moment it would go the thread is read again, and it goes only if nothing changed: if you answered first, with a text or a tapback, or Alex wrote again, it is stopped and never sent late.

You need three things. The Mac side: your Mac signed into Messages, with the bridge app texting reads your threads through and the runner that sends what texting puts in its outbox, reached by ssh the way the `text` tool reaches it (`[imessage] host`, else the ssh of an owner room's add-on). The reply list: `texting/people.toml` in your private folder, 0600, each person a key, a first name and their phone numbers or addresses. And a sheet for each person, `texting/people/<key>.toml`: what is open to say to them, what they already know, how fast to answer, and how you write to them; `yerk texting sheets --check` reads the list and every sheet, writes nothing, and prints one line, with its file, for each that does not load.

`[texting] mode` in yerkd.toml is `off`, `dry` or `live`. Off, nothing connects and nothing is written. Dry runs everything but the send: each decision is one line of `<state>/texting/dry/YYYY-MM-DD.jsonl`, a text that would have gone is written as a job file beside it, and its card, marked DRY, goes to the room `dry_report` names, or to none. Live sends through the Mac, and the cards go to the room `report` names, your main room.

A text that must wait for you is one card in that room: who it is for, their texts, the draft and why it waits. A card with a draft says why in the code's own few words, never the writer's reasoning: what has no source, else the class that waits for you (`why: dating, your call`), else `your call`. A card with no draft gives the one question only you can answer, and takes `edit <text>` or `skip`, never `send`. The writer's whole reasoning is kept in the ledger, and the `texting` tool's `why` reads back the newest decision's, also after it went or was skipped; for a text the check held, it gives the check's reason. Reply to the card with `send` and it goes as the card shows it, `skip` and it is dropped, or `edit <text>` and your words become a new card, showing what the code's own check finds in them, for your `send`. A bare `send` or `skip` works while that card is the only one open. Your own text or tapback to the person takes the card back, and past `hold_hours` it expires.

Standing release lets a checked reply to one person go with no card, in live. It is off for everyone until you turn it on for a person, in your main room, through the `texting` tool's `release`, which takes only your own words from that turn; `open`, `close`, `knows` and `forget` change a sheet the same way.

Some things always wait for your word: health, medication, substances, faith, money, job, dating and location. A reply that touches one is held for a card unless that person's sheet opens it (`open = ["location"]` in Beta's sheet lets a reply to Beta say where you are).

It never brings up anything of yours the thread has not, never says what it is (a draft that names an assistant, or a name in `[texting] never_say`, is held), never answers anyone who is not on the list, and never texts from dry. A photo in the texts being answered (up to four) is converted on the Mac and shown to the writer's call, and is never stored on the box; any other file in the thread, a video, a voice message, a sticker or an older photo, is named and not opened. The check is not shown a photo, so it holds a reply that says what one shows: that reply waits for your word.

To see what it did: `yerk status` has two texting rows, the bridge and the last text in, then the last text out with how many are held and unseen, or, when the sender's last pass is older than a minute, the time it stopped. `yerk doctor` is red for what keeps texting off, for live with no way to the Mac, and for a sender that stopped while yerkd runs. In your main room the `texting` tool reads a person's `sheet`, a day of their texts and decisions (`log`) and the newest reason (`why`), and your main room is told every turn what texting is and what a card is. The machine room gets one line a day after 8 in the morning, counts only: texts in, decisions by kind, held, sent or would-send, stopped because you answered first or they wrote again, unseen, and the longest run of texting's own sends to one person with no text of yours between. `yerk texting replay --since DAY` runs past threads through the writer and the check as of each cut and sends nothing: without `--run` it only prints the plan, `--person KEY` takes one person and `--limit N` the newest N cuts each. With `--sender` it calls no model: every burst since the day is timed as the live sender would time it, the thread is read as the sender reads it at each send time, and only counts are printed; `--of FILE` keeps the bursts whose reply passed the check in that finished run.

To switch it off, set `mode = "off"` and restart yerkd: what a live run left to send is dropped, never sent. `text-out` in `[gates] off` stops every text from yerkd's next start, one left waiting and standing release included.

## Needs that wait for a deeper check

The needs pipeline (decision 40, `yerk_ai/pipeline.py`) takes a need a room filed from its build to live with no person: built, the box's checks, one cold read, merged, deployed. A need whose change touches what can do the most harm waits instead, since review is matched to risk and the change sets the tier, never who or what built it (the rule the Claude Code team keeps for agent-written changes, started strict). When the cold read says `merge`, before anything is merged or landed, the pipeline reads the paths the pull request's head changes against its merge base with `origin/main`, with git in the daemon's own tree and no network (a rename counts as both its paths). One on the list, or a branch the need carries in a listed plug-in, holds the need: its line in the machine room opens "the cold read said merge; it waits for a deeper check" and names the first three things it touches with how many more, and `yerk needs list` shows the same why. The need's row in `<state>/needs.json` carries the hold in a field of its own, `deeper` (the head it judged, the paths, the plug-ins, and `unread` with git's words when git could not read the change, which waits too: an unreadable change is never taken as a safe one), so a program can find the needs that wait; any other stop of the need clears it. Every need is judged the same way, on the head its cold read read, so a fix worker's later commit on a listed path stops it too, and a need off the list travels exactly as before.

The default list is `SENSITIVE` in `yerk_ai/pipeline.py`, each entry beside what going wrong there means: `yerk_ai/texting/` and `yerk_ai/emails.py` (a text or an email goes out in your name that you did not approve), `yerk_ai/gates.py`, `yerk_ai/hooks.py` and `yerk_ai/deletes.py` (an action outside the box, money, a message, a post or a delete for good, runs with no hold), `yerk_ai/accounts.py`, `yerk_ai/git_askpass.py` and `yerk_ai/github.py` (a login or a token used where it should not be, or every room on a dead account), `yerk_ai/deploy.py`, `yerk_ai/pipeline.py`, `yerk_ai/needs.py` and `yerk_ai/workers.py` (Yerk changes or ships itself wrongly, or a worker leaves its sandbox), `.github/`, `pyproject.toml`, `uv.lock` and `units/` (what checks a change, what code is pulled in, what runs on the box), and `plugin:hands` (the hands plug-in drives your own browser). The list in force is the running daemon's, its own code and your yerkd.toml, never the pull request's tree, and the file that holds the default is on it, so a change cannot loosen the list that judges it. An entry is a path from the repository's root, a folder with a trailing slash (every file below it, never a longer name that only starts the same: `units/` does not take `units_old/x`), or `plugin:NAME`, an add-on with a git repository of its own by its server's name in rooms.toml. `[needs] sensitive = [...]` in yerkd.toml replaces the default whole (yerkd.toml.example writes the default out, to copy and change), and `sensitive = []` turns the wait off, the pipeline as before; the daemon reads it at its start. To release a need that waits, read its pull request, merge it on GitHub and run `yerk needs done DAY N PR`: the pipeline deploys it and says it is live as it does for any held need.

## A live page

A room with `page = true` in its rooms.toml table is also a browser tab, its live page, for work where typing, drawing and a test run are the conversation (teaching someone to code, say). yerkd serves it on its own local port, beside /mcp and /hook, and `yerk room page NAME` prints its address: `http://127.0.0.1:<port>/page#room=NAME&key=<key>`. The room and its key ride in the address's fragment, which a browser never sends; the page takes the key out of the address bar and sends it in the `x-yerk-secret` header on each of its calls. The key is minted once a room, a 0600 file in the state folder's `secrets/pages/`, which no room reads and no worker sees; it opens that room's page calls (`/page/stream`, `/page/event`, `/page/run`) and nothing else, and neither the install's secret nor a room's token opens them. `/page` itself is the same page for every room, with no room, key or data in it. Set `port` in yerkd.toml so the address stays the same across restarts; a tab reconnects by itself after one. On Windows with WSL, Chrome on the same machine reaches the box's local address. To open it on another screen, the Mac or a phone, the box's own tailnet address is used with nothing set (as `tailscale ip -4` prints it when yerkd starts; never a LAN address unasked, and `[page] listen = "127.0.0.1"` keeps the page on loopback alone), or set `[page] listen` to the box's tailnet address or its LAN one: yerkd then serves the page's routes on that address too, on its own port, and nothing else of its own (`/mcp`, `/hook`, `/control` and `/status` are not found there whatever secret comes), and `yerk room page NAME` prints the address with that host, the key still in the fragment (`--here` prints the box's own). It binds the address even before the box has it, as at boot before tailscale is up, so the page is there once it comes up; a wildcard, a public address or a host name is refused and the page stays on loopback. On the tailnet the page and its key are encrypted end to end; on a LAN they cross it in plain text, and yerkd's log says so.

The owner can also ask for the page in the room ("open my page"): the room's `page` tool with `open` turns it on with no restart, so no turn is cut, and keeps it on across restarts in the room's override (the daemon's own file in the state folder, over rooms.toml, which is never written); `off` turns it off the same way, its open tabs' feeds ending, and back on it has the same address. Then yerkd opens the page on the owner's screen itself, with the box's own opener: `[page] open` in yerkd.toml (a list, the address added last), else `wslview` or Windows' `rundll32.exe url.dll,FileProtocolHandler` under WSL, `open` on a Mac, `xdg-open` on a Linux desktop with a display. The address it opens carries a one-time ticket in place of the key (`/page?room=NAME&open=<ticket>`), since an opener's command line is readable by every local user: the page trades the ticket once, within a minute, at `/page/open` for its key and takes it out of the address bar, and a used or older ticket gets nothing. Nobody pastes the address, and no room ever holds it or its key. Where nothing opens it (a box with no screen, a failed opener), the page is still on and the room says `yerk room page NAME` on the box prints the address. On the Mac, ask for the page there ("open my page on my Mac"): the tool's `where` is then `mac`, and yerkd sshes to the Mac (`[page] mac`, else `[imessage] host`, else `ssh` in the `mac.json` beside an owner room's add-on's server, the hands plug-in's, read only from a file of yours no other user writes and none under the state folder) and runs `open` on the one-time address as the Mac reaches yerkd (`[page] address`, the box's tailnet or LAN host and port, else `[page] listen`'s address on yerkd's port, which unset is the box's own tailnet address as `tailscale ip -4` prints it at yerkd's start, since 127.0.0.1 on the Mac is the Mac), the address handed on ssh's input, so not even the ticket is on a command line; `pc`, the box's own screen, is the default. With the hands plug-in attached and Tailscale on the box, nothing is set: under WSL that is Tailscale inside WSL itself, or else `[page] address` names the Windows host with a port forwarded into WSL. What it lacks is said in words (no Mac named, no address, a Mac that does not answer). On the PC, a monitor named ("open my page on my middle monitor": the tool's `screen`, else `[page] screen` in yerkd.toml, left, middle, right, primary or its number from the left; middle is the centre one, of two the right one) takes the open: under WSL, Windows' own PowerShell opens the one-time address, carried in its environment and never on a command line, in a new window of the default browser (Chrome, Edge, Brave, Vivaldi, Opera or Firefox), moves it to that monitor, maximizes it there and raises it above the rest without taking the focus, having first woken the display with a display-required request and a still mouse event (no click, no key, the pointer unmoved). The tab then says when it has drawn a frame while it shows, which no browser does for a covered window or a screen asleep or locked, and the open waits 10 seconds for it: the room hears "painted" with the monitor's rectangle for a desktop screenshot, else that it is not painted and why, so it never reads an old frame as the page. A monitor that is not there, a browser it opens no window of, a window that never showed or a box that is not a Windows PC is said in words, and the page opens once at most, by the box's opener only when nothing opened yet. A tab keeps its room and key in its own session storage, never the address bar, the history or a bookmark, and they go when the tab closes, so a reload or a retyped `/page` in that tab opens the page again; a tab with no key says a line typed there reached no room and keeps the words in the box.

The page shows a program in an editor (`solution.py`) on the left, its unittest file (`test_solution.py`, which imports `solution`) on the right above the tests' result, a scoreboard along the top, a hint card under the program, and the chat, a pane of its own, on a dark theme. The chat holds the whole conversation, so a night on the page needs no Discord open: the owner's lines and the room's replies, notices and sends, each time-stamped, the newest at the bottom (the column stays where the owner scrolled, with a button to the newest), and each reply shown the way Discord shows it, since yerkd reads every line said into parts beside its words (bold, italic, underline, strike, a spoiler, code and a fenced block in a box of its own, a heading, subtext, a quote, a list item, a blank line a gap between thoughts, a link only to http or https opening in a tab of its own), drawn as elements with every word as text. Its newest 200 lines are kept in `work/page/chat.json`, so a reload or a restart shows them again. The say box takes many lines (Enter sends, Shift+Enter a new line), keeps the focus after a send and puts back words yerkd did not take; the grip between the code and the chat drags it wider or narrower (a double click evens them, the arrow keys move it), and `wide chat` and `wide code` set it in one click, the browser keeping the split; on a narrow screen the chat goes under the code. A whole-line `#` comment the owner types in the program is talk too: it is a line of theirs on the chat, one still being typed growing its own line, and goes to the room as said, beside the typing's diff (`yerk explain page-chat`). What the owner does there reaches the room as the owner's messages, folded into a running turn as a Discord message is: each keystroke is a line in the room's `work/page/events.jsonl` at once (its line and column, what it took out and what it put in), and the program and its tests are kept whole beside it, so the room reads them mid-turn; once the typing pauses for 1.5 s one message goes, `[from the owner's live page]` and the change since the room last heard as a diff, with the tests' newest result when it says something new. A stroke on the draw layer (the lines of the program or the tests it covers, its points in the file), a line said in the box, the countdown's end and a stall go at once. Each message is ledgered and in the day log as a Discord message is; one a restart cut short is closed, not run again, since its keystrokes are in the file. With the chat closed to nothing (the grip dragged to the edge, `close` on the chat, or the room's `page` tool with `chat` "closed" on the owner's ask; `chat` on the bar, or the tool's `chat` "open", brings it back) the talk lives in the program: a # line ended with Enter goes at once, and the room's replies, notices and sends that answer a message from the page come back as bubbles between the editor's rows under the line asked from (the # line said last when the message named none), never written into solution.py, a typing mark there until the turn ends; Ctrl+Enter on a line or a click on its number asks about it, a red test tile about that test, its answer under the line with the chat open too, and both editors colour Python, the owner's own # lines in their own colour; what the room says in any other thread (an answer on Discord, a job's post, a scheduled note's, a worker's end) stays on the chat alone, kept for when it opens (`yerk explain page-talk`). The room's switch is the buttons' own: every open tab shows it at once (an opened chat at the width it had) and keeps it in the browser's split, posting nothing back; yerkd keeps it across a restart, so a tab that opens later shows it too, and a word other than "closed" or "open" is refused in words with nothing drawn. The room is told in its next message when the owner closes or opens the chat, never of its own switch, nor of an owner's switch it undid before it heard.

The tests are the page's, never the model's: every pause in typing runs them on the box in a fresh folder under `python3 -I`, capped at 10 s of wall clock and 1 GB of memory and killed past the cap, and each test comes back red or green with its message and the line it failed at, or the syntax error that stopped them loading with its line. The room's replies, its notices and its sends to itself render on the page beside Discord, and its `page` tool draws: a new program or tests (run at once, their result in the tool's answer), marks on lines (a highlight or an arrow, each with a short note), a hint, the bar's labels and values (a rank, points, a streak), a countdown, the stall wait (seconds of no typing before the page tells the room) and the chat, closed to nothing or open (`chat`, on the owner's ask). The room sets only the words; the look is the page's, the same in every room. yerkd reads the bar's words as a scoreboard: a tier word, Iron to Challenger, with its division or none ("Gold II"), or any value under a rank label, is a rank badge in its tier's colour; N/M, N of M, N% or a number under LP or before LP is a bar filled that far (LP of 100); a number is big, a signed one green or red; anything else stays words. Each cell is a box of its own in a row with its own gap, its label over its value, so a room never pads its words to keep them apart: yerkd keeps the bar's words alone (a run of spaces of any kind, a no-break one too, is one space, and none is kept at either end), drops a cell left with none, and the tool's answer says when it did (`yerk explain page-cells`). The countdown is a clock, amber in its last minute and red in its last 10 s, each test a green or red tile that pops when it flips, and every word goes on the page as text, never markup (`yerk explain page-look`). The rules of a game played on it, what a hint costs or when to nudge, are the room's to write; the page carries what happens, both ways. `yerk explain live-page` has it all.

## Web reach

Rooms read pages and search the web through one plug-in, `plugins/web` (`yerk-web`, an MCP server in JavaScript with its own package.json and tests), outside the harness: it is not in budgets.toml's [code] count, and the harness's only part in it is the ledger's `spend` table and the morning diff's spend line. A room attaches it with an `mcp` table and allows its five tools, and `[defaults]` in rooms.toml does both for every owner room at once (rooms.toml.example's `[defaults]` has both, commented):

- `web_fetch(url, max_chars?)`: the fetch ladder. Free rungs on the machine first, each only when installed and skipped without a try when not: F1 a plain fetch with browser headers, F2 the machine's own stealth browser (CloakBrowser, or Chromium with playwright-core), F3 trawl's captcha-solving browser. Then Browserbase, paid, with its key: L1 Fetch, L2 Fetch with proxies, L3n a browser session without proxies, L3 one with proxies, captcha solving and a saved login per site. Every read passes the same blocked-page check; a page that stays shut comes back named by its wall (login_required, captcha_unsolved, geo_blocked, http_404 and the rest) with every rung tried. Since Claude Fable 5.2 shipped (2026-11-09), a room's checks follow the model it runs. Every room reads the general guide, the Fable family page (the only page that holds the memory recipe) and code-memory. Beside them, each room reads its own model's prompting page, named by the model's id: `claude-fable-5-2` reads `prompting-fable-5-2`, `claude-opus-5-5` reads `prompting-opus-5-5`. The shared rules store and the write gate read the pages of every model any room runs, since every room loads the store, and each doctor finding names its page. A model a room runs whose page `yerk docs refresh` does not fetch is a doctor line and a need naming the page to add, so a model shipped later cannot leave the checks behind. The 5.2 page adds four checks. An absolute rule (never, always, must not) says where it applies and why, and writes the go-ahead or case that lifts it into the same rule, or says that nothing does ("Be explicit about exceptions."). A rule that requires asking first names the exact actions it covers. A line telling the model to think less, or to write its reasoning into the reply, is refused with the fix to remove it. A hard number of lines, sentences or words is counted in `docs/shape/lessons.md` and never refused, since it is often the owner's own preference; the gate asks it only for its reason. The 40-word sentence cap left the gate, since the 5.2 page says a hard sentence limit makes prose choppy, and the 5.1 density note binds a 5.1 room only. The mechanics say the page's finishing, opening-and-recap and communicating-clearly blocks in their own voice and name the steps that need no approval. A resumed session keeps the system prompt it began with: each session's start file is kept by its id beside `assembled.jsonl`, a resume or a compaction's copy is given it, and every change since rides the newest message as `Rules changed since you last looked:`. On 5.2 the API checks that prefix for every account, and a changed system prompt makes the thinking after it invalid ("Make these changes in new conversations only.").

**Upgrading:** yerkd.toml gains an optional `[docs]` table: `pages` (slug = URL, replacing the default list whole), `refresh_days` (1), `fetch` (true; false and the doctor never fetches), `topics` (name = regex, added to the shipped topic map) and `acronyms` (words of four or more capitals that are names, not shouting). budgets.toml gains `[shape]` (every threshold 0). The memory index takes `<state>/docs` as a new root at its next start, so every file is chunked again once; run `yerk docs refresh` once to fetch the pages before the doctor's first run.

## Ledgers

One SQLite file, `ledger.sqlite`: `turns` (account, models, time to first visible event and to the end, how it ended, which messages it answered), `inbound` (every channel message by its id, written before anything runs; a crash runs it again once, marked), `outbound` (every message posted, with the id the channel returned, and a card's text at each post and edit, so a card the reply replaced can still be read back), `holds`, `health` (the daily call per account: pass or fail, login method, an identity fingerprint, never the email), `spend` (one row per paid call a plug-in makes: room, tool, engine, US dollars; the morning diff's spend line), and beside them `deliveries`, `attachments`, `cards`, `workers`, `job_runs`, `evidence`, `shadow`, `gates`, `approvals`, `hook_calls`, `tool_times`, `tamper`, `stalls`, `deploys`, `calls` and `message_links`. A turn row also names the failure's source in the table and the hop that brought the turn to its account.

## Files

- `budgets.toml`: every size limit, in characters as Claude Code counts them
- `failures.toml`: failure classes and what each one does next
- `units/`: yerkd's service, the memory index service, the timers of the daily jobs (backup, retention, doctor, curate, morning, health) and the weekly recall bench timer, each in docs/units.md (copy and enable them yourself)
- `abilities.toml`: every ability, what it needs and its cost tier (free, key or paid), with the free path
- `rooms.toml.example`, `yerkd.toml.example`, `accounts.toml.example`: templates for your private folder
- `yerk_ai/lifted/`: code taken from other MIT projects and from the author's own tools, each file with its origin; see `NOTICE`
- `yerk_ai/channels/`: channel adapters (Discord)
- `plugins/web/`: the web plug-in ("Web reach" above), outside the [code] count
