# Yerk AI

Yerk AI turns chat rooms into long-lived Claude Code sessions. It is a small Python program that does only what Claude Code does not do by itself: carry messages between a room and a session, build each room's context to a declared size, keep memory across sessions, and move work across the accounts you already have. The agent loop, tools, skills, compaction and resume are Claude Code's own, used through its documented flags, settings and hooks.

## What it is, and what it is not

- A personal tool. You run it on your own machine, for yourself.
- Bring your own installed Claude Code. Yerk AI starts the `claude` command you already have, under the login you already made with it. Each account is just a Claude Code config folder named in your own `accounts.toml`.
- No login handling for anyone else. Yerk AI never offers, brokers or copies a login, and it never reads the credential files in a config folder (a test greps the package for any read under one). One thing touches your own credentials, and it never prints or logs one: a one-year token you minted yourself with `claude setup-token` can be kept in your private folder (`secrets/claude-<account>.token`, 0600) and is handed to Claude Code in `CLAUDE_CODE_OAUTH_TOKEN`. The usage meters in `yerk status` come from the usage events Claude Code itself prints in each room's stream. It never writes a config folder.
- Nothing stored for anyone else. Persona, memory and room settings live in a private folder you keep outside this repository; the repository ships only a fake example of it.

## Status

Layer 5, run 3: watchers, one heavy worker per account, worker tools and the relay's edge cases. A `watcher` job (`kind = "watcher"` in `jobs.toml`, with `command`, a `prefix` or a `regex`, `batch`, `lines`, `wake` and `prime`) runs its command all the time under its own systemd service, restarted with a backoff when it ends; matching output lines are events, every other line goes to the unit's log, the very first start primes (what is already there is history), a line seen before never wakes anyone again, and each event is a ledger row that wakes one turn (the room's own when the room is idle, or a worker) and is marked handled only after that turn ends clean: a crash replays it once, never twice, and a worker the owner stops ends its event with no replay and no alert. Workers wait in line for their account (`[workers] per_account`, default 1), the card saying "waiting for an account" and the place, and the daemon starts the next when the account frees; `yerk status` shows the line. A worker gets no Yerk AI tools unless `[workers] yerk_tools` names the read-only ones (`recall`, `read_memory`), which come from its own stdio server that has no `send`, `worker` or `schedule` to give. A relay waits for an idle room (the card carries the result meanwhile), runs as a turn of its own (two completions are two relays, in order, never merged), and resumes the room's own session when the room's process is closed, as any message does, never a fresh one. A job's failure in a room reads "job NAME failed: it ended with an error" or "job NAME stopped: timed out at 10 min"; the exit code is in the run's ledger note and `yerk status --full`. A worker that moves account mid-run is not built.

Layer 5, run 2: scheduled jobs and the typing signal. The owner's timed work comes from one private `jobs.toml` (the example with placeholder values is `examples/private/jobs.toml`; `yerk explain jobs` describes every key from the code): a job is a `script` (a shell line run inside its unit under an account-free environment, with a cap) or an `agent` (a worker with the message as its brief, the job's account and cap, its card in the job's room), on one of three schedules: a cron expression with an IANA `tz`, `every` (an interval) or `at` (one time, removed from the file after it fires). `yerk jobs sync` generates one systemd user timer and service per job, idempotently (unchanged jobs untouched, changed ones rewritten and restarted, removed ones disabled and their files gone), prints the diff and then every next fire time read back from systemd, naming any job that cannot be scheduled with why; `yerk jobs list` is the read-back, and `yerk status` lists the jobs with their next fire from systemd, never from memory. Timers carry `Persistent=true` and `AccuracySec=1s`, so a missed run fires once on return and a one-shot lands on its second. A run delivers by the cron-wrap rule: exit 0 with output posts the output to the room, exit 0 with nothing posts nothing, a failure or a timeout posts one alert line to the ops room (`[jobs] ops_room` in yerkd.toml, else the job's room); an agent job's last message is told by the room's own session through the same relay as a worker's, and a last message of exactly `NO_REPLY` is silence. Every run is a row in the `job_runs` ledger (planned and fired times, how it ended, what was delivered or why nothing was). The `schedule` tool in every room and `yerk schedule` add a one-shot or a recurring job, remove one or list them, writing the file and syncing, and answer with the next fire time read back; a missing zone is the room's configured one, never UTC by accident. The Discord adapter now sends the typing signal from the moment a message is taken until the first card post or the reply, refreshed every 8 seconds while nothing is visible and never once a card exists; it is not a delivery and is ledgered as nothing.

Layer 5, run 1: workers. Heavy work leaves the room: `worker` (a tool in every room) and `yerk worker start|list|stop|report` run a headless `claude -p` as its own systemd transient unit `yerk-worker-<id>`, which outlives the daemon: one named account (its token file is the only one the unit's environment names, read inside the unit the way a room reads it), a brief, a staging folder with stdout and stderr in it, a report path, a TASKS.md and a cap (65 minutes unless the call or `[workers]` in yerkd.toml says otherwise), no MCP server and no subagent tool, so no worker starts another. Its card in the room shows the start and the cap and ticks a row per TASKS.md line as the worker ticks it (an inotify watch on the folder, at most one edit a second). When the unit ends, its ExecStopPost record settles the card with the report's first line, the report path and the exit state (done, died, timed out, stopped, lost); when the room is idle (no human message for 60 seconds and no turn running) one relay turn in the room's own session says the outcome in its voice under 1,500 characters with the report path, and a message landing during it is answered inside it; otherwise the relay is skipped and the ledger says why. The `workers` table in the run ledger keeps every worker; `yerk status` lists the running ones checked against the unit list; a daemon restart re-attaches from both, so no card is orphaned.

Layer 4, run 1: memory, the foundation. Every message of every room is filed in the day's log in the private memory tree as it lands (attachment-only and one-character ones included, one line per attachment, never twice for one message id). `yerk-index` keeps an FTS5 index over that tree in its own process (`units/yerk-index.service`), writing only the chunks that changed, with `yerk-index --check` comparing it against the disk and telling a timeout from a failure. Rooms get `recall` and `read_memory`; `yerk recall-bench` runs a fixed question set from the private layer against the index (weekly, `units/yerk-recall-bench.timer`). Each ability and its cost tier is in `abilities.toml`.

Layer 4, run 2: recall before the first word. `yerk-index` also builds a name index from the fact files and the curated file's headings whenever one changes; the prompt hook puts the entries for the names a message mentions, then the room's own lines of the last 14 days on the message's topic, in front of the model before it starts (at most 1,500 characters, `budgets.toml` `[per_message.on_hit]`), and writes what it assembled, part by part, to the room's `assembled.jsonl`. The session-start recall pack is the room's own filed items of the last 14 days (what the owner sent, decisions, drafts), newest first, up to 6,000 characters with the open commitments, and a SessionStart command hook adds it again after every compaction (`yerk room compact ROOM` asks for one). Every tool call is ledgered with what it read, and a rule check after each reply logs, in shadow, a quoted figure or file the turn never read and a "what did we decide" answered with no memory read. `yerk-index --rebuild` builds a new generation and swaps a link, so recall never fails during a rebuild.

Layer 4, run 3: meaning search behind the keywords. With a provider key in the private folder (`secrets/openai.key`, or where `[memory] embeddings_key` in `yerkd.toml` points), `yerk-index` embeds every chunk once (OpenAI `text-embedding-3-small` at 256 dimensions, changed chunks only, the vector stored next to the chunk's hash and copied across a rebuild), backfills the tree in the background, resumable and in batches with a gap between them, and serves the search on a local port; `recall` fuses the meaning rank with the keyword rank by reciprocal rank fusion, its answer shape unchanged. No key: keywords only, exactly as before, and the room is told once in one line. A provider timeout or error: keywords only for that query, logged, told apart from a failure of the index. `yerk abilities` lists every ability as 🟢 on, 🟠 needs a provider key, or ⚪ on its free path, and `yerk explain NAME` answers from `abilities.toml` (what it does, needs and costs, the free path). The example question set (`examples/private/evals/recall-questions.json`) carries the two room-recall kinds: what was sent in a room recently, and what was said there on a day.

Layer 4, run 4: recall moved from its misses. The bench grew from 46 to 164 scored questions (13 controls) in eleven kinds, and the misses were read by reason before anything was tuned: 13 of the 14 paraphrase golds sat outside the chunk vector's own top ten (a chunk vector averages several unrelated lines), and 5 keyword hits at ranks 2 to 6 were lost in the merge (under reciprocal rank fusion with constant 60 a lone rank-2 hit scores 1/62 and loses to any chunk both searches place anywhere in their pools). So `yerk-index` now embeds every line of a day log and every bullet of a fact or topic file on its own (a units table beside the chunks: 20 characters or more past the bullet, one vector per distinct text, shared with a one-line chunk, filled for an existing index on first start, written and dropped with its chunk, copied across a rebuild), serves the line vectors and the chunk vectors together (`[memory] embeddings_units`, measured best as `both`; `lines` or `chunks` alone are the alternatives) from a blocked float16 store that grows without copying itself (`[memory] embeddings_width` narrows it; 128 dimensions was measured and lost), and `recall` fuses with constant 20 and holds each search's own first hit in the top six. A source prior for fact and topic files over day logs was built as a boost and measured at 0.15, 0.3 and 0.5: every value lost on both rates, so it ships at 0. On the 164-question set: top six 66.5% to 71.3%, top one 37.2% to 36.0%, paraphrase 0 to 3 of 14, correction 12 to 15 of 15. The targets (75, 40, paraphrase 50) are not met; the remaining paraphrase misses are the embedding model's, 9 of 14 golds sitting outside the line vector's own top 50 on questions built to share no word with their line. The line backfill took 5 minutes and about 10.4M tokens; the index process serves 342,800 vectors at about 260 MB resident.

Layer 6, run 1: the rule-based gates. Every Claude Code hook a room uses posts to the daemon (UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, Stop and ConfigChange over http; SessionStart through curl, the one way Claude Code runs it), and `yerk_ai/gates.py` decides by code, so its gates block. A plain `rm` or `unlink` (with -r too) is rewritten to the trash command with the same paths and runs; a delete in any other shape is refused with the trash line for the model; the room hears nothing unless the trash fails. Shell text is read quote-aware first: quoted text, heredoc bodies and a word in a sentence are not commands. A command on the hardline list (from Hermes Agent) never runs. A write to yerkd.toml, rooms.toml or accounts.toml, or a restart of yerkd, is refused with one line while a person is mid-conversation or the memory index rebuilds. An external action (a send to another room, a public post, a login, money, a message out through another tool, or a rule under `[gates.external]` in yerkd.toml) is held with one line until an approver says `approve` in the room, then that same call (its normalised text and folder) runs once and any other is held again; the word counts only from a message the room itself wrote into its running turn, under the room's bound session (/hook has no secret yet); hold, word and release are ledgered. A working turn that ends with nothing in the room bounces once, naming the message it owes, and never when a part already landed under the turn's key; a session that replaced another posts a reset line; a changed settings file is a tamper row (who, what, when, the diff's hash, from line hashes, never the text). The evidence ledger gains each call's time and failure, and every hook call's own time is a `hook_calls` row, so `Ledger.hook_overhead` is the overhead per turn against the 150 ms bar at the 95th percentile. Decision 25 runs in shadow: a sentence claiming what code does or lacks, what is running, a decision or a file's contents, with no test run, status read, memory read or file read behind it in the turn, is ledgered with the sentence and the tools the turn ran. The five judge-model reply gates are not built; none may block until it shows under 1 in 10 false alarms on 100 cases with a known-good control passing. A room gets tools beyond Read through `allow` in rooms.toml (permission rules), and the gates still run first.

Layer 7, run 1: the status socket and card, the watchdog beat, the morning diff. The running yerkd answers `POST /status` (local only, like `/hook` and `/control`) with the rooms that have a turn in flight and since when, the workers and their caps, the jobs due within the hour (from systemd), each account's 5-hour and weekly meters with reset times and the reading's age, the memory and CPU of the daemon and of each open room's process tree (from /proc), and today's stalls; `yerk status` renders it as a phone-width card (every line 40 columns or less, state first, a red or orange dot only for an account at or near its limit, a room busy past 10 minutes, a worker whose unit is gone, a stall today or a daemon down; every other line a dash), and with no daemon answering says so and shows what the files hold. A loop task sets a mark every second and a thread beside the loop beats systemd's watchdog only when the mark moved (`sd_notify` through Hermes' `gateway/systemd_notify.py`, lifted whole, 119 lines, MIT); once the loop is more than 2 s late the thread writes a dump of the loop thread's stack, the asyncio tasks and /proc for the daemon's threads and each room's processes under `<state>/stalls/` (never in the memory tree, checked), and when the loop runs again a `stalls` row in the run ledger (when it began, how late, what the loop was running). `units/yerkd.service` is the example unit, `Type=notify` with `WatchdogSec=30`. `yerk morning` (`units/yerk-morning.timer`, 06:30) writes, a line each, every room's payload against the last delivered diff (a planted change shows up as its part and size), yesterday's messages, queue wait and time to the first visible line, stalls and shadow-gate flags, memory and CPU per unit, and the meters, and posts it through the daemon to the room with `role = "machine"` in rooms.toml, which refuses any other room; with no such room it is written under `<state>/morning/` and one line says where. A finding the last delivered diff lacked opens the diff as an alert, a detector that could not run says unknown, and nothing is stamped until the diff is delivered, so a failed post shows the change again. 503 new lines outside tests and the lifted module (status 177, beat 112, morning 117, 97 in six existing files), 12 new tests, 437 in all. Left for run 2: `yerk deploy` with its proof card and rollback, the Claude Code upgrade drill, message-first dead-turn detection, and the first week of stall counts and morning posts against the acceptance list.

Layer 7, run 2: `yerk deploy` with its proof and rollback, dead turns found from the message, and run 1's leftovers. `yerk deploy [REF]` records the commit the running yerkd reports, moves the branch checked out in the daemon's tree to REF by `git merge --ff-only` only when REF is ahead of both the running commit and that branch (a tree found detached stays detached), so the merge lane's next `git pull --ff-only` still works, runs the fast tests there (`--no-tests` skips them and the card says so), waits until no person's turn runs or waits, no room has had a person's message for `[deploy] quiet_seconds` (240) and the memory index is not rebuilding, and gives up after `cap_minutes` (60) with the checkout as it found it, restarts the unit, and proves it: the unit active, the channel connected, `/status` answering under the install's secret with the new commit and every room it served before. A failed proof rolls back to the recorded commit the same way, the branch moved back by `git reset --keep` (the card says what the next pull brings back), and the card says both; a rollback that never gets a quiet moment says why and leaves the daemon and the checkout on the new commit, a `gave up` row; the card goes to the room with `role = "machine"`, else to the terminal. Every deploy and rollback is a row in the ledger's `deploys` table with the commit before and after, the outcome and how many people's turns the restart left open (it must be none). `/status` now carries the running commit, whether the channel said connected and whether the memory index is rebuilding, READY=1 goes out only once the HTTP port listens, and the beat times a hold by the probe a thread puts on the loop every tenth of a second (a 3 s hold is written 3.0, not 2.5) and owns the old 250 ms log line. The morning diff gains dead turns: every person's message in the last 24 hours with no reply part under its turn's key and no visible notice or file linked to it, older than ten minutes, counted with its rooms and the newest one's time; a changed set is a new finding, said once, and with no yerkd answering the line says unknown. The card cuts a long name and never the fact after it, job failure alerts go to the machine room when there is one, `units/yerkd.service` gains `MemoryHigh=2G` (five open rooms at 350M each plus yerkd; past it the unit is slowed, never killed) and `MemoryMax=4G` for a leak only, and `yerk drill` is the Claude Code upgrade drill. Proven live on a second daemon under its own unit: moved from `systemd-run` onto the unit file and deployed, then a planted commit whose channel never connects, rolled back.

Room settings: a room's model and thinking level, changed from the room in plain words. The `settings` tool (in every room; only a room whose privacy is owner may use it, any other hears one line saying only the owner's rooms can change this, and the room is known by its process's token, never by an argument) takes a model, an alias or a full id from `[models]` in yerkd.toml (alias = full id; the list ships in the package as `models.toml`, naming claude-opus-5-5, claude-sonnet-5-5, claude-haiku-5-5 and claude-fable-5-1, and `[models]` in the private yerkd.toml replaces it whole: edit it when Anthropic ships a new model), and a level, low, medium, high, xhigh or max (Claude Code's `--effort`); `default` for either goes back to rooms.toml, and anything else is refused with the list. It answers at once with one line ("next reply: Sonnet 5.5, low thinking") and writes the daemon's own override, `<state>/rooms/<room>/override.json` (0600, created with its mode; `settings.json` beside it is Claude Code's), which is read wherever the room's spec is built, over rooms.toml, which is never written, and survives a restart. It never lands mid-turn: the running turn ends on the model it began on, a hop or a retry inside it included; then the room's process closes and the next message starts one with `--resume` of the same session and the new `--model` and `--effort`, so the conversation carries on (a resume that fails takes the fresh-session fallback and its recap line, unchanged). `yerk config get room NAME` shows the room's model and effort and where each comes from. An override value that is not on the list or not a level (a hand-written file, or a model taken off the list since) is ignored with one log line, rooms.toml's value is used, and `config get` shows it as ignored. A switched-to model that turns out not to run (model not found) is dropped from the override: the room hears one line naming it and the model it is back on, and the next message resumes the same session on rooms.toml's. A turn that crashes after a switch still lands it at its end. Measured live on one account: a turn on claude-haiku-5-5 called the tool itself when asked for Sonnet at low thinking, and the next turn's init event named claude-sonnet-5-5 with the session id unchanged, about 4 cents in all. A worker's relay that has no report file now carries "no report" with its command, never "report saved". Against main at 1c0ce48: 149 new lines outside tests (config 37, daemon 32, room 36, words 17, cli 15, mcp_server 9, workers 3; 12,044 against 11,895), 9 new tests, 532 in all.

Slash commands: `/model`, `/effort`, `/new`, `/stop` and `/status` on the rooms' own Discord bot, each the daemon method the room's tool or `yerk` command already calls, so there is no second path. On connect the daemon registers exactly these five on each guild its rooms live in, one bulk overwrite per guild that replaces whatever the application had there (guild commands show at once; nothing is ever registered globally); `[discord] commands = false` in yerkd.toml registers and answers none and leaves the application's commands alone, so commands an earlier start registered stay listed in those guilds, unanswered, until a start with them on overwrites them. Only the owner (`[discord] owner`) is answered, and only in a room: anyone else, or any other channel, gets one line. With `[discord] owner` missing or not an id (a bool, a float, other text), the Discord side still starts and serves its rooms, no person's message is answered, every command answers one line naming the setting, and the log says so once at start. Every answer is ephemeral, seen by the owner alone; a call still running after 1 second is deferred first (Discord shows it thinking) and answered when it ends, so nothing misses Discord's three seconds. `/model` and `/effort` offer the models list (its aliases and `default`) and the levels (low, medium, high, xhigh, max and `default`) and call the settings tool's own method, so a switch lands between turns on the same session; with no choice they say what the room is on now. `/new` starts the room's next message in a fresh session with the room's recap line (the last reply's first line), kept in the daemon's own `<state>/rooms/<room>/fresh-next` so a restart before that message keeps it; memory stays, since every start carries the session-start pack, and the room is not told the last session could not go on. `/stop` ends the running turn now: only the live process is signalled (TERM, then KILL after 5 seconds), the turn is never rerun, hopped or retried fresh (a /stop between two of its runs, an account hop or a rerun's wait, starts no further run, writes nothing again and ends the wait at once), and its messages are ledgered `stopped`, so a restart does not run them again; the next message resumes the same session. `/status` is the phone-width card `yerk status` prints, from the same /status. Proved offline with fake interactions; the merge lane proves it live. Worker sandbox: a worker cannot reach the files a gate on tool calls cannot see. Its unit gets `PrivateUsers=yes`, `ReadOnlyPaths=` the state folder, `ReadWritePaths=` its own folder (and its account's config folder when that lives under the state folder, since Claude Code writes its transcript there) and `InaccessiblePaths=` the install's secret and `<state>/rooms` (each room's mcp.json, its settings with the hook header, its override.json and its work folder, so a worker writes in its own folder, never in a room's), all set by systemd itself, so no tool or shell shape gets around them. The worker secret stays readable for a worker's own recall and read_memory. The daemon creates `<state>/rooms` at start, so both hidden paths exist before the first unit. sessions.json keeps a SHA-256 of each room's token (`token_sha256`), never the token: the daemon hashes the caller's value and compares in constant time, a table from before is rewritten with hashes on its first load, and every write hashes any plain token first, so a copy of the file opens nothing. Only a room whose privacy is owner may use workers: any other room's `worker` call (start, report, list, stop) and `schedule` add of any kind but script gets one line, "only the owner's rooms can use workers", and nothing starts; an owner room starts a worker or an agent job for itself only. `yerk worker` and the job runner, through /control, keep every form for any room. Against main at 007e523: 79 new lines outside tests (engine 35, daemon 22, workers 20, words 2), 3 new tests, 552 passing and 2 skipped in all. Left for a later run: a script job from a room that is not the owner's still runs its shell line as the owner's user, outside any sandbox, and a live worker run under the new properties.

Layer 3, run 1: delivery and the visible turn. Every turn has one card built from Claude Code's stream (its newest words, then one row per tool call naming the file, command or host, ticked or crossed), replaced by the reply or kept to say what was owed. Every outbound part has an idempotency key in the delivery ledger before it is posted, so a crash between producing and confirming a reply redelivers it once, labelled, and never twice. Files go out on one checked path with the message id recorded and a visible notice on any miss; files sent in are staged under their own names, and an image the model never opened is bounced back once.

Layer 2, run 1: the accounts as one engine (the failure table with a test per Claude Code error type, cooldowns per account and kind, the hop that continues the same turn, one-year token plumbing, the daily health call, the meters). Layer 1, run 3: one Discord test room answers through Claude Code. Measured there over 50 scripted messages, 10 of them sent mid-turn: none dropped, every mid-turn message answered inside the turn it landed in, first visible line 1.7 s and final reply 3.7 s at the median. Built so far: the room runner (the mid-turn fold, idle close and resume, the empty retry, the account hop), the Discord adapter, Yerk AI's MCP server with `send` and `hold`, the HTTP hook with the clock line, read access to each room's private folder, and the ledgers.

## Use

```
uv sync
uv run yerk map example-room                 # the example room's context, part by part, against budgets.toml
uv run yerkd                                 # every room with a discord:<channel id>, through the Discord adapter
uv run yerkd --console example-room --config-dir ~/.claude   # one room on the terminal: a line in, a JSON reply out
uv run yerk map example-room --wire          # also the sizes as sent, read from the room's Claude Code transcript
uv run yerk setup-room ROOM                  # a Discord room's test webhook; its URL goes to secrets/ (0600), never printed
uv run yerk room close ROOM                  # the running yerkd closes ROOM's process now (never mid-turn); the session stays
uv run yerk accounts                         # per account: order, token age and days left (warns inside 30), rests, last health call
uv run yerk accounts cool NAME MINUTES       # rest an account by hand; `clear NAME` lifts it; a running yerkd sees both at its next pick
uv run yerk accounts mint NAME               # `claude setup-token` for NAME: the browser flow shown, the token stored 0600, never shown
uv run yerk accounts token NAME              # or store a token from stdin (never echoed), 0600, issued today
uv run yerk accounts health                  # one tiny model turn per account and its login identity, a ledger row each
uv run yerk status                           # the card: what runs, the meters with resets, memory and CPU, today's stalls
uv run yerk morning                          # the morning diff to the role = "machine" room (units/yerk-morning.timer: 06:30)
uv run yerk deploy [REF]                     # REF onto the running yerkd: fast-forward only, fast tests, a quiet room, proof, else rollback
uv run yerk deploy --unit                    # the same, moving a systemd-run yerkd onto units/yerkd.service (Install below)
uv run yerk drill --config-dir DIR           # the Claude Code upgrade drill: the version, hello, fold and resume on one account, a verdict
uv run yerk probe hello|fold|resume|blocks|smoke|measure|check|idle --config-dir ~/.claude
uv run pytest
```

- `--private DIR` or `YERK_PRIVATE` points at your private folder (default: the fake one in `examples/private/`).
- `YERK_STATE` sets the state folder (default `~/.local/state/yerk`): the room-to-session table, session locks, the ledgers, cooldowns, logs.

## Install as a service

`units/yerkd.service` runs yerkd under systemd with `Type=notify` (a start counts once READY=1 says the port listens), `WatchdogSec=30` (the beat stops when the event loop stops, and systemd restarts it) and `MemoryHigh=2G` with `MemoryMax=4G` (raise MemoryHigh by 350M for each room kept open past five). Copy it to `~/.config/systemd/user/`, set `YERK_PRIVATE` and `YERK_STATE`, and `systemctl --user enable --now yerkd.service`. A yerkd started by hand with `systemd-run --user --unit=NAME` moves onto it with `yerk deploy --unit` (`[deploy] unit = "NAME"` in yerkd.toml): the unit's command (read word by word from systemd's bus), folder and environment go into the file under the same name, written 0600, and the file unit starts at the next quiet moment; a failed proof puts the transient unit back. After that `yerk deploy` restarts it in place. `[deploy] tree` names the daemon's checkout (default: the unit's working folder), `tests` the fast subset (default `tests/test_scrub.py`, `test_budget.py`, `test_card.py`, `test_style.py`), and `proof_seconds` how long the proof may take (60).

## The private folder

- `rooms.toml`: one entry per room: channel (`discord:<channel id>`), account order, model, tool allowlist, privacy class, time zone, and the context files. `layer` names the folder those files come from (default: the private folder itself).
- `accounts.toml`: one line per account: `name = { config_dir = "...", order = 1 }`, optionally `token = "secrets/..."` (the default is `secrets/claude-<name>.token`). Adding or removing an account is that one line; a room's own `accounts` list only orders the accounts it names, the rest follow.
- `yerkd.toml`: the daemon's settings: the Discord token file, the owner's user id, webhook ids accepted as senders in test mode, the local port. A running `yerkd` writes its pid and port to `yerkd.json` in the state folder.
- `secrets/`: files only you can read (mode 0600), for example the bot token. Nothing in the repository reads them except the daemon at start.

## How a room runs

One `claude -p` process per active room, stream-json in and out, with:

- `--session-id` on a session Yerk AI minted, or `--resume` on the room's own session; one live process per session, by lock file
- `--setting-sources ""` and `--settings`, so only the settings Yerk AI writes apply: a Read rule for the room's folder and the `UserPromptSubmit` hook, `type: http`, posting to the daemon
- `--add-dir` on the room's folder; every part of the appended context starts with `[from <absolute path>]`, so the model can re-read the file a fact came from
- `--mcp-config` naming only Yerk AI's server, with `alwaysLoad: true`, and `--strict-mcp-config`; a `--tools` allowlist; `--model`
- `--append-system-prompt-file` with the assembled context, built to the sizes in `budgets.toml`

The room runner:

- A message for an idle room starts a turn. A message that arrives mid-turn goes straight to the process's stdin and is answered inside the same turn; the replayed copy (`--replay-user-messages`) is the proof it was accepted.
- Only the final text after the last tool call is delivered. A turn owns one progress message, edited with its first visible line, then replaced by the reply, split under the channel's limit and never inside a code block.
- Files go out on one path, up to what the bot can send (measured: 20,971,520 bytes, Discord's own answer, above discord.py's 10,485,760 for a tier 1 guild). A file a crash left unconfirmed is sent again from its outbox snapshot, labelled, unless the room already shows it; the message runs again told which files are in the room.
- An edit of a message still waiting revises it before it runs; an edit of one already running or answered comes in again, marked; a message deleted while it waits never runs. A reply carries the message it answers.
- A failed turn takes the action `failures.toml` gives its class: transient reruns the same session (twice at most), overflow compacts then reruns, auth and quota rest that account (doubling per account and kind, kept across restarts) and continue the same turn under the same card on the next account, resuming the same session; a session that cannot be resumed starts fresh with a one-line recap; anything else is a visible notice. An empty reply retries once fresh.
- A turn Claude Code answered on a fallback model after a block stands, and its card and ledger row say so; the room's next turn starts a fresh session on the room's own model.
- After 30 idle minutes the process closes; the next message resumes the session.
- A hop resumes the same session on the next account by the transcript's absolute path (`--resume` takes one, as the docs promise), learnt from the first hook call of the session and kept in the room's binding; the id alone is searched only in the resuming account's own `projects` folder. Pointing every account's `projects` folder at one (a symbolic link) is an optimisation that lets the id be found anywhere, not a requirement.
- Every call to the daemon (`/hook`, `/mcp`, `/control`) carries the `x-yerk-secret` header: a room process sends the token minted for it at start and bound with its session (the daemon knows the room by that binding, never by a header a caller picks), the CLI and the job units send the install's secret from `secrets/yerk-http.secret` under the state folder (never inside a room's layer, so no room's read rule reaches it; `yerkd.json` names the path), and a worker's own server sends `secrets/yerk-worker.secret` beside it, which opens `recall` and `read_memory` only. A hook call no binding explains is answered `{"yerk": "unbound"}` and logged, never with a silent `{}`.
- The day log's line is `- HH:MM:SS+hh:mm room#id role@who: body [c:class] [m:id]`: the offset is each line's own from the configured IANA zone, the room's stable id (`id` in rooms.toml, else its channel) rides beside its name, the author is a role and a handle, and the class (private, room or shared) says who may read the line back. `recall` and `read_memory` return to a room only shared files and its own lines; the owner's rooms read everything. The daemon rewrites lines written before this shape once at its start, before any channel opens, each file that changes copied to `backups/` first (`yerk memory migrate-daylogs` runs the same rewrite by hand; both hold the lock capture holds, so no line is lost to the rewrite), and the reader still parses the old line.

The daemon's one local HTTP server carries `/mcp` (the tools `send`: text, or a file from the sending room's own folders, to a room; `hold`: end the turn while waiting on a named event or worker; `recall`: ranked chunks of the memory tree with path, line and a `file:line` to cite; `read_memory`: exact lines of a file inside the memory tree, nothing outside it), `/hook` (the clock and metadata lines and the recall part, keyed on the session id through the room-to-session table; the recall pack after a compaction; the Stop checks) and `/control` (`yerk room close`, `yerk room compact`).

## What you see

Every card, notice and status line follows one rule set, written down with an example of each in [STYLE.md](STYLE.md): the state first (🟢 done, 🟠 running or partly, 🔴 not done, ⚪ nothing to do), one short line per item at phone width, no file paths or exit codes in a room (a report is "report saved" with `yerk worker report <id>` behind it), times as a person says them, and the same words in every room from one vocabulary, `yerk_ai/words.py`. The developer detail lives behind `yerk worker report <id>` and `yerk status --full`. `yerk abilities` lists every ability one line each, built or known but not built (voice is described, not shipped, and `yerk explain voice` says how it would be built and why it is not); `yerk config get presentation` prints the presentation settings with their plain words. `tests/test_style.py` holds every renderer to it.

## What it knows it can do

`abilities.toml` holds 75 abilities: 14 built and 61 described, known and not built. The described ones are the abilities a long-running personal install grew over months, written neutrally: reading bank balances read-only, job applications that are true and reviewed, texting as you with a preview and a veto, a browser on its own profile, a morning brief, watching a page, transcribing a voice note, and 54 more. Each carries what it is, how it would be built, its tier (50 free, 6 need a provider key, 5 are paid), what it needs, what it would cost, its free path and why it is not built yet; one that is partly built names the built ability under `upgrade`. `yerk abilities` lists them one line each, `yerk explain NAME` answers for any one, a room that names one gets that entry's answer before the model starts, and "what can you do" gets every name by its state. `examples/abilities/` shows five of them with placeholder values; `tests/test_abilities.py` keeps every entry in that shape and free of anything shaped like a person's name and role, a room, a handle, an address, a dollar figure or a date.

## Ledgers

One SQLite file, `ledger.sqlite`: `turns` (account, models, time to first visible event and to the end, how it ended, which messages it answered), `inbound` (every channel message by its id, written before anything runs; a crash runs it again once, marked), `outbound` (every message posted, with the id the channel returned, and a card's text at each post and edit, so a card the reply replaced can still be read back), `holds`, `health` (the daily call per account: pass or fail, login method, an identity fingerprint, never the email). A turn row also names the failure's source in the table and the hop that brought the turn to its account.

## Files

- `budgets.toml`: every size limit, in characters as Claude Code counts them
- `failures.toml`: failure classes and what each one does next
- `units/`: the daily health call's systemd user timer, the memory index service and the weekly recall bench timer (copy and enable them yourself)
- `abilities.toml`: every ability, what it needs and its cost tier (free, key or paid), with the free path
- `rooms.toml.example`, `accounts.toml.example`: templates for your private folder
- `yerk_ai/lifted/`: code taken from other MIT projects and from the author's own tools, each file with its origin; see `NOTICE`
- `yerk_ai/channels/`: channel adapters (Discord)
