# Yerk AI

Yerk AI turns chat rooms into long-lived Claude Code sessions. It is a small Python program that does only what Claude Code does not do by itself: carry messages between a room and a session, build each room's context to a declared size, keep memory across sessions, and move work across the accounts you already have. The agent loop, tools, skills, compaction and resume are Claude Code's own, used through its documented flags, settings and hooks.

## What it is, and what it is not

- A personal tool. You run it on your own machine, for yourself.
- Bring your own installed Claude Code. Yerk AI starts the `claude` command you already have, under the login you already made with it. Each account is just a Claude Code config folder named in your own `accounts.toml`.
- No login handling for anyone else. Yerk AI never offers, brokers or copies a login, and it never reads the credential files in a config folder (a test greps the package for any read under one). One thing touches your own credentials, and it never prints or logs one: a one-year token you minted yourself with `claude setup-token` can be kept in your private folder (`secrets/claude-<account>.token`, 0600) and is handed to Claude Code in `CLAUDE_CODE_OAUTH_TOKEN`. The usage meters in `yerk status` come from what Claude Code itself prints: its own `/usage`, run as `claude -p /usage` on the account's config folder when the card is asked for (Claude Code reads its own login there; a one-year token cannot read the meters, so it is left out of that call; no model call is made), else the usage events in each room's stream. It never writes a config folder.
- Nothing stored for anyone else. Persona, memory and room settings live in a private folder you keep outside this repository; the repository ships only a fake example of it.
- Who it trusts. One person per install: it runs as your user and serves you, and the people a room lists are answered there but never trusted with your memory or your machine. The machine's other users are not trusted: yerkd makes its state folder 0700, writes every file that holds a credential or your words 0600, hands a room's token to its hooks through a 0600 file and never on a command line (which every local user can read in /proc), and `yerk doctor` names any file or folder in your private or state folder another user can read; keep the private folder 0700 too. A room's shell runs in Claude Code's sandbox, and no room may read a secret (a token, the bot token, a provider key, the daemon's own secrets, an account folder's login) with its Read tool or its shell, because a web page, a mail or a pasted message can steer a model. What a room recalls or imports, and what anyone but you writes (mail, a web page, a quoted message), reaches it marked as a record, never an instruction; a person's own message in their room is an ask to act on there, and an order in it to act as you, in another room or against a rule is reported, not followed. An outward action (a send to another room, a public post, a login, money, a message out through another tool) waits for your word in the room; a person's room can never post into yours. No credential is printed or logged, and the doctor names any secret-shaped line in your memory or imports by file and line, never by value, for you to scrub and rotate. It does not defend against root or anyone who can log in as you, a stolen token, a model that is wrong or that you tell to do harm, or a room you give an unsandboxed shell.

## Status

Layer 5, run 3: watchers, one heavy worker per account, worker tools and the relay's edge cases. A `watcher` job (`kind = "watcher"` in `jobs.toml`, with `command`, a `prefix` or a `regex`, `batch`, `lines`, `wake` and `prime`) runs its command all the time under its own systemd service, restarted with a backoff when it ends; matching output lines are events, every other line goes to the unit's log, the very first start primes (what is already there is history), a line seen before never wakes anyone again, and each event is a ledger row that wakes one turn (the room's own when the room is idle, or a worker) and is marked handled only after that turn ends clean: a crash replays it once, never twice, and a worker the owner stops ends its event with no replay and no alert. Workers wait in line for their account (`[workers] per_account`, default 1), the card saying "waiting for an account" and the place, and the daemon starts the next when the account frees; `yerk status` shows the line. A worker gets no Yerk AI tools unless `[workers] yerk_tools` names the read-only ones (`recall`, `read_memory`), which come from its own stdio server that has no `send`, `worker` or `schedule` to give. A relay waits for an idle room (the card carries the result meanwhile), runs as a turn of its own (two completions are two relays, in order, never merged), and resumes the room's own session when the room's process is closed, as any message does, never a fresh one. A job's failure in a room reads "job NAME failed: it ended with an error" or "job NAME stopped: timed out at 10 min"; the exit code is in the run's ledger note and `yerk status --full`. A worker that moves account mid-run is not built.

Layer 5, run 2: scheduled jobs and the typing signal. The owner's timed work comes from one private `jobs.toml` (the example with placeholder values is `examples/private/jobs.toml`; `yerk explain jobs` describes every key from the code): a job is a `script` (a shell line run inside its unit under an account-free environment, with a cap), an `agent` (a worker with the message as its brief, the job's account and cap, its card in the job's room) or a `note` (a reminder: when it is due the room's own session is told its `message` and says it in its own voice; no worker, shell or account), on one of three schedules: a cron expression with an IANA `tz`, `every` (an interval) or `at` (one time, removed from the file after it fires). `yerk jobs sync` generates one systemd user timer and service per job, idempotently (unchanged jobs untouched, changed ones rewritten and restarted, removed ones disabled and their files gone), prints the diff and then every next fire time read back from systemd, naming any job that cannot be scheduled with why; `yerk jobs list` is the read-back, and `yerk status` lists the jobs with their next fire from systemd, never from memory. Timers carry `Persistent=true` and `AccuracySec=1s`, so a missed run fires once on return and a one-shot lands on its second. A run delivers by the cron-wrap rule: exit 0 with output posts the output to the room, exit 0 with nothing posts nothing, a failure or a timeout posts one alert line to the ops room (`[jobs] ops_room` in yerkd.toml, else the job's room); an agent job's last message is told by the room's own session through the same relay as a worker's, and a last message of exactly `NO_REPLY` is silence. Every run is a row in the `job_runs` ledger (planned and fired times, how it ended, what was delivered or why nothing was). The `schedule` tool in every room and `yerk schedule` add a one-shot or a recurring job, remove one or list them, writing the file and syncing, and answer with the next fire time read back; a missing zone is the room's configured one, never UTC by accident. A room that is not the owner's adds, lists and removes its own notes and sees no other job, since agent and script jobs run as the owner and stay the owner's rooms' own; such a room keeps 20 notes at most and adds 3 per 5 minutes, so a reminder and its follow-up check go in one turn, its call with no `kind` sets a note, and a note's message is at most 600 characters in any room (`[jobs] room_notes`, `room_note_minutes`, `room_note_burst` and `note_chars` in yerkd.toml; each refusal says the cap); a note missed while yerkd was down is told at its next start. The Discord adapter now sends the typing signal from the moment a message is taken until the first card post or the reply, refreshed every 8 seconds while nothing is visible and never once a card exists; it is not a delivery and is ledgered as nothing.

Layer 5, run 1: workers. Heavy work leaves the room (the mechanics send work that will take more than about five minutes to it, with a one-line answer now): `worker` (a tool in every room) and `yerk worker start|list|stop|report` run a headless `claude -p` as its own systemd transient unit `yerk-worker-<id>`, which outlives the daemon: one named account (its token file is the only one the unit's environment names, read inside the unit the way a room reads it), a brief, a staging folder with stdout and stderr in it, a report path, a TASKS.md and a cap (65 minutes unless the call or `[workers]` in yerkd.toml says otherwise), no MCP server and no subagent tool, so no worker starts another. Its card in the room shows the start and the cap and ticks a row per TASKS.md line as the worker ticks it (an inotify watch on the folder, at most one edit a second). When the unit ends, its ExecStopPost record settles the card with the report's first line, the report path and the exit state (done, died, timed out, stopped, lost); when the room is idle (no human message for 60 seconds and no turn running) one relay turn in the room's own session says the outcome in its voice under 1,500 characters with the report path, and a message landing during it is answered inside it; otherwise the relay is skipped and the ledger says why. The `workers` table in the run ledger keeps every worker; `yerk status` lists the running ones checked against the unit list; a daemon restart re-attaches from both, so no card is orphaned.

Layer 4, run 1: memory, the foundation. Every message of every room is filed in the day's log in the private memory tree as it lands (attachment-only and one-character ones included, one line per attachment, never twice for one message id). `yerk-index` keeps an FTS5 index over that tree in its own process (`units/yerk-index.service`), writing only the chunks that changed, with `yerk-index --check` comparing it against the disk and telling a timeout from a failure. Rooms get `recall` and `read_memory`; `yerk recall-bench` runs a fixed question set from the private layer against the index (weekly, `units/yerk-recall-bench.timer`). Each ability and its cost tier is in `abilities.toml`.

Layer 4, run 2: recall before the first word. `yerk-index` also builds a name index from the fact files and the curated file's headings whenever one changes. A line whose first six words hold a known one-word name is keyed by that name; a first name answers through its own line ("Ada: ..."). The prompt hook puts the entries for the names a message mentions, then the room's own lines of the last 14 days on the message's topic, in front of the model before it starts (at most 1,500 characters, `budgets.toml` `[per_message.on_hit]`), and writes what it assembled, part by part, to the room's `assembled.jsonl`. The session-start recall pack is the room's own filed items of the last 14 days (what the owner sent, decisions, drafts), newest first, up to 6,000 characters with the open commitments, and a SessionStart command hook adds it again after every compaction (`yerk room compact ROOM` asks for one). Every tool call is ledgered with what it read, and a rule check after each reply logs, in shadow, a quoted figure or file the turn never read (a figure in one of the room's replies posted earlier in the same session counts as read, since the check read that reply; its narration before a tool call, its sends, file captions and notes, which the check never read, do not) and a "what did we decide" answered with no memory read. A figure is on file only where a line is about the same thing: the label words beside it in the reply sit beside it there too, its unit agrees, and the line is not the reply's own record; a line that only shares the digits is not its source. `yerk-index --rebuild` builds a new generation and swaps a link, so recall never fails during a rebuild.

Layer 11, rail run 2: the room reaches for the owner's past before it answers, code deciding when (`words.py`): a question about the owner's past ("what did I", "who did I go to lunch with", "last friday", a date asked about) runs the recall tool's own search, in the room's scope and as its reader, and its best hits come in with their cites; a name brings its best lines from that scope after its card, newest first, and so does a name or topic the message asks about ("who is X", "what do you know about X"), which has the line `[named, nothing on file: X]` when nothing holds it, so "not on file" is code's word and the mechanics tell the room to say it plainly. The 2,000 characters of the recall part bend per hit: one name takes all of it, several names share it, and a past-tense search takes what the names leave (beside one, each name brings its card's first line). Measured on twenty questions about the owner's own days, with the meaning search too busy to answer inside the hook's two seconds: a 1,500-character part held the answer for 8, 2,000 for 10, 3,000 for 11; with the index healthy (the cold read of Oct 21), 9 at 1,500 and 11 at 2,000. So `recall = 2000` in `[per_message.on_hit]`, 500 more characters (about 125 tokens) on a message that hits and inside the 4,000 cap, set in its own commit as a visible decision.

Layer 4, run 3: meaning search behind the keywords. With a provider key in the private folder (`secrets/openai.key`, or where `[memory] embeddings_key` in `yerkd.toml` points), `yerk-index` embeds every chunk once (OpenAI `text-embedding-3-small` at 256 dimensions, changed chunks only, the vector stored next to the chunk's hash and copied across a rebuild), backfills the tree in the background, resumable and in batches with a gap between them, and serves the search on a local port; `recall` fuses the meaning rank with the keyword rank by reciprocal rank fusion, its answer shape unchanged. No key: keywords only, exactly as before, and the room is told once in one line. A provider timeout or error: keywords only for that query, logged, told apart from a failure of the index. `yerk abilities` lists every ability as 🟢 on, 🟠 needs a provider key, or ⚪ on its free path, and `yerk explain NAME` answers from `abilities.toml` (what it does, needs and costs, the free path). The example question set (`examples/private/evals/recall-questions.json`) carries the two room-recall kinds: what was sent in a room recently, and what was said there on a day. The backfill cuts a request at 250,000 bytes, under the provider's 300,000 tokens since its tokenizer makes at most one token a byte, and halves it at once on a 400 that names the size; its unit caps it at MemoryHigh = 256M + 8.3M per 16,384 vectors (800M holds 1,064,960); `yerk deploy` restarts yerk-index right after yerkd, and its proof wants both on the new commit.

Layer 4, the recall diet: `recall` hands the room the lines that carry the match, not whole chunks. Each hit is `{cite, text}`: the best line (the most query weight, each word weighted by its rarity as the keyword rank weighs it; the line whose vector the meaning search matched, which yerk-index now names, counts as a match), then every other line holding a query word, heaviest first, then the lines nearest the best one, at most 750 characters a hit, cut at line ends and kept in file order (a gap reads "…"; a line too long for what is left is cut around its matches, at spaces). The cite is the snippet's first line, and `read_memory` takes it as its path. A call's first six snippets hold at most `[memory] recall_chars` together (default 4,500, six hits of 750; `yerk config get recall_chars`), each a share of what is left, and each hit past the sixth adds its best line, cut around the match to at most 160 characters, so a call of twenty hits shows its first six exactly as a call of six does. Ranking is untouched: `ranked` is the old recall (the same hits in the same order), the bench scores rank on its whole chunks and adds `kept`, the found answers whose snippet still holds every answer token. read_memory's default window is 12 lines, from 40: a whole hit chunk from its first line for 98 in 100 found answers (the 98th percentile is 11 lines), and its description says to ask for more lines or a later `from_line`. Layer 4, recall warm: `yerk-index` keeps the pages the keyword rank reads (the FTS tables, the `chunks` rows it joins, `meta`; 413 MB at 314,010 chunks) mapped into itself, so recall, which reads the index file itself as before, finds them in RAM. A box may drop its page cache on a clock (`echo 1 > /proc/sys/vm/drop_caches`; the author's trimmer does, every 2 minutes), and a drop passes any mapped page by, for every reader of the file. A connection's own page cache cannot do this: SQLite drops it whenever the writer commits, which is every pass. The pages are mapped at start, within 5 s of a writer pass that changed chunks, every 10 minutes and after a rebuild, and never locked, so real memory pressure can still take one until the next pass. index.json carries `pin`, and the unit's MemoryHigh rule and `yerk doctor` count its bytes. Measured on the author's box with the trimmer running, 16 keyword ranks 12 s apart across one drop, recall's own read (a fresh read-only connection and the same search, 80 hits each): on a pinned copy of the live index a median of 0.116 s (0.173 at most, 0.116 right after the drop), on the live file unpinned at the same moments a median of 0.494 s (3.604 right after the drop); the first pass took 7.1 s.

Layer 6, run 1: the rule-based gates. Every Claude Code hook a room uses posts to the daemon (UserPromptSubmit, PreToolUse, PostToolUse, PostToolUseFailure, Stop and ConfigChange over http; SessionStart through curl, the one way Claude Code runs it), and `yerk_ai/gates.py` decides by code, so its gates block. A plain `rm` or `unlink` (with -r too) is rewritten to the trash command with the same paths and runs; a delete in any other shape is refused with the trash line for the model; the room hears nothing unless the trash fails. Shell text is read quote-aware first: quoted text, heredoc bodies and a word in a sentence are not commands. A command on the hardline list (from Hermes Agent) never runs. A write to yerkd.toml, rooms.toml or accounts.toml, or a restart of yerkd, is refused with one line while a person is mid-conversation or the memory index rebuilds. An external action (a send to another room, a public post, a login, money, a message out through another tool, or a rule under `[gates.external]` in yerkd.toml) is held with one line until an approver says `approve` in the room, then that same call (its normalised text and folder) runs once and any other is held again; the word counts only from a message the room itself wrote into its running turn, under the room's bound session (/hook has no secret yet); hold, word and release are ledgered. A working turn that ends with nothing in the room bounces once, naming the message it owes, and never when a part already landed under the turn's key; a session that replaced another posts a reset line; a changed settings file is a tamper row (who, what, when, the diff's hash, from line hashes, never the text). The evidence ledger gains each call's time and failure, and every hook call's own time is a `hook_calls` row, so `Ledger.hook_overhead` is the overhead per turn against the 150 ms bar at the 95th percentile. Decision 25 runs in shadow: a sentence claiming what code does or lacks, what is running, a decision or a file's contents, with no test run, status read, memory read or file read behind it in the turn, is ledgered with the sentence and the tools the turn ran. The stance check runs beside it, also in shadow (ROADMAP-v3 claim 3): it reads the owner's messages of the turn for a disagreement word on a short list (`words.PUSHBACK`: nah, no, nope, wrong, actually, not true, that's not, you're wrong, I disagree), counts only when the room posted a reply earlier in the same session, reads the reply for agreement, a "still stands" clause and a mistake it names, and checks the turn's tool calls after the message for a source read; it logs one `stance` row per such reply, `held` (what still stands, with that read, or a reply that neither agrees nor names a mistake of its own, read or not), `conceded` (what it got wrong, with that read) or `folded` (it agrees or concedes with neither), counted by label in the morning diff with only a fold as a finding, and it would start bouncing a fold only once it shows under 1 in 10 false alarms on 100 cases with a known-good control passing (decision 8). Two more run in shadow beside them: `person`, a sentence telling what someone said, wants, knows, decided or asked, or where they were (the owner as "you" included), from a turn that made no call that reads, and `quote`, a quoted span of three or more words given as someone's or a document's words that no read, prompt or earlier reply of the session carries; each is ledgered with its sentence or span and counted in the morning diff. The five judge-model reply gates are not built; none may block until it shows under 1 in 10 false alarms on 100 cases with a known-good control passing. A room gets tools beyond Read through `allow` in rooms.toml (permission rules), and the gates still run first.

Said or noted: in an owner's room a reply or a `send` that tells what a third person said, decided, wants or asked, or quotes their words, from a turn that made no reading call is turned back once with the fix (read where their words are and cite it, or write it as "from my notes, not their words"); the second try goes out, a person's room only logs, and each refusal is a `person-refused` or `quote-refused` shadow row the morning diff counts. A sentence about the owner ("you", or the name `[import] me` gives his words) or the room is never such a claim. A room's own note is shown behind "[the room's note, not their words]" wherever recall shows it, a person's words filed with `remember` `said` and `source` behind "[their words]", and the text files sent to an owner room (its `work/inbox`, transcripts included) are recall roots there.

Pictures seen: a picture sent to an owner room (png, jpg, jpeg, gif, webp, heic) is filed beside it in the same turn as `NAME.seen.txt`, so a later recall finds it the way it finds the uploads and transcripts. The room reads the picture before answering anyway, so the `seen` tool costs no second model call: it writes a first line by code (the room, the message id, the local time it was saved, its name), then every word on the picture as the room read it, in reading order (a screenshot of a chat keeps who said what exactly as shown), then a line or two of what it shows: a person in a photo the owner sends in his own room is the owner unless its own text says otherwise, anyone else named only as the picture's own text names them. The sidecar is a text kind of the inbox, private, cited as `<room>/work/inbox/<id>/NAME.seen.txt:line`, and recall and read_memory show its lines behind "[text on a picture he sent, as the room read it]", never as anyone's words; a room that read a picture and filed nothing is turned back once to file it. A person's room files no picture, as its uploads are never indexed. `yerk pictures backfill ROOM [--limit N] [--dry-run]` files the pictures sent before this: Yerk workers on the room's own account and model read them 20 to a batch, one batch after another so the account's other workers wait for one batch at most, each batch's card and one line in the machine room; `--dry-run` lists each sidecar it would write and starts nothing. `--root FOLDER` does the same for the pictures under a folder the room lists in rooms.toml (`read` or `also`), each sidecar beside its picture, cited and indexed under that folder as its other files are (a file there with no front matter is private); any other folder is refused.

Needs: a room that cannot do what it was asked (no tool, a refused tool, a page that will not open) files what it needed with the `need` tool and never builds a way of its own, so every room keeps the one same way of doing each thing. The filing is one line, `- ROOM, TIME: asked: ...; tried: ...; needed: ... [m:ID]`, and a workaround the room did anyway rides on it as `did anyway: ... [shadow]`, so the builder sees what was improvised. Each need is a proposal of kind `need` on the day's `<memory>/rules-proposals/<day>.md`, `## N. need: ABILITY`, numbered with curate's proposals in one count a day (curate's own take the numbers the day's needs leave, and its 05:00 rewrite of the page keeps their blocks), recorded in `<state>/needs.json`, and said in one line in the machine room. A month of a busy room in tests/test_retention.py (page renders, a 900 MB burst, sends, transcripts, workers, ledger rows, the sweep each morning) stays under one bound fixed before it starts. A person room made by `yerk room add` copies the other person room's persona and rulebook without that room's own text: every line naming its folder goes, and so does the persona's `# About the owner` section, written again from the template with OWNER, PERSON and RELATION for the owner to fill in.

`yerk doctor` checks the install each day after the sweep (units/yerk-doctor.timer, 04:40): the private folder's layout, any rooms.toml key no loader reads (config.ROOM_KEYS), memory classes and day-log lines, token expiry where the token file says when it was issued, the index, each running room's hooks and the folders' growth past `[doctor] growth_mb` (500 MB a day), quiet when all is well and a line per finding, the count and the first in the morning diff. It also reads the memory index: a memory cap under what `units/yerk-index.service`'s rule gives its vector count, a backfill paused after three failures in a row, two memory roots with one cite (a root whose folder name an earlier root has is cited with as much of its path as tells them apart), and yerk-index on other code than yerkd. It is also the crash repair, on yerkd's start before any room opens and daily: a hard power-off zeroes the line a file was writing, so every day log, assembled log and bound transcript with a NUL byte is backed up, then its line mended (the NULs out, the text kept when it still reads), else blank in a day log so every cited line number holds, dropped from a JSONL file, never in a room with a turn in flight or waiting.

`yerk curate` keeps the cards each night after the doctor (units/yerk-curate.timer, 05:00), in two parts: a sweep in code blanks a card line said twice, a superseded line and a line `until` a date now past, and moves a cite only when its quoted words sit on exactly one line of its file, every other drift one finding in the morning diff, each card backed up first. Then each card gets a pack of the day's lines that name it as the card's reader may read them, a worker that sees only the pack proposes lines, a second knocks them down by `yerk_ai/curate.md`, code checks shape, head, secrets and that each cite is a line of the pack, and the lines land with a backup only when the recall bench does not fall, a correction only ever proposed, never applied, and `--since DATE` the same code over a range for a backfill.

Then the rule files, by proposal only: the same nightly run (and `yerk curate --rules [--dry-run]` alone) reads the rules file, each room's rulebook and `rules-overflow.md` whole and proposes merges (one job, near-duplicate words, or one message on jobs that overlap, never one message alone, every clause and the fuller example kept), cuts (a superseded line a session start still sends, a cite to a day-log line that is gone, an older line a newer one on the same job says otherwise to, both quoted), condensations (a line past 600 characters, its examples and quoted asides out first, never a reason, only its own words kept) and promotions (a held rule that fits again), each with the week's evidence: the shadow bounces, rated replies and `yerk` lines that touch it, with their cites. They go numbered to `memory/rules-proposals/<day>.md` (0600, BEFORE, AFTER, WHY, EVIDENCE, each file's size now and with all of them in) and the ten that save the most to one card in the machine room, once a day, none when there are none. Nothing in a rule file changes until the owner says so: `yerk curate --apply DAY N[,N...]` writes those numbers, every file backed up first, refused whole when a line changed since or a file would pass its line in `budgets.toml`, a line blanked rather than cut so every cite keeps its number, and `yerk curate --apply DAY undo` puts the last apply back byte for byte.

## Use

```
uv sync
uv run yerk map example-room                 # the example room's context, part by part, against budgets.toml
uv run yerkd                                 # every room with a discord:<channel id>, through the Discord adapter
uv run yerkd --console example-room --config-dir ~/.claude   # one room on the terminal: a line in, a JSON reply out
uv run yerk map example-room --wire          # also the sizes as sent, read from the room's Claude Code transcript (a line that does not parse, as a crash leaves one, is skipped and counted)
uv run yerk setup-room ROOM                  # a Discord room's test webhook; its URL goes to secrets/ (0600), never printed
uv run yerk room close ROOM                  # the running yerkd closes ROOM's process now (never mid-turn); the session stays
uv run yerk room add NAME --from discord:ID  # a Discord chat moves in as the room NAME-on-yerk (Moving a chat in, below)
uv run yerk import discord-guild:ID --dry-run   # every chat on the server, counted; without --dry-run, imported (Importing a chat, below)
uv run yerk accounts                         # per account: order, token age and days left (warns inside 30), rests, last health call
uv run yerk accounts cool NAME MINUTES       # rest an account by hand; `clear NAME` lifts it; a running yerkd sees both at its next pick
uv run yerk accounts mint NAME               # `claude setup-token` for NAME: the browser flow shown, the token stored 0600, never shown
uv run yerk accounts token NAME              # or store a token from stdin (never echoed), 0600, issued today
uv run yerk accounts health                  # one tiny model turn per account and its login identity, a ledger row each
uv run yerk status                           # the card: each account's live meters, resets and bill day, the next resets in order, what runs, memory, stalls
uv run yerk morning                          # the morning diff to the role = "machine" room (units/yerk-morning.timer: 06:30)
uv run yerk deploy [REF] --private DIR       # REF onto the running yerkd: fast-forward only, fast tests, a quiet room, proof, else rollback
uv run yerk deploy --unit                    # the same, moving a systemd-run yerkd onto units/yerkd.service (Install below)
uv run yerk retention --dry-run              # what the nightly sweep (units/yerk-retention.timer) would move to the trash, by kind
uv run yerk doctor --dry-run                 # the daily check (units/yerk-doctor.timer): a line per finding, nothing when all is well
uv run yerk curate --dry-run --since 2026-10-19   # the night's card curation (units/yerk-curate.timer): what it would sweep and propose
uv run python tests/contract/probes.py drill --config-dir DIR   # the Claude Code upgrade drill: the version, hello, fold and resume on one account, a verdict
uv run python tests/contract/probes.py hello|fold|resume|blocks|smoke|measure|check|idle --config-dir ~/.claude   # one contract probe
uv run pytest
```

- `--private DIR` or `YERK_PRIVATE` points at your private folder (default: the fake one in `examples/private/`).
- `yerk map ROOM --wire` reads every later message by part, Yerk AI's (clock, metadata, rules, recall, taste, a compaction's recall pack) against their budgets.toml keys, which is where its OVER comes from, the reply header, attachment lines and the message's own text as reported and never cut, and Claude Code's own blocks by name, then lists the week's five largest by the part that made them large.
- `YERK_STATE` sets the state folder (default `~/.local/state/yerk`): the room-to-session table, session locks, the ledgers, cooldowns, logs, which `yerk retention` (units/yerk-retention.timer, 04:20) keeps from growing forever: the days each kind keeps are `[retention]` in yerkd.toml, a room's scratch (its work folder but the person's files in inbox/, and the copies of what it sent) keeps 2 days and 500 MB (`scratch`, `scratch_mb`), and what leaves waits a week in the state folder's trash, a room's scratch a day (`trash`, `scratch_trash`).

## Moving a chat in

`yerk room add NAME --from discord:<channel or thread id> [--person ID] [--voice FILE] [--since YYYY-MM-DD] [--like ROOM] [--dry-run]` moves a Discord chat in as the room NAME-on-yerk, in six steps, each said as it is done. `--dry-run` reads and prints every step and writes and sends nothing: run it first.

1. Channel: a private channel NAME-on-yerk, made with the bot token yerkd.toml names, with the permission overwrites of the room it is made like (so the same people see it); with `--person` that person is let in as well. A channel of that name already there is kept.
2. Voice: `--voice FILE` is copied to the layer's rooms/NAME.md; without it, a one-line placeholder to write.
3. Block: `[rooms.NAME-on-yerk]` from a template in examples/rooms/. owner.toml copies an owner room of yours (`--like`, else the last owner room in rooms.toml that is not the machine room) with its channel and voice set. person.toml copies a person room (`--like`, else the last room with `people`), so its wall is reused: privacy family, `people` the id, Read, Grep and Glob only, no `read`, `also` or sandbox, and a layer of its own under the private folder (0700) holding copies of that room's persona and rulebook less its own text (every line naming its folder, and the persona's `# About the owner` section, the one about its person), the template's `about` section at the persona's end in its place, and pinned.md and open-loops.md to write. Before anything changes, the rooms.toml it would write is loaded (config.rooms) and the daemon's people guard runs on it, and a person room's files are read for any path into the private folder outside its own layer; a miss stops it with one line. Then rooms.toml is copied into backups/ with the time in the name, and the block is appended.
4. History: the old channel's or thread's messages (from `--since` on, else all) filed in the day log under the room's id and class: the owner's lines `owner`, the person's `person`, everyone else's `other`, each with its author's handle, as the daemon files a live line; attachments up to 25 MB saved into the layer's NAME-attachments/ (0700, files 0600). It goes by message id and file name, so a second run only tops up. Yerk's bot must be able to read the old channel.
5. Restart: none. It prints the one `yerk deploy` line to run, detached, at a quiet moment.
6. Check: the room's context against budgets.toml; the test webhook (yerk-test-sender) found or made in the new channel, its URL in secrets/discord-NAME-webhook.url (0600, never printed); the yerkd.toml `test_senders` line with its id added, printed to apply before the deploy and never written here; and the warm-up line to post through it.

A person room's persona and rulebook start as the other person room's less its own text: fill in OWNER, PERSON and RELATION in the persona's last section, read the rest for anything else of that room's, and write pinned.md, before the person talks there.

## Importing a chat

`yerk import discord:<channel or thread id> [--since YYYY-MM-DD] [--files] [--dry-run]` files a Discord chat's whole history into the day logs with no room made, through the one import `yerk room add` uses (step 4 above): by message id, so a second run only tops up and a message already in the day log is never filed twice. Its lines go under the room id `discord:<id>`, the chat's name as the label, class `private`: an owner room reads them, no person room does. `[import] classes` in yerkd.toml changes that per id: `"shared"` lets every room read them, and `"room:<a room's id>"` files them under that room's id and class, behind its wall, its people's lines as `person`; a person's old channel belongs with her room, `classes = {"<old channel id>" = "room:discord:<her room's channel id>"}`. A message is filed once, under the first room id it gets: a chat imported before its room is made stays under `discord:<id>`, and a later `yerk room add` files none of it under the room, so a chat that will become a person's room waits in `[import] skip` until `yerk room add` has moved it in. A chat a room covers (its `channel` or `watch` in rooms.toml) is filed as that room files it. Attachments are named in their line with their size and not downloaded; `--files` saves each one up to 25 MB into the private folder's attachments/discord-<id>/ (0700, files 0600). `--dry-run` reads and counts, writes nothing, and prints every line it would file.

`yerk import discord-guild:<guild id> --dry-run` is the server's inventory: every text, news, voice and stage channel and every thread under one (active and archived, public, and the private ones the bot may list), one line each: its parent, how many messages (counted by paging them all; for a chat the bot cannot read, Discord's own count where a thread has one, said as such, else unknown), the first and last day, whether a room covers it, and the class it would get. Without `--dry-run` it imports every chat on the list that no room covers and `[import] skip = ["<id>", ...]` leaves in, one after another, each said as it is done; a chat it cannot read is said, the rest go on, and the run ends 1. Discord hands one bot about a hundred messages a second, so a big server takes minutes. Yerk's bot must be able to read a chat (View Channel and Read Message History): one it cannot read is listed with the day it was made and the day of its last message, read from their ids, and its threads are not asked for.

`yerk import imessage:<chat.db> [--contacts <db>]` and `yerk import gmail` move a person's texts and mail in as files, not day-log lines: `imports/texts/<person or group>.md`, a file a person (named by their contact, else their number or address) and a file a group chat, a chat deleted on the phone placed by its messages' `ck_chat_id`; and `imports/mail/<YYYY-MM>.md`, Gmail's All Mail a file a month. One line a message: who, when in the install's zone, the text on one line, attachments and app messages as tags; a newsletter, a draft and a security mail marked; 400 characters of a mail's text, 1,200 of your own sent mail. Both only read: the databases are opened read-only (a copy of `~/Library/Messages/chat.db` with its `chat.db-wal` beside it, or the newest texts are missing, which the Terminal needs Full Disk Access to make; and of the Contacts `AddressBook-v22.abcddb` under `~/Library/Application Support/AddressBook/Sources/`), Gmail with EXAMINE and BODY.PEEK, by `[gmail] user` and `password_file` in yerkd.toml (a path in the private folder, or absolute, to a file holding an app password alone on its line or after `App password:`, never printed; Google makes one at myaccount.google.com/apppasswords once 2-Step Verification is on, and revokes it when the account's password changes); `[import] me` is the name your own texts are written under. A security mail, a security text from a short code (a bank's, a sign-in's) and anything shaped like a key, a token or a one-time code are written as their kind only, never the secret, so no file the index reads holds a live code or key. A setup that is not there (the database, the `[gmail]` keys or its file, a folder of files no import wrote) is refused with exit 2 before anything is read; a Gmail batch that fails is said and left for the next run, and the run ends 1. By id (a message's guid, a mail's UIDVALIDITY:UID, one a line in `imports/texts.ids` and `imports/mail.ids`), a second run adds only what is new, and a folder of files no import wrote is refused. The files carry no class, so they read as private: with `imports/texts` and `imports/mail` in `[memory] also`, an owner room reads them and no person room does. `--since` and `--dry-run` work as for a chat.

## Install as a service

`units/yerkd.service` runs yerkd under systemd with `Type=notify` (a start counts once READY=1 says the port listens), `WatchdogSec=30` (the beat stops when the event loop stops, and systemd restarts it), `MemoryHigh=2G` with `MemoryMax=4G` (raise MemoryHigh by 350M for each room kept open past five), `KillMode=mixed` with `TimeoutStopSec=30` (a stop sends yerkd SIGTERM alone: it says STOPPING=1, ends each room's Claude Code itself, closes the gateway clean and exits 0, in about a second; a turn cut mid-run has its messages run again once at the next start, marked), and `NoNewPrivileges` with `PrivateTmp` (no setuid gain for a room's shell, a /tmp of its own). `yerk status` names the version and the commit that runs; `yerk status --json` is the same as one document for a monitoring tool (rooms, accounts, the last turn per room, the day's failed turns and unanswered messages, the index, the newest backup's age). CHANGELOG.md names what each merge changed. Copy it to `~/.config/systemd/user/`, set `YERK_PRIVATE` and `YERK_STATE`, and `systemctl --user enable --now yerkd.service`. A yerkd started by hand with `systemd-run --user --unit=NAME` moves onto it with `yerk deploy --unit` (the unit is the one the running yerkd's pid is in; `[deploy] unit = "NAME"` in yerkd.toml names it instead): the unit's command (read word by word from systemd's bus), folder and environment go into the file under the same name, written 0600, and the file unit starts at the next quiet moment; a failed proof puts the transient unit back. After that `yerk deploy` restarts it in place. `[deploy] tree` names the daemon's checkout (default: the unit's working folder), `tests` the fast subset (default `tests/test_scrub.py`, `test_budget.py`, `test_card.py`, `test_style.py`), and `proof_seconds` how long the proof may take (60). The fast tests run with the deploy's private and state folders as `YERK_PRIVATE` and `YERK_STATE`, so the budget test builds every real room the way the daemon does, rules file included, and a room past a budget fails the deploy with the room and its part on the card. With no `--private` and no `YERK_PRIVATE` those folders are the ones on the running yerkd's own command line (`--private` and `--state` in its unit's ExecStart, and the card's second line says `private layer: the daemon's`), and with none there the deploy refuses in one line, `no private layer: pass --private`, so the fast tests never read the fake example layer.

## The private folder

- `rooms.toml`: one entry per room: channel (`discord:<channel id>`), account order, model, tool allowlist, privacy class, time zone, and the context files. `layer` names the folder those files come from (default: the private folder itself). `people` lists the Discord user ids the room answers besides the owner (unset: the owner only; the owner is answered in every room).
- A room with `people` reads its own lines and the shared files only, so it takes no `read` folder and no shell tool, unless `shell = "trusted"`: then it lists the owner rooms' tools (Bash, Write, Edit and the rest), its shell runs inside the wall the daemon builds (below), and Write and Edit reach its layer and work folder only. Its `[rooms.NAME.sandbox]` table may add `filesystem.denyRead`, `filesystem.denyWrite` and the `network` allowlist; any other key, an `allow` rule for the file tools, or a wall that cannot be built stops the start with one line. `yerk explain trusted` says the same. What is sent to a person's room (its uploads, a recording's transcript, the pictures it files with `seen`) is recalled there as its own, read by that room and the owner's rooms only, and a reply there that says what a third person said from a turn that read nothing is turned back once, as in an owner room.
- `taste.jsonl` in an owner room's layer: the owner's thumbs on the room's replies, kept the way the old box keeps them. A message of the owner's in the room's own channel that praises or faults the last reply ("that was good", "too long") adds one row, one per reply per sign; a test sender, a person or the harness never rates. Every message in that room then carries the `taste` part after recall: three praised and two faulted replies, the owner's words beside what the room had said, the room's own newest first, then the other rooms' (`[per_message.on_hit] taste`).
- The file is the switch: a layer without `taste.jsonl` gets no row and no part, and a room with `people` gets neither. `yerk map` shows the part's size.
- `accounts.toml`: one line per account: `name = { config_dir = "...", order = 1 }`, optionally `token = "secrets/..."` (the default is `secrets/claude-<name>.token`). Adding or removing an account is that one line; a room's own `accounts` list only orders the accounts it names, the rest follow.
- `yerkd.toml`: the daemon's settings: the Discord token file, the owner's user id, webhook ids accepted as senders in test mode, the local port. A running `yerkd` writes its pid and port to `yerkd.json` in the state folder.
- `[watch] assistants` in `yerkd.toml` lists other assistants' Discord user ids: in a channel a room watches, their messages go in that room's day log under their own label once they stop changing, never answered and never read as anyone's instruction, so the room can read what was already said there.
- `secrets/`: files only you can read (mode 0600), for example the bot token. Nothing in the repository reads them except the daemon at start, and every room's settings deny its Read tool and its shell the folder.
- The Discord bot: invite it with the `bot` and `applications.commands` scopes and permissions `274878008384` (View Channels, Send Messages, Send Messages in Threads, Read Message History, Add Reactions, Attach Files), and turn on its Message Content intent; it asks for no other intent (Guilds and Guild Messages, no members, presences or direct messages). `yerk room add` and `yerk setup-room` also need Manage Channels and Manage Webhooks (`275414879312` with them), and an import of a server's private archived threads Manage Threads. Administrator adds every channel and every server setting, which Yerk itself never uses: give it only when a plug-in of yours acts as the bot on the server (moderation, admin writes), knowing that a room steered through that plug-in reaches all of it.

## How a room runs

One `claude -p` process per active room, stream-json in and out, with:

- `--session-id` on a session Yerk AI minted, or `--resume` on the room's own session; one live process per session, by lock file
- `--setting-sources ""` and `--settings`, so only the settings Yerk AI writes apply: a Read rule for the room's folder, Read deny rules on every secret, the hooks (each a command hook whose `curl` posts the event to the daemon with the room's token read from a 0600 file beside the settings), and `autoCompactWindow` from `budgets.toml` `[session] compact_window` (a room's own `compact_window` in `rooms.toml` overrides it; 0 leaves it to the model), so a room compacts where Yerk AI says, never at the model's window edge: a room that rides the whole window re-reads all of it on every message and pays it in full after an idle hour, when the prompt cache is gone. A compaction loses nothing searchable: every line is in the day log, and the recall pack comes back after it
- Claude Code's sandbox, `enabled` with `autoAllowBashIfSandboxed`, for a room whose `tools` run a shell (Bash, Monitor, PowerShell or `default`) and that rooms.toml gives no `[rooms.NAME.sandbox]` table: without it a Read deny stops `cat` and the Read tool but not a script, `grep` or a redirect; a room's own table, `enabled = false` included, is passed as written (on Linux the sandbox needs bubblewrap and socat)
- for a room with `shell = "trusted"`, the daemon's own sandbox instead, rebuilt at each process start: no command retried outside it, no start without it, and denied to the shell for reading and writing every entry of the private and state folders but the room's own (the other layers, the memory folder, rooms.toml, imports; every other room's folder, the ledger), every memory root and every other room's layer and `read` folders, `projects/` under each account's folder, and each folder of the home that holds one of those; its outbox is read only and the Python user site-packages are re-opened (proven on Claude Code 2.1.304 by a scratch probe: its layer, work folder and python-docx open, every walled path, the rest of the home and the network closed)
- `--add-dir` on the room's folder; every part of the appended context starts with `[from <absolute path>]`, so the model can re-read the file a fact came from
- `--mcp-config` naming only Yerk AI's server, with `alwaysLoad: true`, and `--strict-mcp-config`; a `--tools` allowlist; `--model`
- `--append-system-prompt-file` with the assembled context, built to the sizes in `budgets.toml`; the install's rules file is a part of its own (`rules`, after the hand-kept files, since the rooms write it as they go), so a rulebook near its cap never pushes a shared rule out, and a part past its size is sent trimmed under a marker that names it (a rule file, the rules part or a rulebook, keeps its first lines whole and drops the newest, never a middle line); a rule filed with `remember` and `job` that would take the rules file past its size is fitted first, the `<example>` blocks out of the rules newest first and its own first until the file is 150 characters under it, the rule's own words never cut; a rule with no room even then goes whole to `rules-overflow.md` beside the rules file and reaches no room: its result says `held`, the room ends its reply saying so, the machine room (else `[jobs] ops_room`) gets one notice with its job, its room and the cap, and `yerk doctor` counts it, orange, until it is moved in by hand

The room runner:

- A message for an idle room starts a turn. A message that arrives mid-turn goes straight to the process's stdin and is answered inside the same turn; the replayed copy (`--replay-user-messages`) is the proof it was accepted. When that turn fails, a message that folded into it after it started is not failed with it: it runs next as its own turn, and its card says so. A result of Claude Code's own turn for a background command's notice (`origin` kind `task-notification`, what a resume streams first for the commands a crash left running) never ends or answers a turn.
- Only the final text after the last tool call is delivered. A turn owns one progress message, edited with its first visible line, then replaced by the reply, split under the channel's limit and never inside a code block. Every `remember` result ends with `next`, the shape of the answer that follows the call (first and whole, the filing one clause at its end), and a final text that only reports a filing (`remember`, `schedule`, `hold` or `settings` called last, the answer above the call or never written) bounces once, a `stub` row in the shadow ledger the morning diff counts. In a room with people, a final shaped as the owner rooms' status board (a line opening on ☑, ☐, ⛔, 🟦 or 🟨, the colour key, "unblocks:") bounces once for two or three plain sentences, a `board` row. A fenced block a room posted on an earlier day of the last 14, equal once each line is stripped, blank lines dropped, runs of spaces made one and the fence's tag left out, is turned back once per result, in `send` before it posts and in the final text at Stop, naming the day and time it first went out and asking for a line-by-line re-read against today, a `paste` row; the room's next send goes out. In an owner's room, a document (.docx, .pdf, .xlsx, .pptx, .txt, .md, .csv) or a pasted block going out through `send` or in the final text with no claims sheet written that turn (a file whose name holds claims, beside the document or in the work folder: one row per claim, its source line, the quote) is turned back once per result the same way, saying what the sheet is and where it goes, a `sheet` row; a room with people only ledgers it.
- Files go out on one path, up to what the bot can send (measured: 20,971,520 bytes, Discord's own answer, above discord.py's 10,485,760 for a tier 1 guild). A file a crash left unconfirmed is sent again from its outbox snapshot, labelled, unless the room already shows it; the message runs again told which files are in the room.
- An edit of a message still waiting revises it before it runs; an edit of one already running or answered comes in again, marked; a message deleted while it waits never runs. A reply carries the message it answers.
- A failed turn takes the action `failures.toml` gives its class: transient reruns the same session (twice at most), overflow compacts then reruns, auth and quota rest that account (doubling per account and kind, kept across restarts; a rate limit instead rests the account for the model it hit until the reset the stream names, else the account's weekly reset from its last reading, an hour at the least) and continue the same turn under the same card on the next account, resuming the same session; when every account is out of the model a room was put on, the turn runs on rooms.toml's model under the same card, which says so, and the next message tries the pinned model again; a session that cannot be resumed starts fresh with a one-line recap; anything else is a visible notice. An empty reply resumes the same session once more on a new process, then starts fresh with the recap line, which says the day log holds what was said; the card names which happened.
- A turn Claude Code answered on a fallback model after a block stands, and its card and ledger row say so; the room's next turn starts a fresh session on the room's own model.
- After 30 idle minutes the process closes; the next message resumes the session.
- A room compacts between turns, never inside one. Idle 25 minutes (budgets.toml `[session] idle_compact_after`) with its session at 0.7 of its compaction window or more (`idle_compact_at`), it is compacted then, in the background, the way `yerk room compact` does it (the recall pack comes back after it), so the next message finds it small instead of waiting minutes in its own turn for Claude Code's compaction. The session's size is the last call's usage as the stream says it, kept in each turn's ledger row, so a restart keeps it. One try per growth: after a compaction, kept or failed, the next waits for a turn to grow the session again, and a failed one is logged once. A message that comes in during a compaction (this one or `yerk room compact`) waits and runs right after it, and the log says how long it waited. A room's own keys in rooms.toml move the line; `idle_compact_at = 0` turns it off, and so does a window left to the model (`compact_window = 0`), whose size Yerk AI cannot know.
- A hop resumes the same session on the next account by the transcript's absolute path (`--resume` takes one, as the docs promise), learnt from the first hook call of the session and kept in the room's binding; the id alone is searched only in the resuming account's own `projects` folder. Pointing every account's `projects` folder at one (a symbolic link) is an optimisation that lets the id be found anywhere, not a requirement.
- Every call to the daemon (`/hook`, `/mcp`, `/control`) carries the `x-yerk-secret` header: a room process sends the token minted for it at start and bound with its session (the daemon knows the room by that binding, never by a header a caller picks), the CLI and the job units send the install's secret from `secrets/yerk-http.secret` under the state folder (never inside a room's layer, so no room's read rule reaches it; `yerkd.json` names the path), and a worker's own server sends `secrets/yerk-worker.secret` beside it, which opens `recall` and `read_memory` only. A hook call no binding explains is answered `{"yerk": "unbound"}` and logged, never with a silent `{}`.
- The day log's line is `- HH:MM:SS+hh:mm room#id role@who: body [c:class] [m:id]`: the offset is each line's own from the configured IANA zone, the room's stable id (`id` in rooms.toml, else its channel) rides beside its name, the author is a role and a handle, and the class (private, room or shared) says who may read the line back. `recall` and `read_memory` return to a room only shared files and its own lines; the owner's rooms read everything. The daemon rewrites lines written before this shape once at its start, before any channel opens, each file that changes copied to `backups/` first (`yerk memory migrate-daylogs` runs the same rewrite by hand; both hold the lock capture holds, so no line is lost to the rewrite), and the reader still parses the old line.

The daemon's one local HTTP server carries `/mcp` (the tools `send`: text, or a file from the sending room's own folders, to a room; `hold`: end the turn while waiting on a named event or worker; `recall`: ranked chunks of the memory tree with path, line and a `file:line` to cite; `read_memory`: exact lines of a file inside the memory tree, nothing outside it), `/hook` (the clock and metadata lines and the recall part, keyed on the session id through the room-to-session table; the recall pack after a compaction; the Stop checks) and `/control` (`yerk room close`, `yerk room compact`).

## What you see

Every card, notice and status line follows one rule set, written down with an example of each in [STYLE.md](STYLE.md): the state first (🟢 done, 🟠 running or partly, 🔴 not done, ⚪ nothing to do), one short line per item at phone width, no file paths or exit codes in a room (a report is "report saved" with `yerk worker report <id>` behind it), times as a person says them, and the same words in every room from one vocabulary, `yerk_ai/words.py`. The developer detail lives behind `yerk worker report <id>` and `yerk status --full`. `yerk abilities` lists every ability one line each, built or known but not built (voice is described, not shipped, and `yerk explain voice` says how it would be built and why it is not); `yerk config get presentation` prints the presentation settings with their plain words. `tests/test_style.py` holds every renderer to it.

## What it knows it can do

`abilities.toml` holds 84 abilities: 27 built and 57 described, known and not built. The described ones are the abilities a long-running personal install grew over months, written neutrally: reading bank balances read-only, job applications that are true and reviewed, texting as you with a preview and a veto, a browser on its own profile, a morning brief, watching a page, and 51 more. Each carries what it is, how it would be built, its tier (50 free, 3 need a provider key, 4 are paid), what it needs, what it would cost, its free path and why it is not built yet; one that is partly built names the built ability under `upgrade`. `yerk abilities` lists them one line each, `yerk explain NAME` answers for any one, a room that names one gets that entry's answer before the model starts, and "what can you do" gets every name by its state. `examples/abilities/` shows five of them with placeholder values; `tests/test_abilities.py` keeps every entry in that shape and free of anything shaped like a person's name and role, a room, a handle, an address, a dollar figure or a date.

## Voice notes

A voice note or recording sent to a room arrives with one line under its `[attachment]` line: the room takes in the sound only through the `transcribe` tool on Yerk's own server (the daemon has the network, a room's shell has none), which returns the words with a timestamp per segment and saves them beside the audio as `NAME.transcript.txt`, and a turn that ends without calling it bounces once.
Pass 1 is OpenAI whisper-1 on the install's OpenAI key (`secrets/openai.key`, ffmpeg on the machine); with `secrets/groq.key`, pass 2 runs Groq whisper-large-v3-turbo on the same chunks and marks uncertain, with both readings, a segment the two disagree on; every paid call is a spend row, the morning diff says the day's total, and a recording past US$1 waits for the owner's yes (`yerk explain transcribe`).

A room answers with a voice note when the owner asks for one or to say it out loud (the mechanics line), through the `voice_note` tool on the same server: the box's recipe, MiniMax speech-2.8-hd first (`secrets/minimax.key`) and Fish Audio s2.1-pro-free on any MiniMax failure (`secrets/fish.key`), the whole note on one voice; `[[pause]]` alone on a line between sections, `(break)` for a short pause, and an optional `voice/pronounce.txt` in the private folder for MiniMax's pronunciation rules, one `word/say-it` a line.
The joined sections go to -14 LUFS and opus 48 kHz in ogg under the room's `work/voice/`, and the first 20 seconds are read back by whisper-1 and must match the script's opening, or the note is deleted; `send` posts it with no text as a Discord voice message (flag 8192, its duration and waveform), or as the plain file when Discord refuses that form, and says so; every paid call is a spend row and a note past US$1 waits for the owner's yes (`yerk explain voice_note`).

## Web reach

Rooms read pages and search the web through one plug-in, `plugins/web` (`yerk-web`, an MCP server in JavaScript with its own package.json and tests), outside the harness: it is not in budgets.toml's [code] count, and the harness's only part in it is the ledger's `spend` table and the morning diff's spend line. A room attaches it with an `mcp` table and allows its five tools (rooms.toml.example has both, commented):

- `web_fetch(url, max_chars?)`: the fetch ladder. Free rungs on the machine first, each only when installed and skipped without a try when not: F1 a plain fetch with browser headers, F2 the machine's own stealth browser (CloakBrowser, or Chromium with playwright-core), F3 trawl's captcha-solving browser. Then Browserbase, paid, with its key: L1 Fetch, L2 Fetch with proxies, L3n a browser session without proxies, L3 one with proxies, captcha solving and a saved login per site. Every read passes the same blocked-page check; a page that stays shut comes back named by its wall (login_required, captcha_unsolved, geo_blocked, http_404 and the rest) with every rung tried. F2 stops waiting once the page's text is readable, settled and has no request in flight (6 s at most, 10 s while a short page is still loading), and waits out only a challenge that clears on its own. A page whose text sits behind a modal dialog that hides the rest reads as the page, not the dialog. When two free rungs meet the same captcha or challenge, L1 and L2 are skipped (a fetch cannot solve one) and the whole call is capped at 45 s. Per site, and per path class within it (the host and the path's first route word, so a site's listing pages and its search pages keep their own), it remembers which step read it and starts there next time (one step cheaper once a day, since sites change), a host that refused the free rungs rests from them a day, and the free rungs keep to 30 reads a minute and 6 a host in one window every room's process shares.
- `web_search(query, count?)`: Exa first, then Parallel's paid Search API, each with its key, then You.com's and Parallel's keyless engines; the answer names the engine. When the query asks for a video and a `yt-transcript` command is on the machine, transcript excerpts join that result.
- `web_research(query, effort?, schema?, system?)` and `web_research_result(run_id)`: the Exa Agent, one cited research job a call, at four fixed efforts (1.2, 2.5, 10 or 50 US cents), the dearer xhigh behind the owner's yes in words and the metered modes refused, under one daily cap of two US dollars for every room, booked before the request goes out.
- `web_image(url, max_bytes?)`: one picture in a post or a page, a jpeg, png, gif or webp of 15 MB at most, read by F1 as a browser asks for a picture and by L1 and L2 only when a site refuses that (never a browser rung), saved in the room's work folder as `web/<the URL's sha1, 12 hex>.<ext>` for the room's own Read, with its path, bytes, type, width, height and rung, the same URL within a day answered from that copy and a private host refused as web_fetch refuses it.

Keys are files in the private folder's `secrets/`, one each, 0600, read on every call and never printed: `exa.key` (search and research), `parallel.key` (search), `browserbase.key` and `browserbase-project.id` (the paid rungs). With none, pages are read from the machine and search runs on the keyless engines; research needs its key. Settings live in an optional `web.json` in the private folder, `{"fetch": {...}, "search": {...}, "research": {"dailyUsd": 2}}`, with the names the code's DEFAULTS use (`plugins/web/lib/fetch/util.js`, `plugins/web/lib/search/util.js`); a key is never read from it. State is `<state>/web/`: the site memory, the Browserbase contexts that keep saved logins, the meters, the call logs (hostnames and query hashes only) and the research runs. Every paid call is one row in the ledger's `spend` table (room, tool, engine, US dollars as billed or at list price), and the morning diff says `spent yesterday: US$0.11 on 2 calls`. Install: Node 22.13 or newer, then `npm ci --omit=dev` in `plugins/web`. Tests: `npm test` there runs the offline cases, and the stealth browser's own cases against a local page server when the machine has its engine; `YERK_WEB_LIVE=1 YERK_PRIVATE=<private folder> npm test` adds a live page read and, with a search key, one live search.

## Yerk knows its harness

A room asked how Claude Code works, or whether its own rules are written the way the docs say, answers from a read. `yerk docs refresh` fetches the Claude docs Yerk runs on into `<state>/docs/claude/<slug>.md`, each headed by its source, fetch time and content hash: the prompting guide, the prompting page of each model in models.toml, and the Claude Code pages on settings, hooks, memory, sandboxing, MCP, the command line and the system prompt flags (the sites answer `Accept: text/markdown` with Markdown). The folder is a memory root of class shared in every install, a room with its own `also` included, so a room's own recall finds the docs in every room and cites them as `docs/claude/<slug>.md:line`, every one below the owner's own notes, which say how this install's things are where the docs say how Claude works anywhere; `yerk docs list` and `yerk docs show NAME` read what is kept. What a room is handed per message (the lines on a name or topic it asks about, the past-tense search) never holds the docs, so a question about the owner's day is not answered from a prompting page by accident. `yerk doctor` fetches them once a week (`[docs] fetch = false` turns that off; `yerk docs refresh` still fetches when run), and a page whose hash moved is a line in the next morning diff (`docs changed: <slug>`), since a changed guide means the rules may be stale against it.

The doctor also scores every rule file a room loads (the mechanics, its persona, rulebook and voice, the rules file) against the guide: a negative with no why in its line, a shouted word, an example outside `<example>` tags, an alarm mark on an instruction, and one topic said in two files a room loads. A count past budgets.toml `[shape]` is a finding, a rule filed with `remember` and `job` in the last day that misses the shape is named by its cite (the room is never refused the rule), each room's report is `docs/shape/<room>.md` (class room, so a room reads its own), and the morning diff carries the totals. `yerk docs shape` prints the reports without a doctor run and `yerk docs shape --rules` each count's exact rule. The mechanics say how a rule is written (what to do, then its why, one line; a ban only where the thing itself is the point; an example inside `<example>` tags, marked landed or bounced) and that a question about the harness or the room's own rules is answered from `docs/`, never from memory; the mechanics and the example layer are in that shape.

**Upgrading:** yerkd.toml gains an optional `[docs]` table: `pages` (slug = URL, replacing the default list whole), `refresh_days` (7), `fetch` (true; false and the doctor never fetches), `topics` (name = regex, added to the shipped topic map) and `acronyms` (words of four or more capitals that are names, not shouting). budgets.toml gains `[shape]` (every threshold 0). The memory index takes `<state>/docs` as a new root at its next start, so every file is chunked again once; run `yerk docs refresh` once to fetch the pages before the first weekly run.

## Ledgers

One SQLite file, `ledger.sqlite`: `turns` (account, models, time to first visible event and to the end, how it ended, which messages it answered), `inbound` (every channel message by its id, written before anything runs; a crash runs it again once, marked), `outbound` (every message posted, with the id the channel returned, and a card's text at each post and edit, so a card the reply replaced can still be read back), `holds`, `health` (the daily call per account: pass or fail, login method, an identity fingerprint, never the email), `spend` (one row per paid call a plug-in makes: room, tool, engine, US dollars; the morning diff's spend line). A turn row also names the failure's source in the table and the hop that brought the turn to its account.

## Files

- `budgets.toml`: every size limit, in characters as Claude Code counts them
- `failures.toml`: failure classes and what each one does next
- `units/`: the daily health call's systemd user timer, the memory index service and the weekly recall bench timer (copy and enable them yourself)
- `abilities.toml`: every ability, what it needs and its cost tier (free, key or paid), with the free path
- `rooms.toml.example`, `accounts.toml.example`: templates for your private folder
- `yerk_ai/lifted/`: code taken from other MIT projects and from the author's own tools, each file with its origin; see `NOTICE`
- `yerk_ai/channels/`: channel adapters (Discord)
- `plugins/web/`: the web plug-in (README "Web reach"), outside the [code] count
